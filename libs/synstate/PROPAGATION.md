# synstate の伝播：実装仕様

1 回の更新が、どのノードを、どの順に、何回訪れるかの仕様と、それを実現するデータ構造です。対象のコードは `src/core/class/` の次のファイルです。

| ファイル                       | 役割                                                        |
| :----------------------------- | :---------------------------------------------------------- |
| `propagation-state.mts`        | 更新のキュー（`UpdateQueue`）と、コピーごとのモジュール状態 |
| `observable-base-class.mts`    | `setNext` で子をキューに入れる。キュー用のフィールド        |
| `manager-observable-class.mts` | `startUpdate` で更新を開き、キューを処理し、閉じる          |
| `observable-node.mts`          | ノード同士が呼び合うメンバーの型                            |

利用者向けの解説は synstate-docs の「How SynState Solved the Glitch」にあります。

## 用語

- **マネージャー**：自分で更新を始めるノード。ルート（`source`、`createState` など）と、非同期の子（`debounce`、`switchMap` など）です。`ManagerObservableClass` を継承します。
- **深さ**：ルートは 0、子は親の深さの最大 + 1。ノードを作るときに決まり、変わりません。
- **更新**：マネージャーの `startUpdate` 1 回分。更新ごとにトークンを 1 つ作ります。
- **トークン**（`UpdateToken`）：更新を表すオブジェクト。値を出したノードは `updateToken` にこれを書きます。トークンは、その更新のキューでもあります。
- **値を出す**：ノードが `setNext(value, token)` を呼ぶこと。`filter` が値を通さなかったときなどは呼びません。
- **届く**：親のどれかがその更新で値を出したこと。

## 保証すること

1 回の更新 U について、次の 4 つが成り立ちます。

1. **glitch-free**：ノードの `tryUpdate` が呼ばれる時点で、その親はすべて、U で値を出すかどうかが確定しています。
2. **届いたノードだけを、ちょうど 1 回**：U が `tryUpdate` を呼ぶのは、U の中で親のどれかが値を出したノードだけで、1 ノードにつき 1 回です。
3. **深さの昇順**：浅いノードから順に訪れます。同じ深さのノードの順序は決めません。
4. **必ず終わる**：グラフが DAG であること（構築時に検査）と 2 から従います。

U の中で作られたノードは、作られた後に親が U で値を出したときだけ訪れます。U の中で complete したノードは訪れません。

## データ構造

### ノードのフィールド

すべてのノード（`ObservableBaseClass`）が持つ、伝播のためのフィールドです。

| フィールド    | 型                            | 意味                                                                   |
| :------------ | :---------------------------- | :--------------------------------------------------------------------- |
| `depth`       | `number`                      | 深さ                                                                   |
| `updateToken` | `UpdateToken`                 | 最後に値を出した更新のトークン。まだ出していなければ `notUpdatedYet`   |
| `children`    | `Set<ChildNode> \| undefined` | 子の集合。最初の子が来たときに作る                                     |
| `queuedFor`   | `UpdateToken \| undefined`    | このノードを最後にキューに入れた更新のトークン。訪れた後もそのまま残す |

ノードは子への辺だけを持ちます。祖先のルートへの登録や、ルートごとの子孫一覧はありません。

### コピーごとのモジュール状態

`propagation-state.mts` のモジュールに 1 組だけあり、更新から更新へ使い回します。

| 名前                   | 意味                                                                          |
| :--------------------- | :---------------------------------------------------------------------------- |
| `mut_bucketSets[l]`    | 入れ子の段 `l` の更新が使うバケットの組（下の `Bucket` の配列）。0 が一番外側 |
| `mut_queueState.level` | このコピーで開いている更新の数。1 なら一番外側                                |
| `mut_propagation`      | 開いている `startUpdate` の数と一番外側のトークン（`runAfterPropagation` 用） |

バケットの組は、深さごとのバケット（`Bucket`）の配列です。`buckets[index]` が深さ `base + index` のバケットで、次の 2 つを持ちます。同時に読み書きする 2 つを 1 つのレコードにまとめています。

| フィールド | 意味                                   |
| :--------- | :------------------------------------- |
| `nodes`    | キューに入ったノードを並べた配列       |
| `length`   | `nodes` の先頭から何個が使われているか |

配列は作り直さず、長さを 0 にすることで空にします（論理的な初期化）。そのため一番外側の更新が確保するのはトークン 1 つだけです。同じ段の更新が同時に 2 つ開くことはないので、段ごとに 1 組で足ります。

### 更新のキュー（`UpdateQueue`、トークンの実体）

| フィールド               | 意味                                                                                 |
| :----------------------- | :----------------------------------------------------------------------------------- |
| `#base`                  | 更新を始めたマネージャーの深さ + 1。深さ `d` のノードはバケット `d - base` に入る    |
| `#buckets`               | この更新が使うバケットの組。`mut_bucketSets[level - 1]`                              |
| `#mut_size`              | 使っているバケットの数。走査中にも伸びる                                             |
| `#mut_isOpen`            | 更新がまだ終わっていないか。`isOpen` として、別のコピーからも読める                  |
| `#mut_queuedDespiteMark` | 開いている別の更新の印がついたまま、この更新がキューに入れたノードの集合。重複を防ぐ |

## 1 回の更新の流れ

`ManagerObservableClass.startUpdate(value)`：

1. `openUpdate(depth)`：`level` を 1 増やし、`UpdateQueue` を作ってトークンとして返す。キューは段 `level` のバケットの組を使う。
2. `beginPropagation(token)`：`runAfterPropagation` が使う段数を増やす。
3. `setNext(value, token)`：値とトークンを書き、**子をキューに入れてから**購読者を呼ぶ。
4. `drainUpdate(token)`：バケットを浅い順に処理する。
5. `closeUpdate(token)`（`finally`）：例外で残ったスロットを空にし、`isOpen` を偽にして、`level` を 1 減らす。
6. `endPropagation()`（`finally`）：一番外側なら、`runAfterPropagation` で延期した処理を走らせる。

### 子をキューに入れる（`enqueueChildren`）

値を出したノードは、`setNext` の中で `enqueueChildren(children, token)` を呼び、トークンの `enqueueChildren` に渡します。ノードがどのコピーのものでも、子は**トークンを発行した更新の**キューに入ります。各子 `child` について：

1. `child.queuedFor === token` なら、この更新のキューにもう入っているので何もしない。
2. `child.queuedFor` が別の、まだ開いている更新のトークンなら、その印は書き換えない。`child` が `queuedDespiteMark` にあれば何もせず、なければ加える。
3. それ以外（印がない、または終わった更新の印）なら、`child.queuedFor = token` とする。
4. `index = child.depth - base` を求め、`bucket = buckets[index]` の `nodes[bucket.length]` に `child` を書いて `bucket.length` を 1 増やす。`size` を `index + 1` 以上に伸ばす。

### キューを処理する（`drain`）

`index = 0, 1, …` と `size` まで進みます。`size` は処理中に伸びます。各 `index` で：

1. `buckets[index]` の `length` を読み、`slot = 0, …, length - 1` の各ノードについて、スロットを `undefined` に戻してから、complete していなければ `tryUpdate(token)` を呼ぶ。
2. `buckets[index].length = 0` とする。
3. 最後に `size` を 0 にする。

`tryUpdate` の中でノードが値を出すと、その子は `index + 1` 以上のバケットに入ります。処理中のバケットは伸びないので、`length` を先に読んでよく、長さを 0 に戻すのは処理の後で構いません。スロットを `undefined` に戻すのは、complete して他から参照されなくなったノードを、スロットが生かし続けないためです。

`queuedFor` は戻しません。後の更新は別のトークンを持つので、古い印は手順 1 に当たらず、手順 3 で上書きされます。

### 閉じる（`close`）

`size` までのバケットの、使われているスロットを `undefined` で埋め、長さを 0 にします。正常に終わった更新では `size` が 0 なので何もしません。そして `isOpen` を偽にし、`queuedDespiteMark` を捨てます。

### 不変条件

更新と更新のあいだ、どのコピーでも次が成り立ちます。

- どのバケットも、`length` が 0 で、`nodes` のスロットがすべて `undefined`。
- 開いている更新はない。したがって、どのノードの `queuedFor` も、終わった更新の印か `undefined`。

更新中は、`queuedFor` がある開いた更新 t の印であれば、そのノードは t のバケットに入っています（訪れ済みのこともあります）。

## 入れ子の更新

購読者や射影の中から別の state に書くと、外側の更新の途中で内側の更新が始まり、内側を最後まで処理してから外側に戻ります。

- 内側の更新は 1 つ深い段のバケットの組を使うので、外側のバケットには触れません。
- 外側のキューに入っているノードに内側の更新が届くと、外側の印は開いた更新の印なので書き換えず、内側は `queuedDespiteMark` で重複を防いでそのノードを訪れます。外側は後でもう一度そのノードを訪れます。これは以前の実装と同じ振る舞いです。
- 内側が先に印をつけたノードに、内側が閉じてから外側が届けば、終わった更新の印なので上書きしてキューに入れます。
- 入れ子は 1 つのコピーで `maxUpdateNesting`（100）段までです。それを超える更新を開こうとすると、`openUpdate` が `panic` します。購読者が自分に届く state に書き戻し続けるループは、こうしてスタックがあふれる前に、原因を示すエラーで止まります。エラーは開く前に投げるので、後片付けは外側の各 `startUpdate` の `finally` だけで済みます。

## 複数のコピー

1 つのプログラムに synstate が 2 つ入り、グラフがコピーをまたぐことがあります（一方のコピーの state に、もう一方のコピーの `map` をつなぐなど）。そのための決まりは 3 つです。

- **トークンがキューを運ぶ**：子をどのキューに入れるかはトークンで決まり、値を出したノードのコピーでは決まりません。
- **開いた更新の印は書き換えない**：コピー A の更新の途中でコピー B の更新が始まると、どちらもそれぞれのコピーで一番外側で、バケットの組もそれぞれのコピーのものです。B が A の印のついたノードに届いても、`isOpen` で A がまだ開いていると分かるので、印はそのままにして `queuedDespiteMark` で重複を防ぎます。これで一方の更新が他方の重複判定を壊しません。
- **コピー間で比べる番号を持たない**：更新番号のようなコピーごとの値は、コピーをまたいで比べられません。そのため「更新中に作られたノード」を番号で判定せず、子をキューに入れてから購読者を呼ぶ順序で扱います。

ノードとトークンは互いに、メソッドと公開フィールド（`queuedFor`、`setQueuedFor`、`isOpen`、`enqueueChildren` など）だけを使います。`#private` フィールドは別のコピーのクラスからは読めないためです。バージョンの違う synstate 同士がグラフをまたぐことは想定していません。

## 更新中に作られるノード

`setNext` は子をキューに入れてから購読者を呼びます。そのため、

- 購読者が作ったノードは、親が値を出した後に作られるので、この更新ではキューに入りません。ノードは親の新しい値から作られているので、訪れる必要もありません。
- この更新の途中で作られ、親がこれから値を出すノードは、親が値を出したときにキューに入ります。訪れないと古い値のまま残るためです。以前の実装は、更新中に登録されたノードを一律に訪れなかったので、この場合に古い値が残っていました。

## 正しさの論証

更新 U（トークン t）について、保証 1〜4 を示します。

**補題（後戻りしない）**：U の中で t を書いて値を出せるのは、U を始めたマネージャーと、U の `drain` から `tryUpdate(t)` を呼ばれたノードだけです。深さ `d` のノードが値を出すと子は `d + 1` 以上のバケットに入るので、処理中のバケットとそれより浅いバケットには何も足されません。

**1（glitch-free）**：`drain` が深さ `d` のバケットを処理し始めた時点で、`d` より浅いバケットは処理済みで、補題よりこれ以上ノードが足されません。深さ `d` のノードの親はすべて `d` より浅いので、U で値を出すかどうかはもう変わりません。

**2（届いたノードだけを 1 回）**：子がキューに入るのは親が t で値を出したときだけです。2 回目以降は `queuedFor === t` か `queuedDespiteMark` で弾かれます。印 t は U が閉じるまで他の更新に書き換えられません（書き換えるのは終わった更新の印だけ）。また、ノードを `queuedDespiteMark` に入れたなら、そのとき印は開いた別の更新 V のものです。キューに入れているのは U なので U がいま動いており、V は U を内側に含む外側の更新（別のコピーのものも含む）で、U より後に閉じます。U とその内側の更新は V の印を書き換えないので、U が開いている間その印は V のままで、手順 3 で 2 回目に入ることはありません。届かなかったノードはキューに入らないので呼ばれません。以前の実装では、届かなかったノードの `tryUpdate` も呼ばれましたが、組み込みのオペレーターはすべて、どの親も t を持たなければ何もせずに戻るので、結果は変わりません。

**3（深さの昇順）**：バケットを浅い順に処理するからです。

**4（終わる）**：各ノードは U で高々 1 回しかキューに入らず、ノードの数は有限です。

## コスト

- **更新**：届いたノードの数を n、そのノードから出る辺の数を m として O(n + m)。届かないノードには触れません。
- **更新の確保**：トークン 1 つだけ。バケットの配列は段ごとに使い回し、空にするのは長さを 0 にするだけです。配列が伸びるのは、その段で今までより多くのノードが同じ深さに入ったときだけです。
- **開いた別の更新と競合したとき**：`queuedDespiteMark` の集合を確保します。入れ子の更新が外側のキューにあるノードに届くときと、コピーをまたぐときだけの、まれな場合です。
- **構築**：子 1 つにつき親への登録だけ。以前の実装の「ノード数 × ルート数」の登録はありません。
- **メモリ**：ノードあたり 1 フィールド（`queuedFor`）と、段ごとのバケット（一度に同じ深さに入った最大のノード数ぶん）。ルートごとの子孫一覧はありません。

届いたノード 1 つあたりの手間は、以前の実装で一覧を読むより少し多くなります。キューへの出し入れで数回の書き込みが増えるためです。そのため、値がすべてのノードに届くグラフでは速くならず、少し遅くなることもあります。速くなるのは、値が途中で止まる更新（`filter`、`skipIfNoChange`）と、多くのルートが合流するグラフの構築です。

## 以前の実装からの変更

以前は、各マネージャーが子孫を深さごとの Set の配列（`propagationOrder`）で持ち、更新のたびにそれを全部たどって `tryUpdate` を呼んでいました。子孫は、自分に値を届けうるすべてのマネージャー（`managers`）に登録していました。

利用者から見える変更：

- `createChildObservable` などで書く `tryUpdate` は、親のどれかが値を出した更新でだけ呼ばれます。以前はマネージャーの更新のたびに呼ばれていました。
- `UpdateToken` は symbol ではなくオブジェクトのブランド型です。
- `setNext` は、購読者より先に子をキューに入れます。
- 更新中に作られ、親がその後で値を出すノードは、その更新で更新されます。
- 同じ深さのノードを訪れる順序は、親が値を出した順になります。以前は登録順でした。
