# テストのオラクルをどこから調達するか

> 姉妹資料 `ai-code-review-slides/` から分離した骨子・素材まとめ。
> あちらの主題は「AI に渡すタスクを、レビューが安く済む形に変換する」で、その 4 つの源泉のうち
> **D：統計的に網羅できる** を掘り下げたのがこの資料。
> 対象オーディエンス：LLM 勉強会の参加者。

---

## 0. この資料の主張

1. テストは「**入力**」と「**合否を判定する仕組み（オラクル）**」の 2 つでできている。
2. **入力の自動生成が安くなっても、オラクルが人間の手書きなら律速は動かない。** 100 万件の入力は生成できても、100 万個の期待値は書けない。
3. だから手法は「**オラクルをどこから調達するか**」で分類できる。これが fuzzing / property-based / differential / metamorphic の違いそのもの。
4. fuzzing が安いのは、**処理系とサニタイザがオラクルをタダでくれる**から。裏返すと「**落ちないが答えが違う**」は原理的に見つからない。
5. 入力生成器を書くコストは残るが、**それこそ AI に書かせるべきコード**（姉妹資料の源泉 A・C）。

---

## 1. 前提：オラクル（合否を判定する仕組み）

- 普通のユニットテスト `assert.deepStrictEqual(f(1), 2)` では、`2` がオラクル。**入力 1 件につき 1 個、人間が書いている。**
- 入力をマシンに作らせる手法では、**ここが律速になる**。
- したがって以下の 4 手法は、「**入力ごとに期待値を書かずに済むオラクルを、どこから調達するか**」で整理できる。

| 手法           | オラクルの出どころ                             | 人間が書く量         |
| -------------- | ---------------------------------------------- | -------------------- |
| fuzzing        | 処理系・サニタイザ（クラッシュ / ハング / UB） | **ゼロ**             |
| property-based | 人間が書く不変量                               | 実装ごとに数行       |
| differential   | 参照実装・旧実装の出力                         | ゼロ（比較するだけ） |
| metamorphic    | 入出力の間に成り立つ関係                       | 関係ごとに数行       |

---

## 2. fuzzing（ファジング）：オラクルがタダで手に入る場合

**「オラクルが無料」とは何か。** fuzzing が合否に使うのは、期待値ではなく **「落ちたかどうか」** である。

- クラッシュ（segfault、panic、未捕捉の例外）
- ハング（無限ループ、タイムアウト超過）
- サニタイザが検出する未定義動作（バッファオーバーラン、use-after-free、未初期化領域の読み出し）
- コード中に既に埋め込まれている `assert` の失敗

これらに共通するのは、**入力が何であれ成り立つべき性質**であり、かつ **判定する仕組みを処理系やサニタイザが最初から持っている**こと。だから人間は期待値を 1 つも書かずに、マシンが作った 100 万件の入力をそのまま回せる。

- 正確に言えば「**入力 1 件あたりの判定コストがゼロ**」。`assert` は人間が書くが、入力ごとにではなく実装ごとに 1 回でよい。ここがユニットテストとの決定的な差。

### 2.1 具体例

- **C/C++ のデコーダ**：画像・フォント・圧縮ライブラリ（libpng、FreeType、zlib）に壊れたバイト列を食わせ続ける。ASan（AddressSanitizer）が heap-buffer-overflow や use-after-free を検出した瞬間に落ちる。Chromium / OSS-Fuzz が回しているのはこれ。
- **処理系**：ランダムなプログラムを生成して食わせ、内部の `assert` が落ちるか、ハングするかを見る。
- **JavaScript / TypeScript で同じことをやるなら**、メモリ安全性がない代わりに以下が無料のオラクルになる：
    - **投げないはずのものが投げる**：`Result` を返す契約のバリデータ（`ts-fortress` 等）が例外を投げたら、入力が何であれ実装の誤り。**契約自体が無料のオラクルになっている**例。
    - **想定外の例外型**：深くネストした JSON を再帰下降パーサに与えて `RangeError: Maximum call stack size exceeded`。
    - **止まらない**：ReDoS。病的な入力で正規表現が指数時間に落ちる。タイムアウトが判定してくれる。
    - **自分で埋めた事前 / 事後条件の `assert`**。
- **入力の作り方で効きが変わる。** 完全ランダムなバイト列はほとんどが入口で弾かれて奥まで届かない。だから実際には、シード corpus からの変異、文法を知った生成、カバレッジ誘導（libFuzzer がやっているのはこれ）を使う。

### 2.2 限界：「クラッシュしないが答えが違う」は原理的に見つからない

- 判定条件が「落ちたか」だけなので、**正常終了しているが答えが間違っている**バグ（silent wrong answer）は素通りする。
- 例：金利計算が 1 円ずれる、ソートが安定でない、バリデータが不正な入力を受理してしまう。どれもクラッシュしないので fuzzer は緑のまま。
- これは実装の質の問題ではなく **オラクルの守備範囲の問題**（オラクル問題）。仕様の正しさを問いたいなら、3 章以降に移るしかない。

### 2.3 だからパーサ・デコーダ・サニタイザ向き

- これらは **攻撃者が入力を選べる境界**であり、そこで一番困るバグが「クラッシュ／メモリ破壊」そのもの。
- つまり **タダで手に入るオラクルの守備範囲と、実際に一番気にしているバグの分布が一致している**。安いオラクルのままで十分な価値が出る。
- 逆に、ビジネスロジックに fuzzing をかけても「落ちないが金額が違う」を見逃すので割に合わない。

### 2.4 守備範囲を広げる手当て

- 実装に事前 / 事後条件を `assert` として埋める（Design by Contract）。書いた分だけ無料のオラクルが増える。
- 往復変換や参照実装との差分（4 章）と組み合わせる。パーサなら `parse(print(x)) === x` がそのままオラクルになる。

## 3. property-based testing：不変量を人間が書く

- 人間が書くのは **入力ごとの期待値ではなく、どんな入力でも成り立つ性質**。入力は fast-check などが生成する。
- **人間のレビュー対象が「実装」から「性質」に縮む**のがポイント。性質は数行で書けて、しかも仕様そのもの。
- 実務で効くのが **shrinking（反例の自動最小化）**。「1000 要素の配列で落ちました」ではなく「`[0, 0]` で落ちます」まで縮めてから報告してくれるので、デバッグまで安くなる。

### 3.1 書ける性質の型（引き出しとして持っておくと書ける）

| 型             | 形                              | 例                                                    |
| -------------- | ------------------------------- | ----------------------------------------------------- |
| 往復           | `decode(encode(x)) === x`       | シリアライザ、パーサ + プリンタ、URL エンコーダ       |
| べき等         | `f(f(x)) === f(x)`              | フォーマッタ、codemod、正規化関数                     |
| 不変量         | `f(x)` が常に満たす条件         | `sort` の結果は昇順、かつ元と同じ multiset            |
| 代数則         | `f(f(x)) === x`、交換則・結合則 | `reverse`、`negate`、集合演算                         |
| 生成器との整合 | 生成した合法値は必ず受理される  | バリデータ × そのスキーマからのサンプル生成器         |
| モデルとの一致 | 素朴な実装と同じ結果になる      | 自作の Map / キャッシュ vs 標準 `Map`（操作列を生成） |

### 3.2 注意

- スキーマからバリデータを生成する例（姉妹資料 2.3）なら：**スキーマから生成した合法データは必ず通る**、**必須フィールドを 1 つ削ったら必ず落ちる**。どちらも生成器を書いた AI とは独立に、スキーマだけを見て書ける。
- 落とし穴：**性質が弱いと、緑でも何も言っていない。** 「例外を投げない」だけの性質は、常に `[]` を返す実装でも通る。性質の強さが、そのままレビューの代替率になる。

## 4. differential testing：もう 1 つの実装をオラクルにする

**同じ入力を 2 つの実装に流して出力を比べる。** 期待値を人間が書く代わりに、**もう 1 つの実装に書かせる**。

- **移行**：旧システムと新システムに同じ入力を流して突き合わせる。移行は「参照実装が手元にある」という稀な状況で、この手法が最も強く効く場面（姉妹資料 2.4 の COBOL → Java がまさにこれ）。
- **手作業版 vs 生成版**：手で書いた定義が残っているなら、生成器の出力と差分が取れる。**移行の瞬間だけ手に入るオラクル**なので、捨てる前に使う（姉妹資料 2.2）。
- **素朴な実装 vs 最適化した実装**：遅いが明らかに正しい実装をテスト用に残す。
- **バージョン間**：依存を更新するとき、旧バージョンと新バージョンに同じ入力を流して差分を見る（フォーマッタや lint の更新でリポジトリ全体を両方で走らせる、など）。
- **独立した別実装**：自作 JSON パーサ vs `JSON.parse`。コンパイラのランダムプログラム生成（Csmith）は、**複数のコンパイラの実行結果が食い違ったらどれかがバグ**、という判定でバグを掘り当てる。

**落とし穴：両方が同じように間違っていると検出できない。**

- 生成器と検証器の独立性の問題そのもの（姉妹資料 3.5）。同じモデルに同じ文脈で 2 つ書かせたら、それは 2 つの実装ではない。
- 特に移行では **旧実装のバグまで仕様として再現してしまう**。「一致した」は「新実装が旧実装と同じ振る舞いをする」であって「正しい」ではない。

## 5. metamorphic testing：入力を変形して、出力の関係を見る

**正解が分からなくても「入力をこう変えたら出力はこう変わるはず」という関係だけは分かる**、という場合に使う。オラクル問題の回避策。

4 章との違いは、何を固定するかの軸：

| 手法         | 固定するもの | 比べるもの                               |
| ------------ | ------------ | ---------------------------------------- |
| differential | 入力         | 2 つの実装の出力（一致するはず）         |
| metamorphic  | 実装         | 変形前後の出力（既知の関係を満たすはず） |

- **検索**：クエリに AND 条件を足したら、結果は元の結果の部分集合になるはず。**正しい検索結果が何かを知らなくても言える**のがこの手法の本質。
- **フォーマッタ**：`parse(format(x))` と `parse(x)` の AST は等しいはず。整形器の本質的な性質で、codemod にもそのまま使える。
- **ソート**：入力をシャッフルしても出力は同じはず。
- **コンパイラ**：最適化レベルを変えても、プログラムの出力は同じはず。
- **バリデータ**：必須フィールドを削ったら必ず拒否に転じ、未知の optional フィールドを足しても受理のままのはず。
- **数値計算 / 機械学習**：`sin(x)` と `sin(π - x)` は等しいはず。画像を少し明るくしても分類結果は変わらないはず。
- 落とし穴：関係が成り立つことは、**個々の答えが正しいことを意味しない**。常に空を返す検索エンジンは、部分集合の関係を満たしてしまう。

---

## 6. コスト

- **オラクル（あるいは不変量、あるいは関係）を書けない領域には使えない。** 「この UI が使いやすいか」には効かない。
- **入力生成そのものにコストがかかる。** 構造を持つ入力（有効な TypeScript、スキーマに適合する JSON）を作る生成器は、それ自体がそれなりの実装物になる。
    - ただしこれは朗報でもある：**その生成器こそ、出力が検証しやすく爆発半径も小さい、AI に書かせるべきコード**。源泉 D を用意する作業自体が、姉妹資料の源泉 A と C が効くタスクになっている。
