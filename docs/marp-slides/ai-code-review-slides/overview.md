# AI の書いたコードのレビューがしんどい問題

> スライド本編（Marp / `slides.md`）に入る前の骨子・素材まとめ。各セクションがスライド 1〜2 枚に相当する想定。
> 対象オーディエンス：LLM 勉強会の参加者（日常的にコーディングエージェントを使っている前提）。
> 姉妹資料：`experimental/llm-eslint-harness-slides/`（規律を lint に焼き込む話）。本資料はその上位の「どのタスクを AI に渡すか」の話。

---

## 0. このトークの主張（最初に結論）

1. **AI で速くなったのは実装だけで、レビューは速くなっていない。** 律速工程が実装からレビューへ移っただけ、という状態になりやすい。
2. しかも、自分で書けば理解できていたはずのコードが、**理解されないままリポジトリに積まれていく**。これは資産ではなく負債。
3. 打ち手は「レビューを速くする」ではなく、**レビューが軽くて済む形にタスクを変換する**こと。
4. 鍵は **実装コストとレビューコストの非対称性**。AI コーディングは「作るのは大変だが、正しさの確認は安い」タスクで特に効く。
5. 非対称性は天から降ってくるものではなく、**作れる**。源泉は 4 つ：**有限の出力 / 独立した検証器 / 小さい爆発半径 / 統計的網羅**。
6. どうやっても非対称にできないタスクは存在する（ビジネスロジック、UX、セキュリティ境界）。そこは「AI に書かせない」ではなく、**受け入れ条件を人間が先に機械可読な形で決める**。

---

## 1. 問題提起：レビューがしんどい

### 1.1 何が起きているか

- アイデアを一瞬で実装してくれるのは便利。しかし **レビューの頻度と量が跳ね上がった**。
- 自分の手で書いたコードほどには深く理解しきれていないコード断片が、ソースコードにどんどん蓄積されていく。
- **AI の書いたコードのレビューに、自分で実装するのと同じだけ時間を掛けてしまっては意味がない。**

### 1.3 体感と実測はズレる

- METR の RCT（2025/07 公開）では、熟練 OSS 開発者が慣れたリポジトリで作業したとき、**AI 利用可の条件のほうが 19% 遅かった**。にもかかわらず本人たちは事後に「**20% 速くなった**」と見積もった。
- 注意して扱うべき数字ではある：被験者 16 名 / 246 タスク、2025 年 2〜6 月、当時のツール（Cursor Pro + Claude 3.5/3.7 Sonnet）。METR 自身が現在は「historical な結果であり、現在のツールやワークフローを必ずしも反映しない」と注記している。
- ここで使いたいのは数値そのものではなく **「速くなった感覚は当てにならない」という一点**。感覚ではなく工程を見る。

---

## 2. なぜ「レビューを頑張る」が解にならないか

- **レビューの検出率は、掛けた時間に比例しない。** diff が大きくなるほど 1 行あたりの注意力は落ちる。読み飛ばしは線形には増えない。
- **理解していないコードのレビューは、書くより難しいことがある。** 書くときは自分の意図が既にあるが、読むときは意図を復元するところから始まる。
- **AI に AI のコードをレビューさせる**のは有効だが万能ではない。生成器と検証器が同じモデル・同じ文脈だと **誤りが相関する**（同じ勘違いを両方がする）。独立性が担保できていない検証は、通ったことの意味が薄い。
- 「理解していないコードは merge しない」を貫くと、AI の速度をほとんど捨てることになる。

→ **レビューの努力量を増やす方向には勝ち筋が薄い。タスクの形を変える。**

---

## 3. 中心概念：実装とレビューの非対称性

- 目指すのは **「検証コスト ≪ 実装コスト」** のタスクだけを AI に渡すこと。
- 比喩としては NP の構造：**解を作るのは大変だが、解が正しいことの確認は安い**。数独、因数分解、経路探索。
- **AI コーディングは、実装とレビューに非対称性があるタスクで特に有効。** 逆に言えば、非対称性がないタスクに AI を投入しても、しんどさが実装からレビューへ移動するだけ。
- 重要なのは、**この非対称性は与えられるものではなく、設計できるもの**だという点。次章の 4 つの源泉が、その設計手段。

---

## 4. 非対称性の 4 つの源泉

| 源泉                      | 何が安くなるか                 | 典型例                                     |
| ------------------------- | ------------------------------ | ------------------------------------------ |
| **A. 出力が有限**         | 全量を目視できる。読めば終わる | コード生成スクリプト、スキーマ翻訳         |
| **B. 独立した検証器**     | 正しさを機械が判定してくれる   | 型検査、スキーマ検証、参照実装との差分     |
| **C. 爆発半径が小さい**   | 間違っていたときの被害が小さい | 開発ツール、使い捨てスクリプト、実験コード |
| **D. 統計的に網羅できる** | 入力空間をマシンが埋めてくれる | fuzzing、property-based testing            |

- 実務ではこれらを **重ねる**。1 つでも効くが、2 つ重なると一気に楽になる。
- 逆に **4 つとも使えないタスク**が、人間が設計を持つべきタスク（10 章）。

---

## 5. 源泉 A：出力が有限 — 「生成スクリプトを書かせる」

### 5.1 基本形

コード自動生成を行うスクリプトをコーディングエージェントに実装させるのは、非常に良いユースケースだった。

- 有限のコードを変換・生成するだけでよい場合、**結果コードだけ確認すれば十分**。
- **生成スクリプトの実装内容は理解できていなくても全く問題ない。** レビュー対象はスクリプトではなく出力。
- ここが本質的な非対称性：スクリプトは 500 行の込み入った AST 処理でも、出力は「読めば正しさが分かる型定義 300 行」だったりする。

### 5.2 運用上のキモ：生成物をコミットする

- **生成物をリポジトリにコミットして、diff をレビュー対象にする。**
- これをやると、スキーマが更新されて再生成したときも、**レビュー対象が「差分」に縮む**。生成物が gitignore されていると、毎回全量を読み直す羽目になる（＝非対称性が 1 回きりで消える）。
- 同時に、**生成スクリプトを決定的にする**（実行のたびに順序が変わらない、タイムスタンプを埋め込まない）。非決定的だと diff がノイズだらけになり、レビューが機能しなくなる。
- CI で「再生成して差分が出たら落とす」チェックを入れると、生成物と生成器の乖離が防げる。

### 5.3 事例 1：OpenSCENARIO XML スキーマ → TypeScript 型定義 / バリデータ

- 対象：[ASAM OpenSCENARIO XML v1.3.1 のスキーマ](https://publications.pages.asam.net/standards/ASAM_OpenSCENARIO/ASAM_OpenSCENARIO_XML/v1.3.1/generated/RenderedXsdOutput.html)。
- **もともとは手作業**で XML のモデル定義を TypeScript の型定義に翻訳していた。XSD は読み方がやや複雑で、**人間がやるとミスが出る**。
- 生成スクリプト化すると：
    - 出力は有限（型定義ファイル一式）。**読めば終わる**。
    - しかも次項の理由で、**人間の手作業より誤りを見つけやすい**。

### 5.4 なぜ生成のほうが安全なのか：系統誤差 vs ランダム誤差

これはこのトークで一番言いたいことの 1 つ。

- **人間の手作業**の誤りは **ランダムに散る**。300 箇所のうちどこか 3 箇所が間違っている。→ **全数チェックしないと見つからない**。
- **生成スクリプト**の誤りは **系統的**。ロジックの誤りは同じパターン全部に等しく現れる。→ **1 箇所見つければ全部直る**し、サンプリングで見つかる。
- 「同じ誤りが 100 箇所」は「100 種類の誤りが 100 箇所」よりはるかに安い。**誤りの分布が変わることそれ自体が価値**。
- つまり生成スクリプト化は、単に速いだけでなく **レビューの効率を構造的に上げている**。

### 5.5 事例 2：Web バックエンドの API 定義（swagger / OpenAPI yaml）→ TypeScript バリデーションコード

- 既製の generator が多数ある領域だが、**自前の型規約・バリデータ規約に合わせたい**ときに自作生成器が効く。
- 検証手段が豊富なのが強み（源泉 B と重ねられる）：
    - 生成した型で既存の呼び出し側コードが `tsc` を通るか。
    - 実際のレスポンス JSON を生成バリデータに流して通るか。
    - 既存の統合テストが緑のままか。

### 5.6 事例 3：ESLint ルールを実装させる

- これは「有限の出力だけ確認すればよい」ユースケースではない（任意の入力コードに対して動く）。
- 効いているのは **源泉 C（爆発半径）**：実装されたもの自体は **開発ツールであり、本番環境で直接動くコードではない**という気楽さ。
    - 誤検知が出ても、壊れるのは CI であって顧客ではない。
    - しかも lint ルールは **ルールごとにテストが書きやすい**（源泉 D にも寄せられる）。
- 詳細は姉妹資料（`llm-eslint-harness-slides`）。

### 5.7 このパターンが崩れる例外

- **任意の入力コードに対する変換を行うツールとして公開する場合。** 入力空間が有限でなくなるので「出力を読めば終わり」が成立しない。→ 源泉 D（テスト網羅）に切り替える必要がある。
- **生成結果のコード行数が膨大でレビューが困難な場合。** 生成ロジック側をレビューしたほうがマシなことがある。目安として、出力が数千行を超えたら「全量目視」は建前になる。
    - この場合の対処は、全量目視を諦めて **検証器（源泉 B）を用意する**こと。出力の抜き取りレビュー + 機械検証、の組み合わせに移行する。
- **生成スクリプト自体が長期保守対象になった場合。** 一度きりの移行なら使い捨てでよいが、スキーマが四半期ごとに更新されるなら、スクリプトは実質プロダクションコード。理解していないままにはしておけない。

## 6. 源泉 B：独立した検証器を持つ

「正しさを人間が読んで判断する」のをやめて、**機械が判定できる形に落とす**。

- **型検査**：strict TypeScript、`noUncheckedIndexedAccess`、readonly 徹底。
- **スキーマ検証**：生成した型/バリデータに、実データを流して通す。
- **参照実装との差分（differential testing）**：既存実装と新実装に同じ入力を流して出力を比較する。移行系タスクで極めて強い。
- **往復変換（round-trip）**：`parse(print(x)) === x`、`decode(encode(x)) === x`。codemod・シリアライザ・フォーマッタ系で使える。
- **メタモルフィックテスト**：正解が分からなくても「入力をこう変えたら出力はこう変わるはず」という関係だけは分かる場合に使う。オラクル問題の回避策。

**設計上の注意：検証器は生成物と独立に用意する。**

- 同じセッションで、同じモデルに、実装とテストを同時に書かせると、**実装の勘違いがテストにもコピーされる**。テストが緑になっても意味が薄い。
- 対策：仕様（スキーマ、要件文）から **別々の文脈で** 実装と検証器を作らせる。あるいは検証器は人間が書く／既存のものを使う。
- 一番強いのは、**もともと存在する外部の検証器**（`tsc`、既存の統合テスト、参照実装、実データ）。これは定義上 AI と独立。

---

## 7. 源泉 C：爆発半径を小さくする

「間違っていたときにどれだけ困るか」でレビューの深さを決める。**一律のレビュー深度をやめる。**

| 爆発半径               | 例                                             | レビュー方針                       |
| ---------------------- | ---------------------------------------------- | ---------------------------------- |
| 小（壊れても自分だけ） | 使い捨てスクリプト、実験コード、ローカル解析   | ほぼ見ない。動けばよい             |
| 中（壊れると CI/開発） | lint ルール、codemod、ビルドツール、社内ツール | 挙動だけ確認。実装は流し読み       |
| 大（壊れると顧客）     | 本番ロジック、課金、認証、データ破壊操作       | 通常のレビュー。もしくは人間が書く |

- **プロダクションで直接動かないコードを書かせる**、というのは有力な回避策。スクリプト、実験コード、開発ツール、分析用コード。
- 可逆性も同じ軸：**消せるか / ロールバックできるか / feature flag で切れるか**。消せるコードのレビューは軽くてよい。
- 注意：「生成コードだから本番で動かない」は誤り。**5.3 / 5.5 の生成物は本番で動く。** そこで効いているのは源泉 C ではなく A と B。**源泉を取り違えると安全側の判断を誤る。**

## 8. 源泉 D：統計的に網羅する

入力空間が有限でないなら、**人間が全部読む代わりに、マシンに入力を作らせる**。

- **fuzzing（ファジング）**：[Chromium の libFuzzer 運用](https://chromium.googlesource.com/chromium/src/+/main/testing/libfuzzer/README.md)、OSS-Fuzz。
    - 強いのは **オラクルが無料** な点：クラッシュ・ハング・UB・assertion 失敗は「明らかに間違い」なので、期待値を書かなくてよい。
    - 逆に言うと、**「クラッシュしないが答えが違う」は見つからない**。パーサ、デコーダ、サニタイザ向き。
- **property-based testing（fast-check など）**：人間が書くのは **不変量** だけ、入力はマシンが作る。
    - 例：`sort` の結果は昇順かつ元の multiset と等しい / `Readonly` 化 codemod は AST の意味を変えない / バリデータは自身が生成した値を必ず受理する。
    - **人間のレビュー対象が「実装」から「性質」に縮む**のがポイント。性質は数行で書けて、しかも仕様そのもの。
- **differential / metamorphic testing**：7 章の再掲だが、入力をランダム生成と組み合わせると威力が上がる。
- コスト：**オラクル（あるいは不変量）を書けない領域には使えない。** 「この UI が使いやすいか」には効かない。

## 9. まとめ表：どのタスクにどの源泉が効くか

| タスク                      | A 有限出力 | B 検証器 | C 爆発半径 | D 統計網羅 | 総評             |
| --------------------------- | ---------- | -------- | ---------- | ---------- | ---------------- |
| スキーマ → 型定義の生成     | ◎          | ◎        | △          | ○          | AI 駆動 100% 可  |
| OpenAPI → バリデータ生成    | ◎          | ◎        | △          | ○          | AI 駆動 100% 可  |
| ESLint ルール実装           | ×          | ○        | ◎          | ◎          | AI 駆動 100% 可  |
| 一度きりの移行 codemod      | ◎          | ○        | ○          | ○          | AI 駆動しやすい  |
| 公開する汎用 codemod ツール | ×          | △        | △          | ◎          | テスト網羅が必須 |
| 分析・実験スクリプト        | ○          | ×        | ◎          | ×          | ほぼ見なくてよい |
| 本番のビジネスロジック      | ×          | △        | ×          | △          | 人間が設計を持つ |
| 認証・課金・データ削除      | ×          | △        | ×          | △          | 通常レビュー必須 |

## 10. 非対称性が作れないタスク（正直な話）

4 つの源泉がどれも使えない領域は確実にある。

- **ビジネスロジック**：正しさの基準が外の世界（仕様、顧客の期待）にあり、コードの中に閉じない。
- **UX / 表示**：不変量が書けない。人間が見るしかない。
- **性能**：測れはするが、「なぜ速いか」の理解が要る。
- **セキュリティ境界**：失敗が非可逆で、爆発半径を小さくできない。

ここでの方針は「AI に書かせない」ではなく、**AI に書かせる前に、人間が受け入れ条件を決める**。

## 11. 仕様駆動＝受け入れ条件を先に機械可読にする

メモにあった「仕様駆動開発？」「書かれたコードの正当性を保証する外側の仕組みを厳重にする」への回答。

- **順序を変えるだけで非対称性が作れる。** 実装 → レビュー、ではなく、**受け入れ条件 → 実装 → 条件が満たされたかの確認**。
- 受け入れ条件を機械可読にする手段（強い順）：
    1. **型**：表現できるものは型で表現する。`tsc` が通ることが仕様の証明になる。
    2. **スキーマ / 境界バリデーション**：外部入力は境界で検証する（`ts-fortress` 等）。型では守れない実行時の境界を守る。
    3. **不変量（property）**：8 章。性質を数行で書けば、実装を読まずに済む。
    4. **テストケース**：具体例。AI に大量生成させられるが、**期待値は人間が決める**か、独立に得る。
    5. **lint ルール**：型で表せない組織固有の規約。姉妹資料の主題。
- **自然言語の規約（CLAUDE.md / AGENTS.md）は揮発する。** 量が増えるほど追従精度が落ち、しかも守ったかを機械検証できない。機械可読に落とせるものは落とす。
- ビジネスロジックの静的検証について（メモの問い）：**汎用の銀の弾丸はない**が、実務的に効くのは以下。
    - **状態機械として書いて、遷移表を網羅テストする**（取りうる状態が有限なら A と D の両方が使える）。
    - **不正な状態を型で表現不能にする**（union 型 + 網羅性チェック）。「バリデーションする」より「不正な状態を作れなくする」。
    - **Design by Contract 的な事前/事後条件を assert として埋める**。fuzzing のオラクルになる。
    - 形式手法（TLA+ 等）は、対象が絞れていれば選択肢だが、コストは高い。

## 12. 運用チェックリスト：タスクを AI に渡す前に問うこと

1. **このタスクは非対称にできるか？** 4 つの源泉のどれが使えるか。
2. **非対称な形に変換できないか？**
    - 繰り返し作業 → **生成スクリプト**に変換できないか。
    - 手で直す修正 → **codemod** に変換できないか。
    - 「レビューで毎回言うこと」 → **lint ルール**に変換できないか。
3. **生成物はコミットするか？** diff をレビュー対象にできているか。
4. **検証器は AI と独立か？** 実装とテストを同じ文脈で書かせていないか。
5. **爆発半径はどこか？** それに見合ったレビュー深度になっているか。
6. **理解していないコードの割合は許容範囲か？** 「明日これを消せるか / 直せるか」を自問する。

## 13. まとめ

1. **AI で速くなったのは実装だけ。律速はレビューへ移った。** 実装をさらに速くしても効かない。
2. **レビューを頑張る方向には勝ち筋がない。** タスクの形を変える。
3. **鍵は実装とレビューの非対称性**。そしてそれは設計できる：**有限の出力 / 独立した検証器 / 小さい爆発半径 / 統計的網羅**。
4. **生成スクリプト化は、速さだけでなく誤りの分布を変える。** ランダム誤差が系統誤差になり、レビューが構造的に効くようになる。
5. **どうしても非対称にできない領域では、受け入れ条件を先に機械可読な形で決める。**
6. → **「AI にどう書かせるか」より前に、「このタスクをどうすればレビューが安くなるか」を問う。**

## 14. 議論したい未解決の問い（勉強会用）

- 生成スクリプト自体の負債化：一度きりのつもりが定常運用になったとき、誰も読んでいないスクリプトをどうするか。
- 「理解していないコード」の総量に、チームとして上限を設けるべきか。設けるとしたら何で測るか。
- AI レビュアーの独立性はどう担保するか。別モデル？ 別文脈？ それで十分か？
- 非対称性を作るためのコスト（検証器の整備）を、いつ払うべきか。プロジェクトのどの段階か。

## 付録 B：元メモに対するコメント（壁打ち用）

元メモの主張はおおむねそのまま使えるが、資料化にあたり以下を足した／直した。

1. **「レビューしなくてよいコード」という言い方は少し危ない。**
   実際には「**レビューの対象を、実装から出力・性質・差分に付け替える**」であって、レビューが消えるわけではない。付け替え先を明示しないと、単に見ていないだけの状態と区別がつかない。→ 3〜4 章の「非対称性」という言い方に変えた。
2. **「本番で動かないコードだから気楽」と「出力が有限だから気楽」は別の理由。**
   メモではやや混ざっていた。OpenSCENARIO の型定義も OpenAPI のバリデータも **本番で動く**。効いているのは爆発半径ではなく「出力が有限」＋「独立した検証器がある」。ESLint ルールだけが爆発半径の話。→ 4 つの源泉に分けて整理した（5〜8 章）。
3. **生成物をコミットする / 生成を決定的にする、という運用条件を足した（5.2）。**
   これがないと非対称性は初回のみで消える。再生成のたびに全量レビューが復活してしまう。
4. **「人間の手作業よりミスが少ない」の理由を系統誤差／ランダム誤差の言葉で言語化した（5.4）。**
   メモの「読み方が複雑でミスも生じていた」の裏返しで、ここがこのトークで一番オリジナリティのある主張になりそう。
5. **fuzzing は万能ではない点を明記した（8 章）。**
   fuzzing が安いのは「クラッシュ＝明らかに間違い」という **オラクルが無料** だから。「答えが違うが落ちない」バグは見つからない。仕様の正しさを問う場面では property-based testing / differential testing のほうが直接効く。
6. **AI に検証させるときの独立性の問題を足した（2 章末 / 6 章末）。**
   実装とテストを同じセッションで書かせると誤りが相関する。これはメモになかったが、実務では踏みやすい落とし穴。
7. **METR の数字は扱いに注意。**
   19% 遅い / 本人の体感は 20% 速い、は 2025 年初頭のツールでの結果で、METR 自身が historical と注記している。**「体感は当てにならない」という定性的な主張の補強**としてのみ使い、「AI は遅い」の根拠には使わない。発表前にリンク先を再確認しておくとよい。
8. **「1 年前の AI ではできなかった」系の記述**は、現行モデルで再検証していない以上、スライドでは必ず「当時」と明示する（姉妹資料と同じ扱い）。
9. **社外秘の固有名詞は入れていない。** 事例は公開スキーマ（OpenSCENARIO）と一般名詞（swagger / OpenAPI）のみで書いた。
