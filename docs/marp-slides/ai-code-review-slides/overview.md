# コードではなく、コードを生成するコードを書かせる

> スライド本編（Marp / `slides.md`）に入る前の骨子・素材まとめ。各セクションがスライド 1〜2 枚に相当する想定。
> 対象オーディエンス：LLM 勉強会の参加者（日常的にコーディングエージェントを使っている前提）。
> 姉妹資料：`docs/marp-slides/llm-eslint-harness-slides/`（規律を lint に焼き込む話）。
> 姉妹資料：`docs/marp-slides/test-oracle-slides/`（テストのオラクルをどこから調達するか）。本資料の源泉 D を分離したもの。

## 0. このトークの主張（最初に結論）

1. **コードの変換そのものを AI にやらせるとうまくいかない。変換ツールの実装を AI にやらせるとうまくいく。** これが紹介したい成功体験で、このトークの中心。
2. **レビュー対象がスクリプトから出力に移り、スクリプトは読まなくてよくなる。** 1000 行の AST 処理を理解する必要はない。
3. **一番効いているのは、誤りの分布がランダム誤差から系統誤差に変わること。** 1 箇所直せば全部直り、抜き取りで見つかり、残りを見積もれる。
4. **決定的なツールにすると「ゆらぎ」と「怠惰」が消える。** 生成物をコミットすればレビューは差分に縮む。
5. 以上の要因を並べ直すと、**実装コストとレビューコストの非対称性**の話になり、その源泉は 4 つに整理できる：**有限の出力 / 独立した検証器 / 小さい爆発半径 / 統計的網羅**。ただしこれは 1 つの成功体験を一般化したもので、**網羅性は主張しない**（4.2）。
6. **崩れるのは、出力が読み切れなくなったとき。** そこは検証器かテスト網羅に切り替える（5 章）。

## 1. 問題：AI で速くなったのは実装だけ

### 1.1 実感していること

- アイデアを一瞬で実装してくれるのは便利。しかし **レビューの頻度と量が跳ね上がった**。
- 自分の手で書いたコードほどには深く理解しきれていないコード断片が、ソースコードにどんどん蓄積されていく。
- **AI の書いたコードのレビューに、自分で実装するのと同じだけ時間を掛けてしまっては意味がない。**

### 1.2 律速はレビューへ移った

**1 人日で実装する規模のタスク**を例に（数字は説明用の仮のもの）：

| 工程         | AI 導入前  | AI 導入後  |
| ------------ | ---------- | ---------- |
| 実装         | 480 分     | 30 分      |
| 自己レビュー | 30 分      | 90 分      |
| 他者レビュー | 60 分      | 90 分      |
| **合計**     | **570 分** | **210 分** |

- 実装は **16 倍速**。しかし全体では約 **2.7 倍**にしかならない。
- 実装時間が **0 になっても、上限は 3.2 倍**。アムダールの法則そのもの。
- **時間の内訳が反転する。** レビューの占める割合は **16% → 86%**。
- **自分で書いていないコードは自己レビューが重い。** しかも実際は、レビュー **対象の本数** も増える。

### 1.3 「レビューを頑張る」が解にならない理由

- **レビューの検出率は、掛けた時間に比例しない。** diff が大きくなるほど 1 行あたりの注意力は落ちる。読み飛ばしは線形には増えない。
- **理解していないコードのレビューは、書くより難しいことがある。** 書くときは自分の意図が既にあるが、読むときは意図を復元するところから始まる。
- **AI に AI のコードをレビューさせる**のは有効だが万能ではない。生成器と検証器が同じモデル・同じ文脈だと **誤りが相関する**（同じ勘違いを両方がする）。独立性が担保できていない検証は、通ったことの意味が薄い。→ 3.5 で戻ってくる。
- 「理解していないコードは merge しない」を貫くと、AI の速度をほとんど捨てることになる。

→ **レビューの努力量を増やす方向には勝ち筋が薄い。タスクの形を変える。**

## 2. やったこと：コードを生成するコードを書かせる

### 2.1 何を AI に渡し、何をレビューしたか

最初に考えるのは「この変換を AI にやらせよう」だが、実際にやったのは「この変換を **やるツール** を AI に書かせよう」だった。

|              | 変換そのものを AI に | 変換ツールを AI に       |
| :----------- | :------------------- | :----------------------- |
| AI の成果物  | 出力そのもの         | ツール                   |
| レビュー対象 | 毎回、出力の全量     | 出力（2 回目以降は差分） |
| ツールの中身 | —                    | **読まない**             |

- 有限のコードを変換・生成するだけでよい場合、**結果コードだけ確認すれば十分**だった。
- **生成スクリプトの実装内容は理解できていなくても全く問題ない。** レビュー対象はスクリプトではなく出力。
- 以下、同じ形でうまく行った事例 3 つ。2 つは自分の経験、1 つは外部事例。

### 2.2 事例 1：OpenSCENARIO XML スキーマ → TypeScript 型定義 / バリデータ

- 対象：[ASAM OpenSCENARIO XML v1.3.1 のスキーマ](https://publications.pages.asam.net/standards/ASAM_OpenSCENARIO/ASAM_OpenSCENARIO_XML/v1.3.1/generated/RenderedXsdOutput.html)。
- **もともとは手作業**で XML のモデル定義を TypeScript の型定義に翻訳していた。XSD は読み方がやや複雑で、**人間がやるとミスが出る**。
- AI に書かせたのは **その翻訳を行うスクリプト**。出てきたのは型定義ファイル一式。
- 自分が読んだのは **型定義のほうだけ**。スクリプトの AST 処理は読んでいない。
- 手作業を AI に代行させたのではなく、**手作業を機械化するコードを AI に書かせた**。差はこの一点。

### 2.3 事例 2：Web バックエンドの API 定義（swagger / OpenAPI yaml）→ TypeScript バリデーションコード

- 既製の generator が多数ある領域だが、**自前の型規約・バリデータ規約に合わせたい**ときに自作生成器が効く。
- ここでも AI に渡したのは「yaml を読んでバリデータを吐くスクリプト」。レビューしたのは生成されたバリデータと、それが通す / 弾く実データ。
- 「スキーマ → コード」は、**入力が既に機械可読な仕様である**という点で特にやりやすい。仕様の解釈を人間がやり直す必要がない。

### 2.4 外部事例：勘定系システムの COBOL → Java 移行（北國銀行）

同じ発想が、桁違いの規模でも報告されている。

- 600 万ステップの COBOL アプリケーションを 4 カ月で Java に書き換えた事例（2027 年 1 月稼働予定の次期勘定系システム）。
- **当初は「変換そのもの」に LLM を使い、失敗している。** PoC を何度やっても期待するコードが出てこなかった。原因として挙げられているのが 2 つ：
    - **怠惰**：生成 AI が勝手に一部を省略してしまう。
    - **ゆらぎ**：1 回目と 2 回目で変換結果が異なる。
- 突破口は発想の転換だった。**変換作業に AI を使うのをやめ、「COBOL を入力すると Java を出力する変換ツール」の開発に AI を使った。** 約 2 カ月でツールの大枠が完成し、最終的に全体の 87% のアプリケーションで変換率 97% に到達。残りは手作業で補った。
- 規模も分野もまったく違うのに、**同じ転回で解けている**。しかも失敗の理由として挙がった「怠惰」と「ゆらぎ」が、次章の要因分析にそのまま対応する。

## 3. なぜうまく行ったのか：要因分析

### 3.1 要因① レビュー対象が「スクリプト」から「出力」へ移った

- スクリプトは 1000 行の込み入った AST 処理でも、出力は「読めば正しさが分かる型定義 300 行」だったりする。
- **レビューすべきは後者だけ。** 前者を理解する必要がない。
- なぜ理解しなくてよいかというと、**出力が有限で、全量を目視できるから**。
- したがってこの要因が効く条件は「**出力が読み切れる量であること**」。出力が数千行を超えたらこの要因は消える（5.1 で戻ってくる）。

### 3.2 要因② 誤りがランダム誤差から系統誤差に変わった

これはこのトークで一番言いたいこと。

- **人間の手作業**の誤りは **ランダムに散る**。300 箇所のうちどこか 3 箇所が間違っている。→ **全数チェックしないと見つからない**。
- **生成スクリプト**の誤りは **系統的**。ロジックの誤りは同じパターン全部に等しく現れる。→ **1 箇所見つければ全部直る**し、サンプリングで見つかる。
- 「同じ誤りが 100 箇所」は「100 種類の誤りが 100 箇所」よりはるかに安い。**誤りの分布が変わることそれ自体が価値**。
- つまりツール化は、単に速いだけでなく **レビューの効率を構造的に上げている**。
- 2.4 で「変換率 97%」という数字が出せているのも同じ理由。**残りを見積もれる。** LLM に直接書かせていたら、誤りは 600 万ステップ全体にランダムに散る。

### 3.3 要因③ 決定的にすると「ゆらぎ」と「怠惰」が消える

- **ツールは決定的。** 同じ入力なら同じ出力になる。→ 2.4 の **ゆらぎ** が消え、diff がレビュー可能になる。
- **ツールは入力を全部処理するか、できなければ落ちる。** → **怠惰**（黙って省略）が原理的に起きない。
- そのうえで運用上のキモが 2 つある。
    - **生成物をリポジトリにコミットして、diff をレビュー対象にする。** スキーマが更新されて再生成したときも、**レビュー対象が「差分」に縮む**。生成物が gitignore されていると、毎回全量を読み直す羽目になる（＝要因①が 1 回きりで消える）。
    - **CI で「再生成して差分が出たら落とす」チェックを入れる。** 生成物と生成器の乖離が防げる。
- 同時に、**生成スクリプト自体を決定的に書く**（実行のたびに順序が変わらない、タイムスタンプを埋め込まない）。非決定的だと diff がノイズだらけになり、レビューが機能しなくなる。
- **生成物をコミットしていない生成器は、レビューを一度先送りしただけ。**

### 3.4 要因④ 検証器が外から手に入った

自分で正しさを判定しなくてよかった。既にあるものが判定してくれた。

- **型検査**：生成した型で既存の呼び出し側コードが `tsc` を通るか。strict TypeScript、`noUncheckedIndexedAccess`、readonly 徹底。
- **実データ**：実際の `.xosc` / レスポンス JSON を生成バリデータに流して通るか。
- **既存の統合テスト**が緑のままか。
- 他に強いもの：
    - **参照実装との差分（differential testing）**：既存実装と新実装に同じ入力を流して出力を比較する。移行系タスクで極めて強い。2.4 の COBOL → Java はまさに「旧実装という参照実装が手元にある」状況。
    - **往復変換（round-trip）**：`parse(print(x)) === x`、`decode(encode(x)) === x`。codemod・シリアライザ・フォーマッタ系で使える。
    - **メタモルフィックテスト**：正解が分からなくても「入力をこう変えたら出力はこう変わるはず」という関係だけは分かる場合に使う。オラクル問題の回避策。

### 3.5 要因④の落とし穴：検証器は生成物と独立に用意する

- 同じセッションで、同じモデルに、実装とテストを同時に書かせると、**実装の勘違いがテストにもコピーされる**。テストが緑になっても意味が薄い。
- 対策：仕様（スキーマ、要件文）から **別々の文脈で** 実装と検証器を作らせる。あるいは検証器は人間が書く／既存のものを使う。
- 一番強いのは、**もともと存在する外部の検証器**（`tsc`、既存の統合テスト、参照実装、実データ）。これは定義上 AI と独立。
- **「テストが通りました」の価値は、そのテストが誰と独立に書かれたかで決まる。**

### 3.6 要因⑤ 間違っても被害が小さいものもある

ここまでの 3 事例とは **別の要因** で成立しているケースもある。「間違っていたときにどれだけ困るか」でレビューの深さを決める、という話。**一律のレビュー深度をやめる。**

| 壊れたときの範囲       | 例                                             | レビュー方針                       |
| ---------------------- | ---------------------------------------------- | ---------------------------------- |
| 小（壊れても自分だけ） | 使い捨てスクリプト、実験コード、ローカル解析   | ほぼ見ない。動けばよい             |
| 中（壊れると CI/開発） | lint ルール、codemod、ビルドツール、社内ツール | 挙動だけ確認。実装は流し読み       |
| 大（壊れると顧客）     | 本番ロジック、課金、認証、データ破壊操作       | 通常のレビュー。もしくは人間が書く |

- **ESLint ルールを AI に実装させる**のがこの型。任意の入力コードに対して動くので「出力を読めば終わり」（要因①）は成立しないが、実装されたもの自体は **開発ツールであり、本番環境で直接動くコードではない**。誤検知が出ても、壊れるのは CI であって顧客ではない。
- しかも lint ルールは **ルールごとにテストが書きやすい**。
- 経験上、**AST ベースの局所的な一対一変換ならほぼ一発で期待通りに動く**。
- 可逆性も同じ軸：**消せるか / ロールバックできるか / feature flag で切れるか**。消せるコードのレビューは軽くてよい。
- **プロダクションで直接動かないコードを書かせる**、というのは有力な回避策。スクリプト、実験コード、開発ツール、分析用コード。
- 詳細は姉妹資料（`llm-eslint-harness-slides`）。

### 3.7 要因を取り違えない

- 注意：**「AI に書かせたのは生成スクリプトだから、本番では動かない。だから気楽」は誤り。**
- 生成スクリプト自体は確かに本番では動かない。**しかし、その出力は本番で動く。** 2.2 の型定義も 2.3 のバリデータも、そのまま製品のコードになる。
- そこで効いているのは要因⑤（被害の小ささ）ではなく、**要因①（有限の出力）＋ 要因④（外部の検証器）**。
- **ESLint ルールだけが被害の小ささの話。** あれは出力が製品に入らない。
- **なぜこのタスクが安全なのかを、要因の言葉で言えるようにしておく。** 言えないなら、それはたぶん安全ではない。要因を取り違えると安全側の判断を誤る。

## 4. 一般化：実装とレビューの非対称性

### 4.1 見ていたのは「検証コスト ≪ 実装コスト」だった

- 3 章の要因はすべて、**「作るのは大変だが、正しさの確認は安い」** に寄せる工夫だった。
- 比喩としては NP の構造：**解を作るのは大変だが、解が正しいことの確認は安い**。数独、因数分解、経路探索。
- **AI コーディングは、実装とレビューに非対称性があるタスクで特に有効。** 逆に言えば、非対称性がないタスクに AI を投入しても、しんどさが実装からレビューへ移動するだけ。
- 重要なのは、**この非対称性は与えられるものではなく、設計できるもの**だという点。3 章でやっていたのは、まさにその設計。

### 4.2 要因を並べ直すと、4 つの源泉になる

**軸は「正しさを誰が保証するか」。**

| 3 章の要因                      | 一般化すると              | 正しさを誰が保証するか                          | 典型例                                     |
| ------------------------------- | ------------------------- | ----------------------------------------------- | ------------------------------------------ |
| ① 出力が読み切れた              | **A. 出力が有限**         | **人間が全部読む** — 読み切れる量だから可能     | コード生成スクリプト、スキーマ翻訳         |
| ④ `tsc` / 実データ / 統合テスト | **B. 独立した検証器**     | **機械が判定する** — 与えた入力に対して         | 型検査、スキーマ検証、参照実装との差分     |
| ⑤ 壊れても CI だけ              | **C. 爆発半径が小さい**   | **誰も保証しない** — 間違っても困らないから     | 開発ツール、使い捨てスクリプト、実験コード |
| （今回の経験には無い）          | **D. 統計的に網羅できる** | **機械が入力も作って判定する** — 入力が無限でも | fuzzing、property-based testing            |

- **A → B → D は「検証の担い手を人間から機械へ移す」一本の軸。** 出力が読み切れるうちは人間が読み、読み切れなくなったら機械に判定させ、入力空間まで無限なら入力も機械に作らせる。
- **C だけが直交している。** 検証の話ではなく賭け金の話で、「そもそも保証しなくてよい」という逃げ道。
- **要因②③は源泉ではない。** ② 系統誤差は A を選んだことの副産物（ただし実務的には一番効く）、③ 決定性と生成物のコミットは、A を初回だけで終わらせないための運用条件。
- **D だけが今回の経験から出ていない。** 出力や入力空間が有限でなくなったときに必要になる源泉で、fuzzing / property-based / differential / metamorphic。詳細は姉妹資料 [`test-oracle-slides/overview.md`](../test-oracle-slides/overview.md) に分離した。
- **網羅性は主張しない。** 1 つの成功体験から、いま見えているのが 4 つ。5 つ目があるかもしれないし、4 つは独立でもない（5.1：出力が膨大になったら A から B に切り替える）。
- 実務ではこれらを**重ねる**。1 つでも効くが、2 つ重なると一気に楽になる。逆に **4 つとも使えないタスク**が、人間が設計を持つべきタスク（5.2）。

### 4.3 まとめ表：どのタスクにどの源泉が効くか

| タスク                      | A 有限出力 | B 検証器 | C 爆発半径 | D 統計網羅 | 総評             |
| --------------------------- | ---------- | -------- | ---------- | ---------- | ---------------- |
| スキーマ → 型定義の生成     | ◎          | ◎        | △          | ○          | AI 駆動 100% 可  |
| OpenAPI → バリデータ生成    | ◎          | ◎        | △          | ○          | AI 駆動 100% 可  |
| ESLint ルール実装           | ×          | ○        | ◎          | ◎          | AI 駆動 100% 可  |
| 一度きりの移行 codemod      | ◎          | ○        | ○          | ○          | AI 駆動しやすい  |
| 公開する汎用 codemod ツール | ×          | △        | △          | ◎          | テスト網羅が必須 |
| 分析・実験スクリプト        | ○          | ×        | ◎          | ×          | ほぼ見なくてよい |
| 本番のビジネスロジック      | ×          | △        | ×          | △          | 人間が設計を持つ |
| 認証・課金・データ削除      | ×          | △        | ×          | △          | 通常レビュー必須 |

## 5. どこで崩れるか

### 5.1 この型が崩れる例外

- **任意の入力コードに対する変換を行うツールとして公開する場合。** 入力空間が有限でなくなるので「出力を読めば終わり」が成立しない。→ 源泉 D（テスト網羅）に切り替える必要がある。
- **生成結果のコード行数が膨大でレビューが困難な場合。** 生成ロジック側をレビューしたほうがマシなことがありうる。目安として、出力が数千行を超えたら「全量目視」は建前になる。
    - この場合の対処は、全量目視を諦めて **検証器（源泉 B）を用意する**こと。出力の抜き取りレビュー + 機械検証、の組み合わせに移行する。
- どちらも **要因①（出力が読み切れる）が失われる**ケース。3 章の要因を名指しできていれば、崩れたことに気づける。

### 5.2 4 つの源泉がどれも使えない領域（正直な話）

- **ビジネスロジック**：正しさの基準が外の世界（仕様、顧客の期待）にあり、コードの中に閉じない。
- **UX / 表示**：不変量が書けない。人間が見るしかない。
- **性能**：測れはするが、「なぜ速いか」の理解が要る。
- **セキュリティ境界**：失敗が非可逆で、爆発半径を小さくできない。

ここでの方針は「AI に書かせない」ではなく、**AI に書かせる前に、人間が受け入れ条件を機械可読な形で決める**。手段と順序は付録 B.2 に置いた。

---

## 6. まとめ

1. **コードの変換そのものではなく、変換ツールの実装を AI にやらせる。** レビュー対象がスクリプトから出力に移り、スクリプトは読まなくてよくなる。
2. **決定的なツールにすると「ゆらぎ」と「怠惰」が消える。** 生成物をコミットすればレビューは差分に縮む。していなければ、レビューを先送りしただけ。
3. **一番効くのは、誤りがランダム誤差から系統誤差に変わること。** 1 箇所直せば全部直り、抜き取りで見つかり、残りを見積もれる。
4. **要因を並べ直すと、実装とレビューの非対称性の 4 つの源泉になる。** 有限の出力 / 独立した検証器 / 小さい爆発半径 / 統計的網羅。
5. **崩れるのは、出力が読み切れなくなったとき。** そこは検証器かテスト網羅に切り替える。
6. → **「AI にどう書かせるか」より前に、「このタスクをどうすればレビューが安くなるか」を問う。**

## 付録 B：デッキに載せていない素材

デッキは「成功体験とその要因分析」に絞ったので、以下は資料としてだけ残す。

### B.1 体感と実測はズレる（METR）

**この節の数字は 2026/02 の続報で更新されている。19% だけを引用してはいけない。**

- METR の RCT（2025/07 公開）では、熟練 OSS 開発者が慣れたリポジトリで作業したとき、**AI 利用可の条件のほうが 19% 遅かった**（CI +2% 〜 +39%）。にもかかわらず本人たちは事後に「**20% 速くなった**」と見積もった。被験者 16 名 / 246 タスク、2025 年 2〜6 月、当時のツール（Cursor Pro + Claude 3.5/3.7 Sonnet）。
- **続報（2026/02）で点推定は符号が反転した。** 2025 年 8 月開始の後続実験では、元の被験者 10 名で **−18%**（CI −38% 〜 +9%）、新規 47 名で **−4%**（CI −15% 〜 +9%）。負が速い側。ただし **どちらも信頼区間が 0 をまたぐ**ので「速くなった」と言えてはいない。
- **METR 自身がこの新データを「unreliable signal」と呼んでいる。** 理由が示唆的で、**開発者が「AI なしでは働きたくない」と実験への参加やタスク提出を断るようになった**ため。30〜50% の開発者が「AI なしでやりたくないタスクは提出しなかった」と回答しており、**AI の効きが大きいタスクほど系統的に実験から抜け落ちる**。報酬が $150/hr → $50/hr に下がったことによる選択効果も認めている。結論として推定値は「lower-bound」「a bad proxy」。
- **したがって「AI を使うと遅くなる」の根拠にはもう使えない。** METR の現在の見解はむしろ「2026 年初頭の開発者は早期 2025 より速くなっているだろう（ただしデータは very weak evidence）」。
- **それでも使える一点はある。** 新記事も自己申告について "as we documented in our earlier study those estimates can be quite unreliable" と書いており、**「速くなった感覚は当てにならない」は生きている**。ただし旧記事のような「過大評価する」という**方向の主張はもうできない**。当てにならない、までで止める。
- 副産物として面白い事実：**この種の測定自体が年々難しくなっている。** 「AI なしで働く」という対照条件を人が受け入れなくなったため RCT が成立しにくく、METR は "these effects will only get more dramatic" として実験計画の見直しに入っている。

### B.2 仕様駆動＝受け入れ条件を先に機械可読にする

5.2 の領域でどうするか、という話。

- **順序を変えるだけで非対称性が作れる。** 実装 → レビュー、ではなく、**受け入れ条件 → 実装 → 条件が満たされたかの確認**。
- 受け入れ条件を機械可読にする手段（強い順）：
    1. **型**：表現できるものは型で表現する。`tsc` が通ることが仕様の証明になる。
    2. **スキーマ / 境界バリデーション**：外部入力は境界で検証する（`ts-fortress` 等）。型では守れない実行時の境界を守る。
    3. **不変量（property）**：性質を数行で書けば、実装を読まずに済む。姉妹資料 `test-oracle-slides` の主題。
    4. **テストケース**：具体例。AI に大量生成させられるが、**期待値は人間が決める**か、独立に得る。
    5. **lint ルール**：型で表せない組織固有の規約。姉妹資料 `llm-eslint-harness-slides` の主題。
- **自然言語の規約（CLAUDE.md / AGENTS.md）は揮発する。** 量が増えるほど追従精度が落ち、しかも守ったかを機械検証できない。機械可読に落とせるものは落とす。
- ビジネスロジックの静的検証について：**汎用の銀の弾丸はない**が、実務的に効くのは以下。
    - **状態機械として書いて、遷移表を網羅テストする**（取りうる状態が有限なら A と D の両方が使える）。
    - **不正な状態を型で表現不能にする**（union 型 + 網羅性チェック）。「バリデーションする」より「不正な状態を作れなくする」。
    - **Design by Contract 的な事前/事後条件を assert として埋める**。fuzzing のオラクルになる。
    - 形式手法（TLA+ 等）は、対象が絞れていれば選択肢だが、コストは高い。

### B.3 運用チェックリスト：タスクを AI に渡す前に問うこと

1. **このタスクは非対称にできるか？** 4 つの源泉のどれが使えるか。
2. **非対称な形に変換できないか？**
    - 繰り返し作業 → **生成スクリプト**に変換できないか。
    - 手で直す修正 → **codemod** に変換できないか。
    - 「レビューで毎回言うこと」 → **lint ルール**に変換できないか。
3. **生成物はコミットするか？** diff をレビュー対象にできているか。
4. **検証器は AI と独立か？** 実装とテストを同じ文脈で書かせていないか。
5. **爆発半径はどこか？** それに見合ったレビュー深度になっているか。
6. **理解していないコードの割合は許容範囲か？** 「明日これを消せるか / 直せるか」を自問する。

## 付録 C：構成と元メモに対するコメント（壁打ち用）

1. **主題を「成功体験の紹介」に据え直した（2026-09）。**
   元の構成は「レビューがしんどい → 非対称性を設計する → その源泉は 4 つ → 源泉 A の事例」という演繹の形で、**4 つの源泉が上から降ってきた枠組みのように見えていた**。実際は逆で、出発点は「変換ツールを AI に書かせたらうまく行った」という 1 つの経験であり、4 つの源泉はそこから逆算して出てきたもの。だから **「やったこと（2 章）→ なぜうまく行ったか（3 章）→ 一般化（4 章）」** の順に組み替えた。4 つの源泉は 4.2 で要因の対応表として導出される。
   副作用として良かった点：**D だけが要因分析に対応物を持たない**ことが表の上で可視化された。D は経験から出ていない源泉であり、姉妹資料に分離した判断とも一貫する。
2. **ESLint ルールの事例を「やったこと」から「要因分析」側に移した（3.6）。**
   あれは「コードを生成するコード」ではないし、効いている要因も違う（出力の有限性ではなく被害の小ささ）。成功体験の列に並べると、読者は同じ理由で成功したと誤解する。
3. **「レビューしなくてよいコード」という言い方は少し危ない。**
   実際には「**レビューの対象を、実装から出力・性質・差分に付け替える**」であって、レビューが消えるわけではない。付け替え先を明示しないと、単に見ていないだけの状態と区別がつかない。→ 4 章の「非対称性」という言い方に変えた。
4. **「生成スクリプトは本番で動かないから気楽」と「出力が有限だから気楽」は別の理由。**
   メモではやや混ざっていた。OpenSCENARIO の型定義も OpenAPI のバリデータも **本番で動く**。効いているのは爆発半径ではなく「出力が有限」＋「独立した検証器がある」。ESLint ルールだけが爆発半径の話。→ 3.7 で明示した。
5. **生成物をコミットする / 生成を決定的にする、という運用条件を足した（3.3）。**
   これがないと非対称性は初回のみで消える。再生成のたびに全量レビューが復活してしまう。あわせて、これが 2.4 の「ゆらぎ」「怠惰」への回答になっていることを示した。
6. **「人間の手作業よりミスが少ない」の理由を系統誤差／ランダム誤差の言葉で言語化した（3.2）。**
   メモの「読み方が複雑でミスも生じていた」の裏返しで、ここがこのトークで一番オリジナリティのある主張。
7. **AI に検証させるときの独立性の問題を足した（1.3 / 3.5）。**
   実装とテストを同じセッションで書かせると誤りが相関する。これはメモになかったが、実務では踏みやすい落とし穴。
8. **METR はデッキから外し、付録 B.1 に退避した（2026-09 に再確認）。**
   19% 遅い / 本人の体感は 20% 速い、は 2025 年初頭のツールでの結果で、旧記事には現在 "These results are out of date." のバナーが出ている。2026/02 の続報で点推定は −18% / −4%（負が速い側）に反転したが、いずれも CI が 0 をまたぎ、METR 自身が選択効果を理由に "unreliable signal" と呼んでいる。**「体感は当てにならない」の補強**としてのみ使えるが、成功体験の紹介という主題には外部 RCT の話は要らないので落とした。
9. **fuzzing は万能ではない点は姉妹資料に移した。**
   fuzzing が安いのは「クラッシュ＝明らかに間違い」という **オラクルが無料** だから。「答えが違うが落ちない」バグは見つからない。詳細は `test-oracle-slides`。
10. **「1 年前の AI ではできなかった」系の記述**は、現行モデルで再検証していない以上、スライドでは必ず「当時」と明示する（姉妹資料と同じ扱い）。
11. **社外秘の固有名詞は入れていない。** 事例は公開スキーマ（OpenSCENARIO）と一般名詞（swagger / OpenAPI）、および公開記事（北國銀行）のみで書いた。
