# issue の着手順 — `Start-After:`

issue の本文に、その issue に着手してよくなる条件を書く。pull request の
`Merge-After:` が「いつマージしてよいか」を宣言するのに対し、`Start-After:` は
「いつ着手してよいか」を宣言する。

```md
`no-new-array.mts` は #2113 が書き換えているので、そのマージ後に着手する。

Start-After: #2113
```

読み手は Pull Requests Manager（`apps/pr-manager-app`）の issue 一覧と
`pnpm run pr-report` を予定している。どちらもまだ読んでいないので、今は人が読むための
宣言である。

## 何を書くか

`Start-After:` は次の 2 つを区別せずに表す。

- **前提。** 名指したものが済むまで、この issue は始められない（使う API がまだ無い、
  方針がそちらで決まる、など）。
- **よりよい順序。** 始めることはできるが、名指したものが済んでから始めるほうが
  効率がよい（同じファイルを書き換えている pull request があり、先に始めると衝突を
  解くことになる、など）。

どちらであるかと、その理由は、宣言の上に文章で書く。宣言は機械が読む部分、
理由は人が読む部分で、理由が無いと、条件が古くなったときに外してよいか判断できない。

**名指すのは、待っている当のもの。** 変更そのもの（衝突する差分、それが足す API）を
待つなら pull request を、やり方を問わず課題が片づくことを待つなら issue を名指す。
issue は、それを閉じる pull request がマージされたときに閉じるので、issue を名指せば
pull request の作り直しにも追従する。

## 書式

`Merge-After:` と同じ規則で読む。

- 行頭（前の空白は可）が `Start-After:` で始まる行。大文字・小文字は区別しない。
  本文のどこにあってもよく、何行に分けてもよい。慣例として本文の末尾に置く。
- 参照は同じリポジトリの `#N` だけ。issue と pull request は番号を共有しているので、
  どちらを名指してもよい。`owner/repo#N` と URL は読まない。
- 重複は 1 つとして扱い、順序は意味を持たない。済んでいるべきものの集合として読む。
- コードフェンスの中は読まない。宣言の書き方を説明する issue が、その説明によって
  自分を縛らないようにするため。`> ` で始まる引用行も、行頭がキーではないので読まない。
- 読むのは本文だけで、コメントは読まない。

issue の本文に書いた `Merge-After:` は読まない。書き間違いとして扱う。

## 書かない issue

**進捗 issue は宣言を持たず、名指されもしない。** 進捗 issue とは、互いに独立した
作業をチェックリストで束ね、全体として着手されることのない issue のこと
（例: #2036、#2155、#1753）。

- 部分ごとに前提が違う。全体に 1 つの宣言を付けると、もう始められる部分まで
  待たせることになる。
- 名指すと、名指した側は全項目が済むまで待つことになり、それはたいてい来ない。
  さらに、項目の側が進捗 issue を名指し、進捗 issue の側が項目を待つと、循環になる。

待っているのが進捗 issue の 1 項目なら、その項目の issue か pull request を名指す。
項目が issue になっていなければ、切り出してから名指す。

**着手済みの issue には足さなくてよい。** その issue を閉じる pull request が
開いていれば、着手はもう済んでいる。そこから先の順序は、その pull request の
`Merge-After:` が表す。issue の側に書いても、下の「pull request への引き継ぎ」で
同じ制約になる。

## 状態

名指したものごとに、次のどれかになる。

| 名指したもの                                                       | 状態                            |
| :----------------------------------------------------------------- | :------------------------------ |
| 開いている issue / pull request（draft を含む）                    | 待っている                      |
| マージされた pull request                                          | 済んだ                          |
| 完了（`COMPLETED`）として閉じた issue                              | 済んだ                          |
| マージされずに閉じた pull request                                  | 完了せずに閉じた（`abandoned`） |
| 対応しない（`NOT_PLANNED`）・重複（`DUPLICATE`）として閉じた issue | 完了せずに閉じた（`abandoned`） |
| 存在しない番号、読めないもの                                       | 不明                            |

**完了せずに閉じた**ものは、待っていた作業が行われないまま閉じたもの。
`Merge-After:` は「開いていなければ制約しない」と読むが、着手順でそう読むと、
前提が放棄されたのに着手できると表示してしまう。前提が別の pull request で
やり直されているなら名指し直し、要らなくなったなら宣言から外す。
どちらなのかは機械には分からないので、人に見直しを求める。

issue の着手状態は、次のうち最初に当てはまるもの。

| 着手状態                | 条件                                                           |
| :---------------------- | :------------------------------------------------------------- |
| 循環（`cycle`）         | issue 同士の `Start-After:` が循環している（自分自身を含む）   |
| 待ち（`blocked`）       | 待っているものが 1 つ以上ある                                  |
| 要見直し（`attention`） | 待っているものは無いが、完了せずに閉じたものか不明なものがある |
| 着手可（`ready`）       | 宣言があり、すべて済んだ                                       |
| 制約なし（`free`）      | 宣言が無い                                                     |

- 循環は issue 同士の宣言だけで生じる。pull request は `Start-After:` を持たない。
- 判定に推移は要らない。名指したものが 1 つでも開いていれば待ちであり、
  それがさらに何を待っているかは関係ない。
- 「着手可」と「制約なし」を分けるのは、待っていたものが済んで始められるように
  なった issue を目立たせるため。
- 着手状態とは別に、その issue を閉じる開いた pull request があれば「着手済み」と
  表示する。

## pull request への引き継ぎ

**issue を閉じる pull request は、その issue の `Start-After:` を引き継ぐ。**
着手の前に済ませたかったものは、着手した後も、先にマージされるべきものだから。
前提なら、それが無いとこの変更は動かない。よりよい順序なら、後からマージする側が
衝突を解くほうが、先にマージされた変更を解き直すより手戻りが少ない。

閉じる issue は closing keyword（`Closes #N` など）で決める。読み方は
`pr-report-core` の `closingKeywordIssuesIn` と同じで、stack された pull request も
含む。引き継いだ宣言は、名指したものごとに次のように読む。

- **開いている pull request** — `Merge-After:` で名指したのと同じに扱う。
- **開いている issue** — それを閉じる開いた pull request があれば、それらを
  `Merge-After:` で名指したのと同じに扱う。無ければ制約しない。
  `Merge-After:` は開いた pull request の間の順序であり、まだ誰も始めていない作業を
  待ってマージを止めると、よりよい順序のためだけに止まり続けることがある。
  カードには「#N（issue）が済んでいない」と出す。
- **済んだもの、完了せずに閉じたもの、不明なもの** — 制約しない。
  完了せずに閉じたものと不明なものは、issue の側で見直しを求めている。

**引き継ぎは読む側が行う。** pull request を開いた後に issue の宣言が書き換わっても
追従するため、`pr-report-core` と `unblock-prs` が読むたびに導く。stack と同じく、
`open-pr` は開くときに引き継いだ分を `Merge-After:` として本文にも書き、本文が順序を
述べるようにする。本文に書いたものと引き継いだものが同じなら、1 つとして数える。
引き継いだ順序も `Merge-After:` の循環の検出に入る。

## 実装の予定

- 解析は `apps/pr-report-core` に置き、`Merge-After:` と共有する
  （`merge-after.mts` の `parseMergeAfter` をキー名を引数に取る形にする）。
  共有にあたり、`other/repo#5` の `#5` を同じリポジトリの `#5` と読まないようにする。
  今の `Merge-After:` の解析にはこの誤読がある。
- 循環の検出には `findMergeAfterCycles` を使う。
- 将来は、GitHub の issue の依存関係（GraphQL の `Issue.blockedBy`）も同じ辺として読む。
  GitHub の依存関係は issue 同士しか結べないので、pull request を名指すには
  本文の宣言が要る。
