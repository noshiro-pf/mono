synstate-next はオペレーターを持つ状態ライブラリです。派生値、時間の扱い、リクエストが、1 つのグリッチフリーなグラフのノードになります。このページでは、プロジェクトで比べることになるライブラリと並べ、好みではなく、それぞれが何をいつ計算するかで比べます。

| ライブラリ                                   | 中心となるモデル           | 派生値                              | 組み込みの非同期オペレーター | 派生値のグリッチフリー   | UI フレームワークなしで動くか            | メンテナンス                                                                        |
| -------------------------------------------- | -------------------------- | ----------------------------------- | ---------------------------- | ------------------------ | ---------------------------------------- | ----------------------------------------------------------------------------------- |
| **synstate-next**                            | Observable のグラフ        | あり（オペレーター）                | あり                         | あり（プッシュ、深さ順） | 動く                                     | [活発](https://github.com/noshiro-pf/mono/tree/main/libs/synstate-next)             |
| **RxJS**                                     | Observable（ReactiveX）    | あり（オペレーター）                | あり                         | なし                     | 動く                                     | [活発](https://github.com/ReactiveX/rxjs)（2026-10 時点で 9.0 がベータ）            |
| **MobX**                                     | プロキシによるリアクティブ | あり（`computed`）                  | なし                         | あり（プル、遅延）       | 動く                                     | [活発](https://github.com/mobxjs/mobx)                                              |
| **Jotai**                                    | アトミックな状態           | あり（派生 atom）                   | 部分的                       | あり（プル、遅延）       | 動く（バニラストア）                     | [活発](https://github.com/pmndrs/jotai)                                             |
| **Redux**                                    | Flux、単一ストア           | あり（セレクター）                  | なし（ミドルウェア）         | 該当なし（プル）         | 動く                                     | [活発](https://github.com/reduxjs/redux-toolkit)                                    |
| **Solid**（`solid-js`）                      | Signal（細粒度）           | あり（`createMemo`）                | 部分的（`createResource`）   | あり（プッシュ）         | 動く（`createRoot`。[後述](#ui-の外で)） | [活発](https://github.com/solidjs/solid)                                            |
| **Preact Signals**（`@preact/signals-core`） | Signal                     | あり（`computed`）                  | なし                         | あり（プル、遅延）       | 動く（`-core` パッケージ）               | [活発](https://github.com/preactjs/signals)                                         |
| **Zustand**                                  | Flux 系のストア            | なし（インラインのセレクター）      | なし                         | 該当なし（プル）         | 動く                                     | [活発](https://github.com/pmndrs/zustand)                                           |
| **Valtio**                                   | プロキシによるミュータブル | なし（別ユーティリティの `derive`） | なし                         | 該当なし（プル）         | 動く                                     | [活発](https://github.com/pmndrs/valtio)                                            |
| **Recoil**                                   | アトミックな状態（React）  | あり（セレクター）                  | 部分的                       | あり（プル、遅延）       | 動かない                                 | [開発終了](https://github.com/facebookexperimental/Recoil)（最終リリース：2023-03） |
| **XState**                                   | 有限状態マシン             | コンテキスト経由                    | なし                         | 該当なし                 | 動く                                     | [活発](https://github.com/statelyai/xstate)                                         |
| **TanStack Query**                           | サーバー状態のキャッシュ   | 該当なし                            | あり（fetch）                | 該当なし                 | 動く                                     | [活発](https://github.com/TanStack/query)                                           |

:::note[プッシュとプル]
synstate-next と Solid は**プッシュ**でグリッチフリーです。更新は届いた派生値を、それぞれ 1 回ずつ、読むものすべての後に計算するので、購読者には辻褄の合った値が渡ります。synstate-next は更新が届いたノードを深さ順に訪れます（[更新の伝わり方](/mono/synstate-next/ja/internals/how-an-update-propagates/)）。Solid は書き込みの下流をすべて印付けしてからメモを再実行し、上流がまだ古いメモがあればそちらを先に実行します。

MobX、Jotai、Preact Signals、Recoil は**プル**でグリッチフリーです。派生値は何かが読んだときに計算し直されるので、途中の状態を見ることはありません。どちらの方式でも保証の対象は派生値です。値を書き込む effect として書いた段は、その外にあります（[評価モデル](#評価モデル)）。
:::

## 評価モデル

「グリッチフリー」は読み手が何を見るかを表すだけで、処理がいつ行われるかは表しません。派生グラフを持つライブラリは、それぞれ違う方法で処理を予定します。

| ライブラリ     | 伝わり方                                             | 派生値が計算されるとき                                                                                               | 派生値のグリッチフリー | リクエストの段のグリッチフリー          | すべての書き込みが次の段に届くか                                                                   |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------- |
| synstate-next  | プッシュ、深さ順。購読者は派生値の後                 | ソースが更新されるたび。読まれているかどうかにかかわらない                                                           | あり                   | あり：`switchMap` はグラフのノード      | `source` と emitter から。`createState` は同値を捨て、その状態の更新の開始時に持っている値を届ける |
| RxJS           | プッシュ、購読ごとに深さ優先                         | 受け取った発行のたび。購読ごとに別々に（コールド）                                                                   | なし                   | なし                                    | 届く                                                                                               |
| MobX           | 無効化はプッシュ、再計算はプル                       | `computed`：読まれたとき（キャッシュは観測中のみ）、`reaction`：依存が変わったとき                                   | あり                   | `reaction` を作った順番による           | 届かない：同値は捨てられ、action は最後の書き込みを届ける                                          |
| Jotai          | 無効化はプッシュ、再計算はプル                       | 読まれたとき（`store.get`、フック）かマウントされたとき（`store.sub`、コンポーネント）。どちらでもない間は計算しない | あり                   | あり：非同期 atom はグラフのノード      | 届かない：同値は捨てられる                                                                         |
| Solid          | プッシュ、書き込みの下流をすべて印付けしてから再実行 | メモ：直前の実行で読んだソースが変わるたび。読まれているかどうかにかかわらない。effect：メモの後                     | あり                   | あり：`createResource` はグラフのノード | 届かない：同値は捨てられ、`batch` は最後の書き込みを届ける                                         |
| Preact Signals | 無効化はプッシュ、再計算はプル                       | `computed`：ソースのどれかが新しいバージョンになった後に読まれたとき。`effect`：最も外側のバッチの終わり             | あり                   | effect を作った順番による               | 届かない：同値は捨てられ、`batch` は最後の書き込みを届ける                                         |

後ろの 3 つの列は別々のことを問うています。最初の 2 つはグリッチについての列で、1 つ目はグラフから読む派生値について、2 つ目はリクエストを始める段についてです。検索欄なら、クエリ、それが始めるリクエスト、両方を読む view があります。ライブラリ自身の非同期の仕組みがグラフのノードなら、view はクエリ 1 回につき辻褄の合った組で 1 回実行されます。段が値を書き込む effect や `reaction` なら、それより先に作った view が先に実行され、新しいクエリと古い結果の組を見て、もう一度実行されます。3 つ目はグリッチではなく、イベントを数えたり組にしたりするオペレーターがすべての書き込みを受け取るかどうかです。2 つ目と 3 つ目は、[Signals の上のオペレーター](/mono/synstate-next/ja/comparison/operators-on-signals/)で Preact Signals を使って動かします。

synstate-next のモデルは短く言えます。書き込みが更新を始めます。更新はまず、届いた派生値を浅いものから順に 1 回ずつ計算し、すべての値が新しくなった後で初めて、購読者と synstate-dom-next の束縛を実行します。派生値を計算している間の書き込みはその購読者と束縛の後まで待ち、購読者や束縛の書き込みは次の更新を始めます。更新の外かつ `batch` の外で行った書き込みが返った時点で、グラフ内のすべての `.value` は最新で、すべての購読者が実行済みです（[更新の伝わり方](/mono/synstate-next/ja/internals/how-an-update-propagates/)）。

RxJS もプッシュ型ですが順序を決める段階がなく、それがグリッチと経路数に比例するコストの原因です。MobX と Jotai は逆に、読むときに計算し直すことでグリッチを避けます。MobX の `ComputedValue` は「アクセスされているときだけ」計算し直し、観測されなくなるとリセットされます（[ソース](https://unpkg.com/mobx@7.0.6/src/core/computedvalue.ts)）。Jotai のストアはマウントされているか読まれた atom だけを計算し直します（[ソース](https://unpkg.com/jotai@3.0.1/dist/vanilla/internals.js)）。そのため誰も読まない処理を飛ばせます。その代わり、処理は何かが求めたときに、求めたときだけ行われます。synstate-next が処理を飛ばせるのは、グラフがノードを外したところ（選ばれた枝への `switchMap`、破棄した owner）だけです。Preact Signals も読むときに計算し直し、signal と `computed` ごとのバージョン番号で、読んだときに計算し直すものがあるかを決めます。Solid は synstate-next と同じくプッシュ型で先行評価ですが、メモは MobX や Jotai の派生と同じく、直前の実行で読んだものだけを購読します。

### UI の外で

ここのライブラリはどれもバニラ API を持つので、UI フレームワークなしで動き、Solid と Preact Signals はそれぞれのフレームワークの外でも動きます。違うのは、読み手が現れる前に何かが動くかどうかと、処理を何が所有するかです。

- **synstate-next** は派生 Observable を作成時に親へ登録し、ソースが更新されるたびに計算するので、モジュールスコープに書いたパイプラインは、購読の有無にかかわらずソースが変わった時点で動きます。検索ボックスのクエリを debounce して `switchMap` で `fromAbortablePromise` につなぐ処理を普通のモジュールに置け、コンポーネントでもテストでもスクリプトでも、読めば同じ値が得られます（[例](/mono/synstate-next/ja/guides/declarative-state/)）。パイプラインが作ったものは現在の owner に属し、owner を破棄すると、リクエストの中断、タイマーの解除、購読の解除がまとめて行われます（[owner と寿命](/mono/synstate-next/ja/guides/owners-and-lifetime/)）。どの owner の外でもないモジュールスコープでは、ページと同じだけ生きます。モジュールに置いたパイプラインにはそれが望ましい振る舞いです。
- **RxJS** もモジュールスコープに書けますが、パイプラインはコールドです。購読されるまで何も動かず、購読のたびにパイプラインが改めて実行されるので、共有（`share`、`shareReplay`）しない限り中の `fetch` は購読者ごとに送られます。
- **MobX** は `computed` を読まれるまで評価せず、観測されていない間はキャッシュもしません。fetch のような副作用を伴う処理は、アプリケーション自身が始める `reaction` / `autorun` やアクション（`flow`）に書きます。`reaction` は先行して動き、`delay` オプションで間引けます。新しい値で古くなった fetch を取り消すのは effect の仕事です。
- **Jotai** は atom の read 関数（非同期 atom の fetch を含む）を、その atom が初めて読まれたかマウントされたときに実行します。React ではそれはコンポーネントのレンダリングで（非同期 atom はそのコンポーネントをサスペンドさせます）、React の外ではコードが `store.get` か `store.sub` を呼ぶまで何も動きません。atom で書いたデータ読み込みは、それを読むものが予定することになり、アプリケーションでは多くの場合 React のレンダリングです。jotai 3.0.1 のバニラストアで確かめると、route の atom から派生した非同期 atom は `store.sub` までは何も取得せず、購読中は route が変わるたびに取得し、前のものを `signal` で中断します（`switchMap` に相当）。最後の購読者が離れると、route が変わっても何も取得しません。debounce は派生の中には書けず、書き込む側に作る必要があります。
- **Solid** のリアクティブプリミティブ（`createSignal`、`createMemo`、`createEffect`、`createRoot`）は `solid-js` 本体にあり、DOM レンダラーも JSX も要りません。計算は synstate-next と同じく owner に属し、owner の外では片付けられません。Node では `import 'solid-js'` がサーバー用ビルドに解決され、そこではメモは 1 回だけ計算され、effect は実行されません。`browser` の export 条件か、クライアント用ビルドのパス（`solid-js/dist/solid.js`）が必要です。ほかのフレームワークとの公式の連携はなく、橋渡しは `observable()` / `from()` か自前の effect です。Solid 2.0 はリアクティブなコアを `@solidjs/signals` として単独で公開しています（執筆時点ではリリース候補）。そこでは書き込みがマイクロタスクか明示的な `flush()` までまとめられるので、書き込み直後に読んだメモはまだ前の値を返します。
- **Preact Signals** のコア `@preact/signals-core` は Preact に依存しません。`signal`、`computed`、`effect`、`batch` はブラウザでも Node でも Worker でも同じように動きます。作るべきルートや owner はなく、`effect` は自分の破棄関数を返し、`signal.subscribe(fn)` はコールバックに値を渡します。`computed` は遅延評価で、読まれたときに実行され、読まれないものは何もしません。effect は先行して動き、最も外側のバッチの終わりに実行されます。非同期オペレーターはなく、fetch は effect の中に書き、古くなったものの取り消しはその effect の後始末です。

## 各ライブラリ

### synstate-next

1 つのスケジューラを軸に作った状態管理ライブラリです。更新は届いたノードを深さ順に訪れ、購読者より先に派生値を計算し、どの読み手にとっても整合したグラフを残します。共有された状態（`createState`）から非同期の処理（`debounce`、`throttle`、`switchMap`、`fromAbortablePromise`）まで、1 つの API で扱えます。

**強み：**

- どの読み手にもグリッチフリーです。派生値は深さ順にそれぞれ 1 回計算され、購読者はその後で、すべての値が新しくなってから実行されます。
- 非同期の段と状態を持つ段（`switchMap`、`debounce`、`scan`）が同じグラフのノードなので、リクエストの段も `map` と同じくグリッチフリーで、emitter の発行は 1 つ残らずイベントです。
- 更新のコストは、グラフのうち変わった部分に比例します。持っている値と同じ値を計算したノードは何も渡さず、その下は訪れません（[値を派生させる](/mono/synstate-next/ja/guides/deriving-values/)）。
- すべてに 1 つの寿命です。owner を破棄すると、そのリクエストは中断され、タイマーは解除され、購読は外れます。伝える完了はありません（[完了がない理由](/mono/synstate-next/ja/internals/why-no-completion/)）。
- 型がグラフに従います。`pipe` は各オペレーターの種類から、結果が常に値を持つか（`InitializedObservable`）を計算します。
- パイプラインはどのコンポーネントからも独立してモジュールスコープで動き、テストやスクリプトでも同じように動きます。

**トレードオフ：**

- 派生値は、何も読んでいなくてもソースが更新されるたびに計算し直されます。MobX、Jotai、Preact Signals はその処理を飛ばします。飛ばされるのはグラフが持たなくてよいノードで、選ばれた枝への `switchMap` や owner の破棄で外せます。
- オペレーターは RxJS より少ないですが、モデルに必要なものは揃っています。どの Observable も最初から共有されているので `share` / `shareReplay` の類は要らず、エラーは `catchError` ではなく `Result` の値として流れます。自前のオペレーターとソースは `createDerived` と `createSource` で書きます（[独自のオペレーターとソース](/mono/synstate-next/ja/guides/custom-operators-and-sources/)）。
- React や Preact との連携はまだありません。UI の層は、Observable を DOM に直接束縛する [synstate-dom-next](/mono/synstate-dom-next/ja/) です。

**向いているもの：** 共有された状態と非同期のパイプラインの両方を 1 つの一貫したモデルで扱い、後片付けまで寿命に任せたいプロジェクト。

### RxJS

RxJS は ReactiveX の Observable 仕様の基準実装で、非同期処理やイベント駆動のプログラムのための多数のオペレーターを持ちます。

**強み：**

- 非常に多いオペレーター（200 以上）。
- 確立されたエコシステムとコミュニティ。
- イベント処理（WebSocket のストリーム、リトライ）に強い。

**トレードオフ：**

- 同期的な派生値を組み合わせるとグリッチが起きます。2 つの経路で届くノードは経路ごとに発行します（[更新の伝わり方](/mono/synstate-next/ja/internals/how-an-update-propagates/)）。
- ストリームには命令的な考え方からの切り替えが要ります。コールドとホットの区別、似たオペレーター（`switchMap`、`mergeMap`、`concatMap`、`exhaustMap`）の慎重な使い分けです。
- 状態のための設計ではありません。`BehaviorSubject` 以外に現在値はなく、共有しなければパイプラインは購読者ごとに実行されます。

**向いているもの：** 派生値どうしのグリッチが問題にならない、非同期のイベント処理が中心のアプリケーション。

### MobX

MobX は JavaScript のプロキシによる透過的なリアクティブプログラミングです。observable なオブジェクトを書き換えると、それを読む `computed` が計算し直され、`observer` コンポーネントが再レンダリングされます。

**強み：**

- ミュータブルな書き方の API。状態を直接書き換えればすべてが更新されます。
- 依存を自動で追跡する細粒度のリアクティビティ。
- 遅延評価の `computed` によるグリッチフリー。

**トレードオフ：**

- 暗黙の依存追跡は、大きなコードベースでデータの流れを追いにくくします。
- 非同期オペレーターはありません（`flow` か自前のコード）。
- `computed` や `reaction` は実行のたびに読むものを追跡し直します。
- `observer()` はレンダリング中の observable へのアクセスを追跡するので、React Compiler とは両立しません（`"use no memo"` で除外する必要があります）。

**向いているもの：** 自動のリアクティビティとミュータブルな書き方を好み、非同期オペレーターを必要としないチーム。

### Jotai

Jotai はプリミティブな atom から状態を組み立てます。派生 atom は自然に組み合わさり、`createStore` で React の外でも使えます。

**強み：**

- アトミックなモデルで不要な再レンダリングを避けます。
- 依存を自動で追跡する、組み合わせやすい派生 atom。
- 小さなバンドル。

**トレードオフ：**

- 非同期オペレーターの連鎖はありません（非同期 atom はありますが、[上](#ui-の外で)の制約があります）。
- `store.set` はすべてストア単位の管理処理を通ります。
- `store.sub()` のコールバックは値を受け取らない（`() => void`）ので、読むには別に `store.get(atom)` が要ります。synstate-next の `subscribe((value) => …)` は値を渡します。

**向いているもの：** 細粒度のアトミックな状態と単純な派生が役に立つ React アプリケーション。

### Redux（Redux Toolkit）

Redux は Flux アーキテクチャにもとづく、予測可能な状態コンテナです。Redux Toolkit は `createSlice` と `configureStore` で定型コードを減らします。

**強み：**

- 予測可能な一方向のデータフロー。
- タイムトラベルデバッグのできる DevTools。
- 大きなエコシステム（ミドルウェア、saga、thunk）。

**トレードオフ：**

- Redux Toolkit を使っても記述が多くなります。
- セレクター（Reselect）はプル型で、メモ化は手で行います。
- リアクティブな伝播はなく、非同期処理はミドルウェアに任せます。

**向いているもの：** 厳格な一方向のデータフロー、タイムトラベルデバッグ、成熟したミドルウェアのエコシステムを重視する大きなチーム。

### Solid

Solid は細粒度の signal（`createSignal`、`createMemo`、`createEffect`）の上に作られた UI フレームワークで、コンパイルされた JSX が DOM を直接更新します。リアクティブなプリミティブはレンダラーなしで動きます（必要なことは [UI の外で](#ui-の外で) にあります）。

**強み：**

- グリッチフリーなプッシュ型の伝播。書き込みの下流をすべて印付けしてからメモを再実行するので、各メモは更新ごとに 1 回実行されます。
- 動的な依存追跡。メモは直前の実行で読んだものだけを購読するので、何も観測していない書き込みはほとんどコストがかかりません。
- `createMemo(fn, initialValue)` は前の値を受け取るので、状態を持つ派生（`scan`）もほかのメモと同じく書けます。
- 成熟したフレームワークと広いエコシステム。

**トレードオフ：**

- フレームワークと切り離して使うことはできますが、パッケージはその形を想定していません。計算には owner が要り、Node では `solid-js` がリアクティブでないサーバー用ビルドに解決され、ほかのフレームワークとの連携はありません。
- 書き込みのたびに更新キューを確保し、再実行のたびに計算をすべてのソースから外して登録し直します。
- 非同期オペレーターの連鎖はなく、取得は Suspense と組み合わせた `createResource` が扱います。

**向いているもの：** Solid のアプリケーション。Solid の外では、ルートの管理と Node が解決するビルドに対処できるコード。

### Preact Signals

Preact Signals は Preact チームの signal ライブラリ（`signal`、`computed`、`effect`）で、フレームワークに依存しないコア（`@preact/signals-core`）と、Preact・React との連携として公開されています。

**強み：**

- 公開の形からしてフレームワーク非依存です。コアは Preact に依存せず、ルートも準備も要りません。
- 更新ごとのオーバーヘッドが小さい。バージョン番号で再実行するものを決め、前回と同じものを読む実行は依存のリンクを使い回し、何も確保しません。
- 遅延評価の `computed` によるグリッチフリー。誰も読まない派生値は計算されません。
- 小さな API。`subscribe(fn)` はコールバックに値を渡します。

**トレードオフ：**

- 非同期オペレーターはありません。
- `computed` は前の値を受け取らないので、状態を持つ連鎖（`scan`）は effect が更新する signal として書くことになり、グリッチフリーの保証の外に出ます（[Signals の上のオペレーター](/mono/synstate-next/ja/comparison/operators-on-signals/)）。
- React との連携は Babel の変換か `useSignals` フックで動き、React Compiler との両立はここでは確かめていません。

**向いているもの：** 小さく速い、フレームワーク非依存の signal を求め、非同期オペレーターを必要としないプロジェクト。

### Zustand

Zustand は Flux に着想を得た小さなストアで、最小限の API、よい TypeScript の対応、React との連携を持ちます。

**強み：**

- 単純な状態に対して軽く速い。
- 覚えやすい最小限の API。
- React でプロバイダーが要りません。

**トレードオフ：**

- 派生値のプリミティブはなく、派生はインラインのセレクターです。
- 独立した派生値を組み合わせられません。
- 非同期オペレーターはありません。

**向いているもの：** 複雑な派生のない、オーバーヘッドの小さい共有状態。

### Valtio

Valtio は JavaScript のプロキシで、ミュータブルな書き方の API を提供します。プロキシのオブジェクトに書き込むと購読者に通知されます。

**強み：**

- オブジェクトを書き換えるだけの直感的な API。
- 小さなバンドル。
- React では `useSnapshot` によるレンダリングの最適化。

**トレードオフ：**

- バニラ API に派生値のプリミティブはありません（`derive` は別のユーティリティです）。
- 独立した派生値を組み合わせられません。
- プロキシによる変更検出には、一部のデータ構造で例外的な振る舞いがあります。

**向いているもの：** 複雑な派生のない共有状態を、最も単純なミュータブルな API で扱いたい場合。

## ほかのライブラリ

目的は違いますが、要件によっては検討に値するものです。

### Recoil

Recoil は Meta による、React 向けの実験的なアトミック状態ライブラリです。もうメンテナンスされておらず（npm の最終リリースは 2023 年）、React の外の API もありません。React にアトミックなモデルを持ち込み、非同期のセレクターと Concurrent Mode に対応していました。新しいプロジェクトなら、Recoil に着想を得てメンテナンスされている Jotai が代わりになります。

### XState

XState は状態マシンとステートチャートのライブラリです。アプリケーションのロジックを、明示的な状態、遷移、副作用を持つ有限状態マシンとして表し、ビジュアルエディター（Stately）もあります。リアクティブな状態コンテナとは別の問題を解くもので、状態のはっきりした流れ（ウィザード、認証、メディアプレイヤー）のうち、伝播より形式的な正しさが大事なものに向きます。

### TanStack Query

TanStack Query はサーバーの状態を扱います。取得、キャッシュ、重複の排除、バックグラウンドでの再取得、stale-while-revalidate を持ち、React、Vue、Solid、Svelte 向けのアダプターがあります。synstate-next のようなクライアントの状態ライブラリの代わりではなく、補い合うものです。`switchMap` と `fromAbortablePromise` で書いたリクエストの段は、キャッシュではなくグラフの中の値です。

## ライブラリの選び方

| 要件                                                  | 候補                                              |
| ----------------------------------------------------- | ------------------------------------------------- |
| 単純な共有状態（ダークモード、ユーザーのセッション）  | Zustand、Valtio、Jotai                            |
| 非同期のパイプライン（debounce、switchMap、リトライ） | **synstate-next**、RxJS                           |
| グリッチフリーな派生値の上の非同期オペレーター        | **synstate-next**                                 |
| グリッチフリーな派生値                                | synstate-next、MobX、Jotai、Solid、Preact Signals |
| リクエストの中断とタイマーの解除まで担う 1 つの寿命   | **synstate-next**、Solid                          |
| ミュータブルな書き方の API                            | MobX、Valtio                                      |
| アトミックで細粒度のリアクティビティ                  | Jotai、Solid、Preact Signals                      |
| 厳格な一方向のデータフロー                            | Redux                                             |
| 形式的な状態マシン                                    | XState                                            |
| サーバーの状態のキャッシュ                            | TanStack Query                                    |
| 単純な状態から複雑な非同期処理まで 1 つの API         | **synstate-next**                                 |

[非同期処理の比較](/mono/synstate-next/ja/comparison/async-logic/)では、派生値を持つ各ライブラリで 1 つの検索ボックスを、同じテストスイートに対して書き比べます。
