[`apps/synstate-dom-benchmark`](https://github.com/noshiro-pf/mono/tree/main/apps/synstate-dom-benchmark) は、[js-framework-benchmark](https://github.com/krausest/js-framework-benchmark) の操作、つまり表の行の作成・置き換え・部分更新・選択・入れ替え・削除・追加・全消去で UI ライブラリの時間を測ります。数値がグラフで互いに派生する 3 つの[シナリオ](#シナリオ)も測ります。その `benchmark:next` は、synstate-dom-next を、置き換える予定の世代である synstate-dom と、このベンチマークで最も速い Solid と比べます。Preact + Signals・Preact・React・VanJS との比較は [synstate-dom のサイト](https://noshiro-pf.github.io/mono/synstate-dom/ja/background/benchmark/)にあります。

以下の数値は同アプリの [`RESULTS-NEXT.md`](https://github.com/noshiro-pf/mono/blob/main/apps/synstate-dom-benchmark/RESULTS-NEXT.md) から埋め込んだもので、1 台のマシンで測ったものです。このハーネスの中で実装どうしを比べるためのもので、js-framework-benchmark が公開している表と比べるものではありません。

## 結果の読み方

synstate-dom-next の時間は、操作によって synstate-dom の <!-- benchmark:next-over-dom-min -->0.78<!-- /benchmark --> 倍から <!-- benchmark:next-over-dom-max -->1.00<!-- /benchmark --> 倍で、Solid に対しては最大 <!-- benchmark:next-over-solid-max -->1.31<!-- /benchmark --> 倍でした。

- **行の作成と全消去**は、行あたりのコストが下がります。行の束縛はそれぞれ、クロージャ・購読者・後始末の組ではなく 1 つのオブジェクトで、行を消すときはその owner を破棄するだけで、ノードに完了を流す必要がありません（[仕組み](/mono/synstate-dom-next/ja/background/how-it-works/#synstate-dom-より速い理由)）。Solid との残りの差はテンプレートの複製です。Solid はコンパイルした `<template>` を行ごとに複製しますが、synstate-dom-next はノードごとに `createElement` を呼びます。
- **部分更新**は、ドキュメントが勧めるとおり配列全体を置き換えます。キーが変わらないので `For` は差分を取らず、各要素をその行の state に入れます。要素が同じオブジェクトの 900 行は等値カットオフで state のところで止まり、変わった 100 行だけが束縛に届きます。
- **行の選択**は、Solid の `createSelector` と同じく `selector` で 2 行だけに書き込みます。synstate-dom では 1,000 行のそれぞれで `map` が走っていました。
- **2 行の入れ替え**はどのライブラリも 2 行を動かすだけなので、ライブラリが省ける部分はほとんどありません。

## シナリオ

js-framework-benchmark では各行が自分のデータにしか依存しないので、変更をどの順で伝えるかはほとんど効きません。以下のシナリオは、数値が少数の入力からグラフで派生する画面です。最初の 2 つでは 1 つの入力が長さの違う経路で 1 つの数値に届くダイヤモンドがあり、3 つ目ではほとんどの変更が、同じ値になる数値のところで止まります。どれも多くの数値を計算して少しだけを表示するので、時間の大半は DOM ではなく伝播にかかります。

- **ローン**：30 年の月払いローンを、1 年 1 行と合計で表示します。各月の利息は前月の残高から、返済額は前月の残高とその利息から、新しい残高は前月の残高と返済額から計算するので、360 か月はダイヤモンドの連鎖です。金利を変えるとすべての月が変わり、181 か月目の繰り上げ返済は連鎖の半分を、349 か月目のものは最後の 1 年を変えます。
- **スケジュール**：それぞれ前の 1〜3 個に依存する 1,000 個のタスクのクリティカルパスです。前向きの計算で各タスクの最早開始と最早終了を、後ろ向きの計算で最遅開始を出し、その差が余裕です。最初のタスクを延ばすとほぼすべての数値が変わり、途中のタスクを延ばすと数十個だけが変わります。周りのタスクの余裕が変化を吸収するためです。
- **ズーム**：地図上の 10,000 か所のラベルを、0.1 刻みのズームで表示します。ズームから詳細度が決まり、各ラベルの大きさは詳細度だけから計算します。同じ詳細度の中でのズームは、詳細度が同じ値になるので画面上のズーム表示しか変わらず、次の詳細度へのズームはほとんどのラベルを変えます。

各シナリオでは画面の構築、つまりグラフ全体の構築の時間も測ります。**synstate-dom (derive)** は synstate-dom-next のコードを synstate と synstate-dom で書いたもので、数値はどれも 1 つの `derive` か `map` です。これと synstate-dom-next の差は、数値の書き方ではなくライブラリの差です。**synstate-dom (skipIfNoChange)** は、すべての数値の後に `skipIfNoChange` を足したものです。

### シナリオの読み方

- **画面の構築**では数値ごとにノードを作ります。synstate-dom-next は最良で synstate-dom の <!-- benchmark:build-next-over-dom-min -->0.33<!-- /benchmark --> 倍の時間です。ノードはメソッドをプロトタイプに持つクラスのインスタンスで、owner はそれを素のリストに持つだけだからです。
- **途中で止まる変更**（途中のタスクを延ばす、同じ詳細度の中でズームする）は、synstate のどちらの世代でも安く済みます。値を渡したノードの子だけを訪れるからです。Solid はまず下流のすべてを「古いかもしれない」と印を付け、それから確かめます。
- **遠くまで届く変更**（金利の変更、最初のタスクを延ばす、次の詳細度へのズーム）では、ドレインのノードあたりのコストが表に出ます。書き込みごとの更新トークンがなく、キューは整数で動く 1 つだけで、各ノードを 1 回だけ訪れます。
- **正しさが先です。** ハーネスは各操作の後、描画されたセルを素のループで計算した数値と比べ、違う数値を描いたライブラリは時間を測らず _wrong_ と記します。

ここでの変更は 1 ミリ秒を大きく下回るので、シナリオでは、ブラウザが 4 ms まで遅らせる `setTimeout` ではなく `MessageChannel` で次のタスクを待ちます。また 1 サンプルは、操作とその逆を交互に行った 20 回の変更の平均です。

## 何を測っているか

js-framework-benchmark の操作では、どの実装も同じ表をマウントします。項目ごとに 1 行で、項目の id とラベルを 2 つのセルに表示し、選択した行に `danger` クラスを付けます。計測の前に、ハーネスはすべての実装が同じ操作の後に同じ行を描画することを確かめます。

1 つの操作は、呼び出しから、マクロタスクを 1 つ経てブラウザが表をレイアウトし直すまでを測ります。この待ちはすべての実装が払うので、すべての数値をほぼ同じだけずらします。

ライブラリは本番ビルド（`mode: 'production'` と `production` の export 条件）と本番用の JSX ランタイムで、Vitest のブラウザモードのヘッドレス Chromium で動かします。

## それぞれの書き方

- **synstate-dom-next**：行は `state` に入れた 1 つのイミュータブルな配列で、`For` は行ごとに state を持ち、`selector` は選択が変わった 2 行だけに書き込みます。シナリオでは各数値が 1 つの `derive` か `map` で、どちらも変わった値だけを渡します。
- **synstate-dom**：行は `createState` に入れた 1 つのイミュータブルな配列で、`For` が各行の値をそこから派生させます。選択は、各行が `pipe(map(...))` で束縛する state です。
- **Solid**：ラベルごとのシグナル、行オブジェクトに対する `For`、選択には `createSelector` を使います。`vite-plugin-solid` でコンパイルします。

## 実行のしかた

これは CI では動かしません。共有ランナーでの計測にはあまり意味がなく、アサートするベンチマークは不安定になるだけです。同じマシンでも実行ごとに 10〜30% ずれるので、ここの数値は `benchmark:repeat` による複数回の中央値です。

```sh
pnpm run ws:build                     # ライブラリは dist/ から import します
cd apps/synstate-dom-benchmark
pnpm run benchmark:repeat -- --next   # 5 回の中央値。RESULTS-NEXT.md を書き換えます
cd ../synstate-dom-next-docs
pnpm run gen:benchmark                # RESULTS-NEXT.md をページに埋め込みます
```
