このページでは、書き込みから DOM までの更新の流れを追います。扱うのは synstate-dom-next と、それが土台にしている synstate-next の部分です。残りは synstate-next の [DESIGN.md](https://github.com/noshiro-pf/mono/blob/main/libs/synstate-next/DESIGN.md) にあります。

## 書き込みから DOM まで

更新には 2 つの段階があります。まず**ドレイン**が、書き込みの届いたノードを深さの順に計算し直します。次に **effect** が実行されます。束縛、switch、`For`、すべての `subscribe` が、落ち着いたグラフに対してそれぞれ 1 回ずつ実行されます。

```text
price$.set(120)                 状態、深さ 0
   │
   │  更新に番号（epoch）を振り、price$ の子をその番号でキューに入れる
   ▼
ドレイン（深さごと）
   深さ 1   label$ = price$.pipe(map(p => `${p} yen`))     1 回だけ計算し直す
   深さ 1   isCheap$ = price$.pipe(map(p => p < 100))      true → false：先へ渡す
   深さ 2   ...                                            変化が届いたものだけ
   ▼
effect（ドレインの後）
   TextBinding(label$)                text.data = '120 yen'
   ClassToggleBinding(isCheap$)       classList.toggle('cheap', false)
   ▼
次のラウンド（effect が状態に書き込んだときだけ）
```

- **キューに入れるのは番号です。** 更新はそれぞれ整数、つまり epoch です。ノードは `queuedAt` が epoch と等しければ今の更新のキューに入っています。そのためキューに入れるのに何も確保せず、親が 1 つのノードはどの親が変わったかを問う必要もありません。
- **深さがグリッチを防ぎます。** ノードの深さは、最も深い親より 1 つ深い値です。ドレインは深さごとに訪れるので、各ノードは更新ごとに、親がすべて済んだ後で 1 回だけ計算されます。ダイヤモンド（`tax$` 自体が `price$` から派生している `total = derive([price$, tax$], ...)`）も、食い違いのない値から 1 回だけ計算されます。
- **等しい結果はそこで止まります。** 計算し直した値が `Object.is` で等しいノードは何も先へ渡さず、その下は訪れません。
- **effect は落ち着いたグラフで動きます。** 束縛が、同じ更新の中でこれから変わる値を読むことはありません。また、入力がいくつ変わっても、更新ごとに 1 回しか実行されません。
- **書き込みは割り込みません。** ドレイン中（`map` の中）の書き込みは、そのラウンドの effect が実行されるまで待つので、そのラウンドの束縛は書き込み前の値を見ます。その後、effect の書き込みと同じく次のラウンドを始めます。effect から書き込み続けるプログラムは、無限に回る代わりに、100 ラウンドで原因を示すエラーとともに止められます。

## 束縛は 1 つの effect

束縛した属性・プロパティ・クラス・スタイル・テキストは、それぞれ 1 つのオブジェクトです。対象を自分のフィールドに持つ effect クラスのインスタンスです。

```text
synstate-dom                          synstate-dom-next
  source.subscribe(v => el.x = v)       class PropertyBinding extends EffectClass {
  ├ 束縛ごとのクロージャ                  #element; #name
  ├ 購読者の記録                          run() { this.#element[this.#name] = this.source.current }
  └ スコープへの後始末の登録            }
                                        オブジェクト 1 つ。owner と一緒に破棄
```

`run` は、同じ種類のすべての束縛が共有するプロトタイプのメソッドです。1,000 行を作るときに作るのは束縛ごとに 3 つではなく 1 つのオブジェクトで、更新が束縛に届いたときに呼ぶのは 1 つのメソッドです。

イベントハンドラも、逆の側から見れば同じ考え方です。ハンドラは要素が持っていればその `on…` プロパティに代入し、取り外しません。要素はそれを作った owner と一緒に手放されるからです。

## マウントはバッチ

`render`・分岐・行は、バッチの中でマウントされます。マウント中の書き込み（props から状態を設定するコンポーネントや、最初の呼び出しで書き込む `subscribe`）は、作りかけの DOM に届くのではなく、ノードが置かれた後に 1 回の更新として伝播します。

## switch は分岐が計算する前に決める

`If`・`MatchOptional`・`MatchResult`・`Switch` は、分岐を effect の中、つまりドレインの後でアンマウントします。それだけだと、ドレインはその前に、分岐を外すまさにその値で分岐自身のノードを計算し直してしまいます。`MatchOptional` の分岐の `map` が `none` を取り出そうとし、行の `map` がもう無い位置を読む、といったことです。

そこで switch はドレインの中で決めます。切り替えの元になる値の下に小さな検査ノードを置き、分岐が作るノードはすべてその検査より深いところに置きます。

```text
深さ 0     page$                                  切り替えの元の値
深さ 1     検査：key(page$) はまだ 'item' か？    違う → ここで分岐を退かせる
深さ 2 以上 分岐 'item'：title$ = page$.pipe(map(p => p.title))
                         ↑ 分岐を外すページのときは訪れない
effect     switch が分岐をアンマウントし、次の分岐をマウントする
```

- 分岐の owner は**深さの下限**付きで作ります。その中、そしてその子の owner の中で作られるノードはどれも下限以上の深さになるので、ドレインは先に検査に届きます。
- 分岐を**退かせる**（retire する）と、そのノードと effect をこれからの更新から外しますが、アプリケーションのコードは何も実行しません。ドレイン中に後始末は実行されません。その後 effect が分岐の owner を破棄して後始末を実行し、次の分岐をマウントします。
- `For` も行について同じことをします。キーをドレインの中で検査し、キーが無くなった行を、そのノードを訪れる前に退かせます。
- キーの関数が投げた例外はドレインの中には出しません。switch は保てなかったものを退かせ、effect がそれを外して、その例外を switch 自身の例外として投げます。更新の残りは最後まで進みます。

分岐が作るのではなく渡される Observable（JSX を書いた場所で作ったもの）は分岐のものではなく、値が来るたびに計算します。[ライフサイクルと owner](/mono/synstate-dom-next/ja/guides/lifecycle/#2-つの書き方)で、分岐で表示するものは分岐の中で作るように勧めているのはそのためです。

## `For` は行ごとに状態を持つ

各行は `item$`（行の関数が受け取るなら `index$` も）の裏に状態を持っています。`items` が変わると、`For` の effect がキーを比べます。

- キーが同じ順で同じなら、キーによる差分を取らず、何も動かしません。
- 要素が前と同じオブジェクトの行は、訪れもしません。
- 要素が変わった行は状態に書き込まれ、起きるのはその行のノードと束縛だけです。
- それ以外の場合は行を足し、破棄し、動かします。動かす数は、元の位置の最長増加列が許すかぎり少なくします。

行の状態への書き込みは次のラウンドを始めるので、行が新しい要素を読むのは `items` が変わった 1 つ後の更新です。どちらのラウンドも描画より前に終わります。`selector` も同じ仕組みで、選択すると古い行と新しい行の状態にだけ書き込み、ほかの行には書き込みません。

## synstate-dom より速い理由

作り直しは[ベンチマーク](/mono/synstate-dom-next/ja/background/benchmark/)で synstate-dom と比べています。時間がどこに使われるかを定性的に見ると、次のとおりです。

- **束縛とノードごとのオブジェクトが少ない。** 束縛はクロージャ・購読者・後始末ではなく 1 つのオブジェクトで、ノードはフィールドを持つクラスのインスタンス、メソッドはプロトタイプにあります。行を作って破棄する時間のほとんどはこれらの確保と解放なので、10,000 行の作成や全行の削除がいちばん改善します。
- **更新トークンがない。** synstate は書き込みのたびにトークンを確保し、下へ伝えながら比べます。ここでは更新は番号です。部分的な更新や選択では、ほとんど何も確保しません。
- **伝播させる完了がない。** Observable は owner と一緒に破棄されることで終わります。行を消すときに、行のすべての子へ `complete` を伝えることも、参照カウントを減らすこともありません。
- **束縛は更新ごとに 1 回。** effect はドレインの後に、入力がいくつ変わっても 1 回ずつ実行されます。
- **`For` の仕事が少ない。** 要素が変わらなかった行は飛ばし、キーの順が変わらなかったリストはキーによる差分を取りません。
- **すべてのノードで等値の打ち切り。** 派生ノードはどれも、後ろにノード（`skipIfNoChange`）を足すのではなく自分で等しい結果を止めます。そのため、同じ結果になる変更（同じ段階の中でのズーム、余裕が遅れを吸収するタスク）は、その下に何があっても最初に気づいたノードで止まり、グラフを作る手間も増えません。
