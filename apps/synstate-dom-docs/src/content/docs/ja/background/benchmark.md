[`apps/synstate-dom-benchmark`](https://github.com/noshiro-pf/mono/tree/main/apps/synstate-dom-benchmark) は、[js-framework-benchmark](https://github.com/krausest/js-framework-benchmark) の操作（表の行の作成・置き換え・部分更新・選択・入れ替え・削除・追加・全消去）で、synstate-dom を Solid、Preact + Signals、Preact、React、VanJS と比べています。値どうしがグラフでつながる 3 つの[シナリオ](#シナリオ)でも比べていて、そのうち 2 つは長さの違う diamond を持ち、残りの 1 つはほとんどの変更が途中で止まります。

以下の数値はその [`RESULTS.md`](https://github.com/noshiro-pf/mono/blob/main/apps/synstate-dom-benchmark/RESULTS.md) から埋め込んだもので、1 台のマシンで計測しています。この計測の中で実装どうしを比べるための数値なので、js-framework-benchmark が公開している表とは比べられません。

## 結果の読み方

synstate-dom が目指すのは、すべての行での最速ではなく、シンプルな API でそこそこ速く、遅くなる場面が少ないことです。最も遅い操作でも最速のライブラリの <!-- benchmark:worst/synstate-dom -->1.56<!-- /benchmark --> 倍で、<!-- benchmark:placement/behind -->Solid・Preact・Preact + Signals には及びません<!-- /benchmark -->が、React（<!-- benchmark:worst/react -->3.79<!-- /benchmark --> 倍）と VanJS（<!-- benchmark:worst/vanjs -->8.89<!-- /benchmark --> 倍）を大きく下回ります。

この計測では、synstate-dom は操作によって Solid の <!-- benchmark:reference-min -->1.01<!-- /benchmark --> 倍から <!-- benchmark:reference-max -->1.56<!-- /benchmark --> 倍の時間がかかりました。数行だけが変わる操作（10 行ごとの更新、行の選択）では最速に近く、多くの行を作る操作でいちばん差が開きます。ほかのライブラリと比べてどの操作が速く、どの操作が遅いかは上の表を見てください。

- **行の作成**は、コンパイラがないことがいちばん効いてくるところです。Solid は行ごとにコンパイル済みの `<template>` を複製しますが、synstate-dom はノードごとに `createElement` を呼び、動的な葉をそれぞれ購読で束縛します。さらに行ごとに synstate のノードも作ります。要素のためのノードが 1 つ（位置を受け取る行ではもう 1 つ作りますが、この表の行は受け取りません。[制御構文](/mono/synstate-dom/ja/guides/control-flow/#for)の `For` を参照）と、2 つの束縛それぞれの `map` のノードです。行の作成と破棄にかかる時間はノード数にほぼ比例して増えます。
- **部分更新**は、実装によって通る経路が違います。Solid・Preact + Signals・VanJS はラベルごとに signal を持っていて、変わる 100 個に書き込みます。synstate-dom はドキュメントでおすすめしているとおり配列全体を置き換え、各行の `item$` が前回の要素と比べるので、要素が変わった 100 行だけが DOM に書き込みます。Preact と React は新しい状態から表を再描画し、props が変わった `memo` の行だけが描画し直されます。
- **行の選択**では、Solid は `createSelector` のおかげで 2 行にしか触れず、Preact と React は `memo` の行を 2 つ再描画します。synstate-dom では各行が選択状態を `map` のノードを通して束縛しているので、1,000 個の `map` がすべて実行され、結果が変わった 2 行だけがそれを下流に流してクラスを切り替えます。Preact + Signals も同じように、行ごとの `useComputed` を再計算します。

## シナリオ

js-framework-benchmark では各行が自分のデータだけに依存しているので、ライブラリが変更をどんな順番で伝えるかはほとんど結果に効いてきません。そこで、少数の入力からグラフを通して値を派生させる画面を用意しました。最初の 2 つでは、1 つの入力が長さの違う複数の経路を通って同じ値に届きます（diamond）。3 つ目では、ほとんどの変更が、前と同じ値になったところで止まります。どれもたくさんの値を計算して少しだけ表示するので、時間の大半は DOM ではなく伝播にかかります。

- **ローン**：30 年間、毎月返済するローンです。年ごとの行と、毎月の返済額・総利息・完済までの月数の要約を表示します。各月の利息は前月の残高から、返済元金は前月の残高とその利息から、新しい残高は前月の残高と返済元金から計算するので、360 か月分が diamond の連鎖になり、金利と返済額はすべての月に入ってきます。金利を変えるとすべての月が変わり、181 か月目に繰上返済すると連鎖の後半が、349 か月目に繰上返済すると最後の 1 年が変わります。
- **工程表**：1,000 個のタスクのクリティカルパスです。各タスクはそれより前の 1〜3 個のタスクに依存し、それぞれ所要日数を持っています。前進計算で各タスクの最早開始と最早終了を、プロジェクトの終わりからの後退計算で最遅開始を求め、その差が余裕日数になります。画面にはプロジェクトの終了日、クリティカルなタスクの数、最後の 50 タスクを表示します。最初のタスクを延ばすとほぼすべての値が変わりますが、中ほどのタスクを延ばした場合は周りのタスクの余裕日数が変化を吸収するので、変わる値は数十個で済みます。
- **ズーム**：地図上の 10,000 地点のラベルです。ズームは 0.1 刻みで設定します。ズームから整数の詳細度（段階）を求め、各ラベルの大きさは段階だけから計算します。各地点は自分の順位に応じた段階から表示され、段階が上がるごとに大きくなります。画面にはズーム、段階、表示中のラベル数、最初の 50 地点を表示します。同じ段階の中でズームしても段階の値は変わらないので、画面上のズームの表示だけが変わります。次の段階までズームすると、ほとんどのラベルが変わります。

### シナリオの読み方

- **まずは正しさです。** 各操作の後に、描画されたセルを単純なループで計算した値と比べ、違う値を描画したライブラリには時間の代わりに「誤り」と書いています。VanJS は派生 state をラウンド単位で再計算します。各ラウンドでは、前のラウンドで変わった state を読む派生をやり直し、100 ラウンドで打ち切ります。そのため、変更がそれより先まで連鎖をたどる必要があるときは、古い値が画面に残ってしまいます。synstate-dom、Solid、Preact + Signals は、1 回の変更につき各値を、それが依存する値がすべて決まった後に 1 回だけ計算します。
- **React と Preact にはグラフがありません。** 入力を 1 つの state に持ち、描画のたびにすべての値をループで計算します。なので、変更がどこまで届くかにかかわらず、1 回の変更で計算全体を 1 回なぞることになります。この規模ならそれでも十分安いので、グラフを使う実装が超えるべき基準としてここに並べています。
- **前と同じ値になったところで止まるかどうか。** Solid と Preact + Signals は、前と等しい値を先へ流しません。synstate の `map` も流しません。各値は `combine` + `map` で作っているので、中ほどのタスクを延ばしたり同じ段階の中でズームしたりしても、同じ値になったところで止まります。synstate-dom の 2 列目、すべての値の後に [`skipIfNoChange`](https://noshiro-pf.github.io/mono/synstate/ja/reference/skip-if-no-change/) を挟んだ版は、`map` がそこで止まるようになる前に足したものです。今は同じところで止まり、値ごとのノードが 3 つになる分だけ構築が遅くなります。
- **止まることがどれだけ効くかは、変更にどう気づくかで決まります。** Solid と Preact + Signals では、書き込みがまず下流のすべてに「古いかもしれない」という印を付け、その後で各値を元の値と照らし合わせます。そのため、段階のところで止まる変更でも 10,000 個のラベルをすべて訪れます。synstate は値を流したノードの子しか訪れないので、同じ段階の中でのズームは、その下にある地図がどれだけ大きくても同じ時間で済みます。VanJS も、すでに持っている値を代入された state は伝播しないので、そこで止まります。React と Preact はラベルを段階に依存する `useMemo` に持っていて、51 行を描画し直します。

ここでの変更は 1 回あたり 1 ms をかなり下回ります。そのためシナリオでは、ブラウザが 4 ms に丸めてしまう `setTimeout` ではなく `MessageChannel` で次のタスクを待ち、操作とその逆を交互に行う 20 回の変更の平均を 1 サンプルとしています。

## 計測しているもの

js-framework-benchmark の操作では、どの実装も同じ表をマウントします。要素ごとに 1 行で、要素の id とラベルを 2 つのセルに置き、選択中の行に `danger` クラスを付けます。計測の前に、同じ操作をした後にすべての実装が同じ行を描画することを確かめています。

各操作は、呼び出してからマクロタスクが 1 つ過ぎ、ブラウザが表をレイアウトし直すまでを計ります。VanJS と Preact は変更をマイクロタスクで描画するので、この待ちを入れています。待ちはすべての実装が同じように払うので、どの値もほぼ同じだけずれます。

ライブラリは本番ビルド（`mode: 'production'` と `production` の export 条件）と本番用の JSX ランタイムを使い、Vitest のブラウザモードのヘッドレス Chromium で動かしています。

## 各実装の書き方

どの実装も、そのライブラリ自身のドキュメントか、js-framework-benchmark のエントリーがこういう表を書くときのやり方に従っています。

- **synstate-dom**：行は `createState` の中の 1 つのイミュータブルな配列で、`For` が各行の値をそこから派生させます。選択状態は、各行が `pipe(map(...))` で束縛する state で、変換した値の束縛はどれもこの書き方です。ドキュメントでおすすめしている書き方そのままで、チューニングはしていません。
- **Solid**：ラベルごとの signal、行オブジェクトに対する `For`、選択には `createSelector` を使うので、選択で触れるのは 2 行だけです。`vite-plugin-solid` でコンパイルします。
- **Preact + Signals**：ラベルごとの signal と、行ごとに `useComputed` で求めるクラスを、どちらも signal として DOM に束縛します。リストはキー付きで再描画します。
- **Preact** と **React**：行と選択状態を、トップの `useState` で 1 つのイミュータブルな状態として持ちます。各行は、ラベルと選択中かどうかを受け取る `memo` コンポーネントです。React は変更ごとに `flushSync` で描画し、Preact はマイクロタスクで描画します。
- **VanJS**：ラベルごとの state と、行ごとのクラス関数を使います。リストは手で管理し、行の要素を直接移動・削除します。

## 実行する

CI では実行していません。共有のランナーで計った時間にはあまり意味がなく、結果をアサートするベンチマークは不安定になるだけだからです。同じマシンでも 1 回ごとに 10〜30% ばらつくので、ここの数値は複数回の中央値を取る `benchmark:repeat` で計ったものです。

```sh
pnpm run ws:build            # synstate-dom と synstate は dist/ から import します
cd apps/synstate-dom-benchmark
pnpm run benchmark:repeat    # 5 回の中央値を取って RESULTS.md を書き直します
cd ../synstate-dom-docs
pnpm run gen:benchmark       # RESULTS.md をこのページに埋め込みます
```
