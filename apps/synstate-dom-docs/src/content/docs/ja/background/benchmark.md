[`apps/synstate-dom-benchmark`](https://github.com/noshiro-pf/mono/tree/main/apps/synstate-dom-benchmark) は、[js-framework-benchmark](https://github.com/krausest/js-framework-benchmark) の操作（表の行の作成・置き換え・部分更新・選択・入れ替え・削除・追加・全消去）で synstate-dom を Solid、Preact + Signals、Preact、React、VanJS と比べる。値どうしが長さの違う diamond でつながる 2 つの[シナリオ](#シナリオ)でも比べる。

以下の数値はその [`RESULTS.md`](https://github.com/noshiro-pf/mono/blob/main/apps/synstate-dom-benchmark/RESULTS.md) から埋め込んだもので、1 台のマシンでの計測である。この計測の中で実装を互いに比べるためのもので、js-framework-benchmark が公開している表とは比べられない。

## 結果の読み方

この計測では、synstate-dom は操作によって Solid の <!-- benchmark:reference-min -->1.10<!-- /benchmark --> 倍から <!-- benchmark:reference-max -->1.36<!-- /benchmark --> 倍の時間がかかった。どの操作でも最速ではない。ほかのライブラリより速い操作と遅い操作は上の表にある。

- **行の作成**は、コンパイラがないことが最も表れるところである。Solid は行ごとにコンパイル済みの `<template>` を複製する。synstate-dom はノードごとに `createElement` を呼び、動的な葉をそれぞれ購読で束縛する。行ごとに要素のための synstate のノードも作り（位置を受け取る行ではもう 1 つ作るが、この表は受け取らない。[制御構文](/mono/synstate-dom/ja/guides/control-flow/#for)の `For` を参照）、行の作成と破棄の時間はノード数にほぼ比例して増える。
- **部分更新**は実装によって経路が違う。Solid・Preact + Signals・VanJS はラベルごとに signal を持ち、変わる 100 個に書き込む。synstate-dom はドキュメントが勧めるとおり配列全体を置き換え、各行の `item$` が前回の要素と比べて、要素が変わった 100 行だけが DOM に書き込む。Preact と React は新しい状態から表を再描画し、props が変わった `memo` の行だけが描画し直される。
- **行の選択**は、Solid では `createSelector` によって 2 行だけに触れ、Preact と React では `memo` の行 2 つを再描画する。synstate-dom では各行が選択状態を `view` で束縛しているので 1,000 個の `view` がすべて実行され、各行のクラスが切り替えられる。Preact + Signals も同様に行ごとの `useComputed` を再計算する。

## シナリオ

js-framework-benchmark では各行が自分のデータだけに依存するので、ライブラリが変更をどの順に伝えるかはほとんど効かない。下の 2 つのシナリオは、少数の入力からグラフを通して値を派生させる画面で、1 つの入力が長さの違う複数の経路で同じ値に届く（diamond）。どちらも多くの値を計算して少しだけ表示するので、時間の大半は DOM ではなく伝播にかかる。

- **ローン**: 30 年の毎月返済のローンで、年ごとの行と、毎月の返済額・総利息・完済までの月数の要約を表示する。各月の利息は前月の残高から、返済元金は前月の残高とその利息から、新しい残高は前月の残高と返済元金から計算するので、360 か月が diamond の連鎖になり、金利と返済額はすべての月に入る。金利の変更はすべての月を変え、181 か月目の繰上返済は連鎖の後半を、349 か月目の繰上返済は最後の 1 年を変える。
- **工程表**: 1,000 個のタスクのクリティカルパスで、各タスクはそれより前の 1〜3 個に依存し、所要日数をそれぞれ持つ。前進計算で各タスクの最早開始と最早終了を、プロジェクトの終わりからの後退計算で最遅開始を求め、その差が余裕日数になる。画面にはプロジェクトの終了日、クリティカルなタスクの数、最後の 50 タスクを表示する。最初のタスクを延ばすとほぼすべての値が変わり、中ほどのタスクを延ばすと、周りのタスクの余裕日数が変化を吸収するので、変わる値は数十個になる。

### シナリオの読み方

- **まず正しさ。** 各操作の後に、描画されたセルを単純なループで計算した値と比べ、違う値を描画したライブラリは時間の代わりに「誤り」とする。VanJS は派生 state を、前のラウンドで変わった state を読む派生をやり直すラウンドで再計算し、100 ラウンドで打ち切る。変更がそれより先まで連鎖をたどる必要があるときは、古い値が画面に残る。synstate-dom、Solid、Preact + Signals は、1 回の変更で各値を、それが依存する値がすべて決まった後に 1 回だけ計算する。
- **React と Preact にはグラフがない。** 入力を 1 つの state に持ち、描画のたびにすべての値をループで計算するので、変更がどこに届くかにかかわらず、1 回の変更で計算全体を 1 回なぞる。この規模ではそれは安く、グラフが超えるべき基準としてここで比べている。
- **同じ値になったところで止まるか。** Solid と Preact + Signals は、前と等しい値を先へ流さない。そのまま書いた synstate-dom は流す。各値は `combine` + `map` で、`map` は計算したすべての値を流すので、中ほどのタスクを延ばすと、変わる値は少なくても下流をすべて計算し直す。そこで、すべての値の後に [`skipIfNoChange`](https://noshiro-pf.github.io/mono/synstate/ja/reference/skip-if-no-change/) を挟んだ形でも計る。こちらはそこで止まるが、値ごとのノードが 3 つになり、構築が遅くなる。

ここでの変更は 1 回 1 ms をかなり下回る。そのためシナリオでは、ブラウザが 4 ms に丸める `setTimeout` ではなく `MessageChannel` で次のタスクを待ち、1 サンプルを、操作とその逆を交互に行う 20 回の変更の平均とする。

## 計測しているもの

js-framework-benchmark の操作では、各実装は同じ表をマウントする。要素ごとに 1 行で、要素の id とラベルを 2 つのセルに置き、選択中の行に `danger` クラスを付ける。計測の前に、同じ操作の後にすべての実装が同じ行を描画することを確かめる。

各操作は、呼び出しからマクロタスクが 1 つ過ぎてブラウザが表をレイアウトし直すまでを計る。VanJS と Preact は変更をマイクロタスクで描画するので、この待ちを入れている。待ちはすべての実装が払うので、どの値もほぼ同じだけずれる。

ライブラリは本番ビルド（`mode: 'production'` と `production` の export 条件）と本番用の JSX ランタイムで、Vitest のブラウザモードのヘッドレス Chromium で動かす。

## 各実装の書き方

それぞれ、自身のドキュメントか js-framework-benchmark のエントリーがこのような表を書くやり方に従う。

- **synstate-dom**: 行は `createState` の中の 1 つのイミュータブルな配列で、`For` が各行の値をそこから派生させる。選択状態は各行が `view` で束縛する state である。ドキュメントが勧める書き方で、チューニングしたものではない。
- **Solid**: ラベルごとの signal、行オブジェクトに対する `For`、選択に `createSelector` を使い、選択で触れるのは 2 行になる。`vite-plugin-solid` でコンパイルする。
- **Preact + Signals**: ラベルごとの signal と行ごとの `useComputed` のクラスを、どちらも signal として DOM に束縛する。リストはキー付きで再描画する。
- **Preact** と **React**: 行と選択状態をトップの `useState` の 1 つのイミュータブルな状態に持ち、各行はラベルと選択中かどうかを受け取る `memo` コンポーネントである。React は変更ごとに `flushSync` で描画し、Preact はマイクロタスクで描画する。
- **VanJS**: ラベルごとの state と行ごとのクラス関数。リストは手で管理し、行の要素を直接移動・削除する。

## 実行する

CI では実行しない。共有のランナーでの時間はあまり意味がなく、アサートするベンチマークは不安定になるだけだからである。同じマシンでも 1 回ごとに 10〜30% ばらつくので、ここの数値は複数回の中央値を取る `benchmark:repeat` によるものである。

```sh
pnpm run ws:build            # synstate-dom と synstate は dist/ から import する
cd apps/synstate-dom-benchmark
pnpm run benchmark:repeat    # 5 回の中央値。RESULTS.md を書き直す
cd ../synstate-dom-docs
pnpm run gen:benchmark       # RESULTS.md をこのページに埋め込む
```
