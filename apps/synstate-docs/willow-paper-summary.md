## 一言まとめ

React 系の reactive フレームワークは「**何を**計算するか」は宣言的で明快だが、「**いつ**更新が起きて**どう伝播する**か」はフレームワークのランタイムに埋め込まれていて静的に読み取れない。本論文はレンダー（render）を時間の基本単位とするコア計算体系 **Willow** を提案し、状態変更・イベント登録・スケジュールされたイベントを **graded effect** として型に載せることで、従来ランタイム任せだったタイミング特性をコンパイル時に検査可能な人工物へ変える。推論されたエフェクトは**時間的依存グラフ（temporal dependency graph）**として解釈でき、標準的なグラフアルゴリズムでレンダーカスケード・レンダー間ループ・リスナーリークなどを静的に検出できる。

## 1. 問題設定

### 1.1 タイミング起因のバグ

reactive プログラムのタイミング仮定は暗黙的であり、以下のバグを生む。

- **stale read** — 更新が伝播し切る前の古い状態を読んでしまう（Cooper and Krishnamurthi 2006）
- **glitch** — 依存する値が別々のタイミングで更新されることによる一時的な不整合
- **order-dependence** — スケジューラの評価順序に結果が依存する（Kahn 1974）
- **delayed-effect violation** — 遅延実行やバッチングにより、プログラムの想定より後にエフェクトが発生する
- **意図しないフィードバックループ / レンダー間ループ** — 更新が互いを繰り返し発火させる

GUI は可能なイベント列・順序の組み合わせ爆発により以前からテストが難しいことが知られている（Memon 2002; Banerjee et al. 2013）。タイミング依存の挙動は、プログラムの依存構造とフレームワークの実行モデルの相互作用から創発するため、その中でも最も難しいケースである。

### 1.2 イベントハンドラのライフサイクル

第二の複雑性の源はイベントハンドラのライフサイクルそのもの。

- 状態変化に応じてハンドラを繰り返し破棄・再登録しなければならない
- 「どの状態変化がどのハンドラを無効化するか」の判断は完全にプログラマ任せ
- 古いハンドラの削除忘れはロジックバグ＋メモリリークを生む
- イベントの発火頻度は種類ごとに異なり、高頻度発火や意図しない二重入力を防御する必要がある

### 1.3 既存の React 形式化との違い

先行研究（Madsen et al. 2020 の λ_react、Lee et al. 2025 の React-tRace）は React ランタイムの挙動を忠実に再現するため、**タイミングは実行から創発する副産物**になる。Willow は逆に、レンダーとイベントの順序・遅延を**意味論のオブジェクト自体に明示的に埋め込む**設計を採る。結果として、React Compiler（Meta Platforms 2024）など既存ツールが見逃す性能欠陥を静的に検出できると主張する。

## 3. React の前提知識

コンポーネントは UI を返す関数であり、実行は**レンダーの列**である。各レンダーは現在の状態と入力から UI のスナップショットを計算し、フレームワークが前回結果と差分を取って最小の DOM 更新を適用する。レンダーは通常毎秒 60 回以上発生するため、1 レンダーの予算はおよそ 16 ms。

### setter

```js
const [x, setX] = useState(e);
```

状態はレンダー中は不変（immutable）で、更新はレンダー間にスケジュールされる。setter は通常 `τ → τ` の updater 関数を取るため、型は `(τ → τ) → unit` となる。1 レンダー中の複数回の setter 呼び出しはキューされ順次適用される。

例: レンダー開始時に `x = 3` で `setX(x => x + 1)` を 2 回呼ぶと、そのレンダー中 `x` は 3 のままで、次のレンダーが 5 を観測する。

### useEffect

```js
useEffect(() => {
  /* side effects */
  return () => { /* cleanup */ }
}, [x, y, z, ...])
```

依存配列の値がレンダー間で変化したときに本体が走る。本体は cleanup 関数を返せ、これは次回の再実行前に走る。論文は Khourshid の "Goodbye useEffect"（2022）を引きつつ、`useEffect` を宣言的パラダイムからの意図的な脱出口（escape hatch）と位置づける。

## 4. 動機づけの例

### 4.1 Moving Dot

クリック位置に点が追従し、チェックボックスで移動可否を制御する例。

React 版:

```jsx
export default function MovingDot() {
  const [position, setPosition] = useState({ x: 0, y: 0 });
  const [canMove, setCanMove] = useState(true);
  let handleClick = (e) => {
    setPosition(_ => ({ x: e.clientX, y: e.clientY }));
  };
  useEffect(() => {
    if (canMove) { document.addEventListener("click", handleClick); }
    return () => document.removeEventListener("click", handleClick);
  }, [canMove]);
  return (
    <div>
      <input type="checkbox" checked={canMove}
             onChange={(e) => setCanMove(_ => e.target.checked)} />
      <div style={{transform: `${position.x}, ${position.y}`}} ... />
    </div>
  );
}
```

このコードの正しさが依存している **3 つの時間的仮定**:

1. クリックハンドラ内の `setPosition` は**イベント中ではなく次のレンダーで**初めて効く
2. `canMove` が反転したとき、cleanup が古いリスナーを削除した**後で**本体が新規登録するか判断する（cleanup 忘れはロジック不整合＋リークになる）
3. 「いつクリックが実際に点を動かせるか」は、コードの字面ではなく **effect ブロックが最後に走った時点とそのときの `canMove`** に依存する

Willow 版:

```
comp MovingDot () : html {
  state position, setPosition default (0, 0);
  state canMove, setCanMove default true;
  let handleClick = λe. setPosition(λ_. (e.clientX, e.clientY));
  on canMove do {
    remove click⟨#doc⟩;
    if canMove then (bind click⟨#doc⟩ handleClick) else ()
  };
  return ( ... /* same html as in React */ );
}
```

React 版との差分:

- state 宣言は初期値を明示（`default (0, 0)`）
- アロー関数の代わりに λ 式
- `useEffect` は **on ブロック**（`on canMove do { ... }`）になり、監視変数が変化したときに発火する
- on ブロックは cleanup を**先頭**で行う（この例では `remove` が最初）
- 条件付き登録が `handleClick` 内のチェックではなく **on ブロック本体**に移動している

推論されるエフェクト:

| 項                             | エフェクト                                           |
| ------------------------------ | ---------------------------------------------------- |
| `bind click⟨#doc⟩ handleClick` | □^click⟨#doc⟩(○^1r @position)                        |
| `remove click⟨#doc⟩`           | ✗ click⟨#doc⟩                                        |
| on ブロック本体                | ✗click⟨#doc⟩ ∗ (□^click⟨#doc⟩(○^1r @position) + (·)) |
| `onChange`                     | ○^1r @canMove                                        |

先の 3 つの仮定がそれぞれエフェクトの構文に対応する:

1. `○^1r @position` — `position` は次のレンダーで変わりうる
2. 登録の**前**に `✗click⟨#doc⟩` があることが、古いハンドラが必ず掃除されることを示す
3. `+ (·)` の分岐が、登録が条件付きであることを示す

### 4.2 Debounce

高頻度で変化する `value` から、100 ms 静止後にだけ更新される `slow` を導出し、下流の高コスト処理を保護する。

```
comp Debounce (value: any) : any {
  state slow, setSlow default value;
  on value do { clearTimeout(); setTimeout(λ_. setSlow(λ_. value)) };
  return slow;
}
```

組み込みの型:

- `setTimeout f` : ◇^timeout⟨⟩(F_f) ∗ ○^100ms timeout⟨⟩
- `clearTimeout()` : ⊘ timeout⟨⟩ ∗ ✗ timeout⟨⟩

`value` の変化がもたらす合成カスケードエフェクト:

```
⊘timeout⟨⟩ ∗ ✗timeout⟨⟩ ∗ ◇^timeout⟨⟩(○^1r @slow) ∗ ○^100ms timeout⟨⟩
```

読み方: 保留中の timeout はキャンセルされハンドラも解除される。新しい timeout が 100 ms 後にスケジュールされる。それが発火することを条件に、`slow` が次のレンダーで変わりうる。

**合成性の効用**: 親が `comp slowInput = Debounce(input); on slowInput do { fetch(...) };` とすると、`input` のエフェクトは先頭に `◇^timeout⟨⟩(○^1r(○^1n F))` を持つ。つまり「ネットワーク呼び出しが debounce タイマーの背後にある」ことが型に見える。逆に **debounce が抜けていれば先頭の ◇ が欠落する**ため、事後解析でフラグを立てられる。

### 4.3 相互再帰（ループ検出）

```
comp MutualRecursion (clock: int) : unit {
  state x, setX default 0;
  state y, setY default 0;
  on x do { setY addOne };
  on y do { setX addOne };
  return ();
}
```

グラフのエッジは `@x —1r→ @y` と `@y —1r→ @x`。`x` の変化がもたらす完全エフェクトは無限交替鎖になり、Willow はこれをコンパイル時に検出する。

## 5. 構文（§3）

**コンポーネント**: `comp A (x₁:τ₁, …, xₙ:τₙ) : τ { p₁ p₂ … pₙ return x }`。最後に宣言されたコンポーネントがトップレベル。

**宣言 p**:

| 形                         | 意味                                                        |
| -------------------------- | ----------------------------------------------------------- |
| `let x = e;`               | 純粋な let 束縛                                             |
| `state x, setX default e;` | 状態変数と setter を束縛（初期値必須）                      |
| `on x₁,…,xₙ do { e };`     | effect ブロック。監視変数が前レンダーと異なるとき本体が走る |
| `comp x = A(x₁,…,xₙ);`     | サブコンポーネントのインスタンス化。戻り値を `x` に束縛     |

**式 e**: 変数、定数（`true`/`false`/`()`）、適用 `e₁ e₂`、逐次 `e₁; e₂`、`λx.e`、`if x then e₁ else e₂`（**分岐条件は変数のみ**）、対 `(e₁,e₂)` と `fst`/`snd`、そしてイベントプリミティブ `bind ℓ⟨v̄⟩ e` / `once ℓ⟨v̄⟩ e` / `cancel ℓ⟨v̄⟩` / `remove ℓ⟨v̄⟩`。

- `bind` — 毎回発火する永続リスナーを登録
- `once` — 最大 1 回発火するワンショットリスナーを登録
- `cancel` — 保留中の発火 1 件を抑止
- `remove` — そのラベルの全リスナーを解除

**イベントラベル**は `ℓ⟨v̄⟩` の形。`ℓ` はイベント種（`click`, `timeout`, `req`）、`v̄` は「どのインスタンスか」を識別する**静的に既知**な基本値のタプル（`#doc`、URL など）。生成されたばかりのタイマー ID のような動的な値はエフェクト層に入れられないため、`timeout⟨⟩` は空タプルを持つ。

## 6. 意味論（§4）

### 設計方針

Willow は意図的に環境非依存で、レンダー出力がその後どう扱われるかは形式化せず、周囲のランタイムが処理すると仮定する。キャッシュ・メモ化は React Compiler が手動最適化の必要性を減らしたことを根拠に省略する。JavaScript の microtask/task キューの交錯と React の priority lane スケジューラは予測困難だとして、Willow はより具体的な実行順序を採る。

### 2 フェーズのループ

1. **レンダーフェーズ** — プログラマのコードが実行され、イベントキューが構築される。状態変数は読み取り専用。
2. **housekeeping フェーズ** — 外部スケジューラとイベントキューがフラッシュされ、状態が更新される。

Willow の内部イベントキューは、setter クロージャ、イベントプリミティブ操作（`bind`/`once`/`cancel`/`remove`）、イベント発火 `ℓ⟨v̄⟩` を保持する。外部イベントは**外部スケジューラ ℰ**（制御外のキュー、レンダーごとに housekeeping 開始時に 1 回フラッシュ）経由で入る。

### 意味論オブジェクト

コンポーネント判断: `Σ; ℒ; V_e; V_s; 𝒞 ⊢ comp C(x̄=v̄) : τ { p } ⇓ s ∣ U`

| 記号 | 役割                                                                                   |
| ---- | -------------------------------------------------------------------------------------- |
| Σ    | プログラムシグネチャ。コンポーネント名 → (コード, Δ, Γ)                                |
| ℒ    | リスナーマップ。イベントラベル → 登録済みリスナー（□ 永続 / ◇ ワンショットのタグ付き） |
| V_e  | 前レンダー終了時点の値環境のスナップショット（凍結）                                   |
| V_s  | 状態変数環境。V_e から初期化され、housekeeping 中に setter で変更される                |
| 𝒞    | キャンセル多重集合。保留 cancel ごとに 1 エントリ、次回ディスパッチを抑止              |
| s    | ステータス。`rendered`（キュー処理中）/ `waiting`（housekeeping 完了）                 |
| U    | イベント／更新キュー                                                                   |

宣言判断: `Σ; [V_e ∣ V_s]; V; c ⊢ p ⇓ v; U; V′`、式判断: `Σ; V ⊢ e ⇓ v; U`。

**環境の役割**: レンダー中は V_e/V_s は読み取り専用、housekeeping 中に書き込まれる。on ブロックの発火判定は V_e と V の束縛変数の比較で行う。

**コンポーネントパス**: 同一コンポーネントが複数インスタンス化されうるため、各状態セルにグローバル一意キーが必要。パス `c` は `.` 区切り（先頭ドットなし）。トップレベルでは `c.x = x`、親のパス `c′` の下で `y` に束縛されたサブコンポーネント内では `c.x = c′.y.x`。setter に付随するパスが V_s/V_e の探索キーそのものになる。

### 主要な規則

- **flush first update** — setter イベント `setter_y(⦇λy.e, V⦈)` をポップ。setter はエフェクトを持てないため、クロージャ実行前に環境から全 setter を除去（`removeSetters`）する。結果が V_s における `y` の新値となり、V_e と異なれば次レンダーで `y` の束縛エフェクトが発火する。
- **flush external events** — `ℰ ⇒_ext U_ℰ` で外部発火を Willow のキューへ移す。U_ℰ は `(ℓ⟨v̄₁⟩, v₂)` の対の列（例: `(click[doc], (100,200))`）。
- **pop listen** — `bind`/`once` は即時登録せず `listen(ℓ⟨v̄₂⟩, c, m)` をキューに入れる（`m ∈ {□, ◇}`）。ポップ時に ℒ の順序付き集合へ `(c,m)` を追加。
- **pop event** — 発火 `(ℓ⟨v̄₁⟩, v₂)` について、`𝒞(ℓ⟨v̄₁⟩) = 0`（未キャンセル）を要求し、全リスナーを `v₂` を引数に実行。各リスナーが生成したキューは **listener-safe**（`⊢ Uᵢ lsafe`、ハンドラは新たなラベル付きイベント発火をキューに出せない）でなければならない。実行後、ℒ には □ タグのリスナーのみ残る。
- **waiting to rendered** — キューが空になるとステータスは `waiting`。新しいトップレベル引数が届き、かつ少なくとも 1 引数が変化していれば（`∃i. vᵢ ≠ v′ᵢ`）新レンダーが始まる。このとき前レンダーの最終環境 V′ が新しい V_e **かつ** V_s になる。
- **state rerender** — 再レンダー時は default 式を無視（初回レンダーのブートストラップ専用）。V には V*s 由来の `x = v₀` と `setX = setter*{c.x}` が入る。setter は型システムからは通常の関数に見えるが、意味論上は状態へのグローバルパスを運ぶダミー値であり、これがレンダー間の橋渡しになる。
- **effect rerender** — 監視変数が全て V_e と一致すれば宣言はスキップ。`∃i. vᵢ ≠ v′ᵢ` なら本体を評価し、戻り値は捨ててキュー U をグローバルキューへ追加。**on ブロックだけが副作用を持つ関数を呼べる唯一の宣言**。
- **subcomp** — (1) Σ から p_A を取得、(2) キーが `"y."` で始まるエントリを選び接頭辞を剥がして V_e′/V_s′ を作る、(3) それらと引数の作業環境の下で p_A を評価、(4) 結果 V_y′ に `"y."` を付け直して V_y″ を得る、(5) `y` を戻り値 v_A に束縛して親の残り宣言を評価、(6) サブコンポーネントのキュー U_y を親の U の**前**に置き、V_y″ を V′ に合併して状態を永続化。
- **setter app** — 引数がクロージャに評価されることを要求するが実行はせず、`setter_x(⦇λy.e₃,V′⦈)` をキューに追加してレンダー間適用に回す。

## 7. 型・エフェクトシステム（§5）

### 文法

```
τ ::= unit | bool | τ₁ × τ₂ | (τ₁ → τ₂ ∣ F)          -- 矢印が latent effect を持つ
F ::= · | @x | ℓ⟨v̄⟩ | ○^{Nu} F | F₁ ∗ F₂ | F₁ + F₂
    | ◇^{ℓ⟨v̄⟩}(F) | □^{ℓ⟨v̄⟩}(F) | ⊘ ℓ⟨v̄⟩ | ✗ ℓ⟨v̄⟩
u ::= r | n | ms | …                                  -- 時間単位
```

### 各構成子の意味

| 構成子        | 意味                                                                   |
| ------------- | ---------------------------------------------------------------------- |
| `·`           | 空エフェクト                                                           |
| `@x`          | 状態変更エフェクト。`x` の setter が呼ばれ、`x` が変わりうる           |
| `ℓ⟨v̄⟩`        | イベントエフェクト（キー入力、マウス移動、ネットワークリクエスト等）   |
| `○^{Nu} F`    | **時間的 next モダリティ**。タイミング解析の主役。`N` は時間単位の個数 |
| `□^{ℓ⟨v̄⟩}(F)` | 「always」。永続登録。「イベントが発火するたびに F が起こる」          |
| `◇^{ℓ⟨v̄⟩}(F)` | 「eventually」。ワンショット登録。発火を条件に F が 1 回起こる         |
| `⊘ ℓ⟨v̄⟩`      | 保留中の発火 1 件をキャンセル                                          |
| `✗ ℓ⟨v̄⟩`      | そのイベントの全リスナーを削除                                         |
| `F₁ ∗ F₂`     | 逐次。左が先にキューされるため **∗ は一般に可換でない**                |
| `F₁ + F₂`     | 分岐。どちらかが起こりうる                                             |

`○` の構文は時相論理の next 演算子（Pnueli 1977）に基づく。単位にはレンダー（r）、ネットワークリクエスト（n）、ミリ秒（ms）、およびホストが導入する任意の単位が含まれる。

`⊘`/`✗` は `□`/`◇` と「釣り合う」ことで、古いハンドラがレンダーを越えて生き残らないことを保証する。この 2 層（レンダー数 vs イベントラベル）は `□^e(○^1r @x)`（外部イベント e を条件に、次のレンダーで x が変わりうる）のようなエフェクトで交わる。

**setter の型**: `(τ → τ ∣ ·) → unit ∣ ○^1r @x`。内側の updater は空エフェクト（`x` の setter は `x` しか更新できない）。

**エフェクトの移動**: 判断は `Γ ⊢ e : τ ∣ F`。式が関数本体として包まれるとエフェクトは型に取り込まれ（latent になり）、呼び出しで解放される。エフェクトがシステムに入る経路は組み込みの注釈のみ（setter、ネットワーク呼び出し、`bind`/`once`/`cancel`/`remove`）。

### 単位演算と入れ子

同一単位のみ結合する: `○^1r(○^1r F) = ○^2r F`。単位は意図的に非互換で、相互変換されない（ネットワークリクエストは追加レンダーより高コストであり、ミリ秒は体感応答性に効くが性能上の含意を持たない場合がある）。

入れ子は時間の逐次化を表す: `○^1r(○^1n F)` は「次のレンダーでリクエストを開始し、その返却後に F」。逐次と分岐は共有の「時刻ゼロ」を基準に子を配置する: `(○^1r F₁ ∗ ○^1n F₂)` では F₁ は次レンダー、F₂ はリクエスト解決後。`(○^1r F₁ ∗ ○^1r F₂)` は `○^1r(F₁ ∗ F₂)` に簡約される。新単位は組み込みから導入されるが、ライブラリ API の可読性のためにプログラマが型エイリアスで自前の単位を作ることも想定されている。

### エフェクト多相の例

`asyncCompute` は成功／失敗コールバックを取り、即座に unit を返し、計算時間 1 単位後にどちらかが起こる。型（`∀F1,F2`）:

```
○^{1u}(comp[suc] + comp[err])
  ∗ ◇^{comp[suc]}(F1 ∗ ✗comp[err])
  ∗ ◇^{comp[err]}(F2 ∗ ✗comp[suc])
```

この 1 つの型から読み取れること: (1) 各イベントがいつ起こりうるか、(2) 全イベントが処理されていること、(3) 全ハンドラが掃除されること。呼び出し時に 2 つのワンショット登録がキューされ、発火した側がコールバックを実行して他方のハンドラを削除する。

### 3 種類のエフェクト

| 種類          | 内容                                                                 |
| ------------- | -------------------------------------------------------------------- |
| **immediate** | 関数自身の latent 副作用                                             |
| **cascading** | ある変数が変化したときに、監視している on ブロックが行うこと         |
| **full**      | 1 つの変更またはイベント発火から推移的に引き起こされうる全エフェクト |

**cascading**: `on x do { setY addOne };` は `x` のカスケードに `○^1r @y` を寄与する（x 変化 → 次レンダーでブロック発火 → setter がキュー → さらに 1 レンダー後に y が変わりうる）。カスケードは Δ 内で依存関係の隣に `x[deps] ∣ cascade` の形で保持される。状態変数は依存を持たず、let 束縛変数は持つ。依存はパラメータ化されたデータフロー関数 `df(e)`（`e` の値を変えうる変数を返す）から得られ、最も単純な具体化は自由変数集合。

**full**: 型検査**後**に Δ 上のグラフ展開（訪問済みノード追跡付き）で復元する。例: `x[] ∣ ○^1r@z`、`y[z] ∣ ·`、`z[] ∣ ○^1r@x` のとき、`x` の完全エフェクトは

```
○^1r(@z ∗ @y ∗ ○^1r loop[x])
```

`loop[x]` は展開が `x` を再訪した箇所を示す。reactive パラダイムではカスケードの循環は通常バグなので、ループは隠さず**表面化**させる。

**エフェクトサマリ**: 子サブコンポーネントのスコープに対応する状態変更エフェクトを隠すことで可読性を上げられる。`"y."` 接頭辞で始まる全変数を隠し、next モダリティの指数を畳み込む（`○^1r○^1r F` → `○^2r F`）。

### サブエフェクト

`F ≤ F′` で F′ が「より情報量が多い／確定的な」側。

- **`+` は meet として振る舞う**: `F₁ + F₂ ≤ Fᵢ`（分岐の過大近似はどちらの側にも置き換えられる）
- **`∗` は join として振る舞う**: F がいずれかの側を精緻化するなら `F ≤ F₁ ∗ F₂`
- **`○^N` は単調**で、`○⁰F = F`、`○^{N₁}○^{N₂} = ○^{N₁+N₂}`（graded monad 則）
- 空エフェクトは `@x`、`ℓ⟨v̄⟩`、イベント保護構成子の下に位置する。`□`/`◇` の本体は単調

preservation により完全エフェクトは「正直」になる。すなわち、well-typed なプログラムが 1 ステップ進んだ後も、サブエフェクト関係の下で元のエフェクトに抑えられるエフェクトで型付けされる ⇒ **コンパイル時の完全エフェクトは実行を過大近似する**。

### 宣言レベルの型付け（§5.1）

判断: `Σ; Δ; Γ₁ ⊢ p ⇒ Γ₂`。Δ は現コンポーネントのエフェクト環境（変数 → `x[deps] ∣ cascade`）。Δ は**与えられたものとして扱われ**、規則はプログラムのエフェクトが Δ のエントリのサブエフェクトであることを検査する。Δ の候補を見つける難所は**最小のカスケードエフェクト**を見つけることであり、プロトタイプはこれをプログラム的に復元する。

**因果判断** `Δ ⊢ @x ⇒ F`（「Δ の下で、x の変化は F を引き起こすのに十分」）:

- _(x causes F)_ — 基底: `x[…] ∣ F′ ∈ Δ` かつ `F ≤ F′`
- _(x causes y)_ — 依存: `y[…, x, …] ∣ F′ ∈ Δ` ならば `Δ ⊢ @x ⇒ @y`（x の変化は y の再計算を強制し、それ自体が状態変更相当）

主な規則:

| 規則            | 内容                                                                                                                              |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| ty state decl   | `Γ ⊢ e : τ ∣ ·`（default は純粋）、`x[] ∣ F ∈ Δ`（依存なし）を要求し、Γ に `x:τ` と `setX : ((τ→τ ∣ ·) → unit ∣ ○^1r @x)` を追加  |
| ty let decl     | 純粋な e を要求、`ȳ = df(e)` を計算、`x[ȳ] ∣ F ∈ Δ` を要求、Γ に `x:τ` を追加                                                     |
| ty on decl      | `Γ ⊢ e : unit ∣ F` と `∀i ∈ [n], Δ ⊢ @xᵢ ⇒ F` を要求。Γ は不変                                                                    |
| ty subcomp decl | 接頭辞付けで親子のエフェクト／型環境を関係づける。`Δ ⊢ @xᵢ ⇒ @y.zᵢ`、`Δ ⊢ @y.return ⇒ @y`、包含条件 `Δ_A[y.v_Δᵢ / v_Δᵢ] ⊆ Δ` など |

式レベルの規則は概ね標準的。

- **app**: `Γ ⊢ e₁ : (τ₁→τ₂ ∣ F) ∣ F₁`、`Γ ⊢ e₂ : τ₁ ∣ F₂` から `Γ ⊢ e₁ e₂ : τ₂ ∣ F₁ ∗ F₂ ∗ F`（関数評価 → 引数評価 → latent effect の 3 つを逐次）
- **fn**: `Γ, x:τ₁ ⊢ e : τ₂ ∣ F` から `Γ ⊢ λx.e : (τ₁→τ₂ ∣ F) ∣ ·`（本体のエフェクトが矢印に移り、クロージャ式自体は純粋）

## 8. 時間的依存グラフと事後解析（§5.4）

### グラフの構成

型付け規則は**単一レンダー**内の依存を捉える。時間的依存グラフはこれを**複数レンダー**に持ち上げる仕組みである。

- **ノード** = 各エフェクト（状態変更の候補）
- **エッジ** = エフェクト環境から導出。依存配列を入辺、カスケードエフェクトを出辺として見る
- **重み** = next / eventually / always モダリティ上のタイミング・イベント注釈

完全エフェクトは単純なグラフ展開で復元する: ノード `n` が自身の展開の子孫になったら `loop[n]` ノードを置いてそれ以上展開しない。論文は使用するアルゴリズムを一貫して「既存の（off-the-shelf）標準的なグラフアルゴリズム」と述べ、**特定のアルゴリズム名（Tarjan など）は挙げていない**。

### 5 つの解析

1. **長いレンダーカスケードの検出** — 1 イベントが多数の逐次レンダーを駆動し性能を劣化させる
2. **レンダー間ループのフラグ立て** — 更新が互いを繰り返し発火（非停止／性能劣化）
3. **高頻度イベントに高コストハンドラが結び付いた場合の警告**
4. **古いイベントハンドラが常に掃除されることの確認**
5. **アプリ初回レンダーのタイミング解析**

Debounce の議論から 6 番目の実用的用途も導かれる: 型の先頭に `◇` が**無い**ことが未保護の下流呼び出しを露呈するため、**debounce の抜け**を検出できる。

#### レンダー間ループの深層

`on x do setY …; on y do setX …` のような単純なケースだけが問題ではない。effect ブロックが存在する理由は**外部状態との同期**であり、そこは宣言的 reactive プログラムが異なるパラダイムのプログラムと接する境界である。effect ブロックが取得か送出の**片方向**のみを担うなら問題ない。バグはクライアント・サーバ間で**双方向同期**が起きるときに生じる。

例: クライアント側でユーザーデータを最新に保つ単純なケース。ユーザーデータは現在のアプリからも、別インスタンスの同一アプリから外部的にも更新されうる。そのため WebSocket でユーザープロファイル更新を購読して先回りで反映するのが一般的なパターンになる。だがこのソケットはクライアント側データのみを更新すべきである。クライアント側での受信がサーバ側への push を引き起こすと、クライアントはその push を自分自身が受け返すかを制御できなくなり、ループが形成されうる。Willow では外部 API に時間的エフェクトを与えられるため、ループ検出がこうしたケースを捕捉できる。

#### イベント検査解析

イベント種ごとに時間分布は異なる。キー入力は短いバースト、マウス移動は頻繁かつ継続的、ネットワークリクエストは 1 回だけ解決する。この分布を知っていれば、性能集約的なハンドラがキーイベントに置かれた場合に警告できる。

#### ハンドラ掃除の確認

変数の完全エフェクトが与えられれば、そのエフェクトのグラフを歩いて全イベントハンドラが対応する remove モダリティで整合しているか確認できる。これには `+` 構成子の**両分岐を別々に**歩き、`□`/`◇` モダリティの**内側も見る**ことが含まれる。単純なグラフ walk で `asyncCompute` の例を再訪すると、関数実行後にイベントハンドラが残らないことが確認できる。

#### 初回レンダー解析

初回レンダーはユーザーが体感するプログラム挙動の一部であり、初期描画は体感性能を支配する。Google の Core Web Vitals は Largest Contentful Paint を第一級の Web 性能指標として成文化している（Google 2020）。

コンポーネントの初回レンダーは**全変数が「変化した」とみなされる**ケースであり、全 effect ブロックが発火する。つまり、いくつかの状態がまだ初期値を持たない時点で全プログラムロジックが評価される。初期レンダー時点でアプリはサーバから最新データを取得する時間もなく、ローカルキャッシュから引く余裕さえない。音声／動画の再生やマイク／カメラの利用許可も（以前に付与されていたかどうかに関わらず）まだ確立していない。したがって初期レンダーは、アプリのライフサイクル中で**最も多くの非同期計算を、完全に未充填の状態で**開始する。プログラマは通常プログラムを定常状態の文脈で読むため、これは難しい思考の切り替えを要する。Willow の型システムは、初回描画のタイミングを定常状態の挙動と切り離して静的に理解させられる。

## 9. メタ理論（§6）

preservation の主要な保証は次のように要約される。

> 「変数が変化したとき、Δ に与えられたそのカスケードのサブエフェクトが次の housekeeping フェーズに現れる」

証明には **instrumented semantics** を用いる。これは有用な副条件で拡張され、単一の更新キューではなく**トレース付き更新キュー**を採用する。トレースの主な機能は、イベントキューをそれを引き起こしたエフェクトと**結合**することである。Δ が `x[y] ∣ F` を持つとき、preservation は「x が変化したなら y が変化していたはずである」ことを教える。

言語の主な拡張は、`bind`/`once` 式にリスナーのエフェクト注釈を要求すること。この情報は型付けで既に得られているので、instrumented semantics でも要求するだけでよい。これによりリスナーマップはイベントラベルから **`(c,m,F)`**（クロージャ、モダリティ、型システムが決定したエフェクト F）への写像に拡張される。

### トレースを構成するレコード

| レコード                                         | 意味                                                                                                                                                                   |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ARG x̄ = v̄₁ → v̄₂`                                | main コンポーネントの引数がこのレンダーで変化したことを記録                                                                                                            |
| `LET (x) ← { ȳ }`                                | let 束縛が影響を受ける変数を記録                                                                                                                                       |
| `EFF (x̄) → { U }`                                | 変数 x̄ がレンダー間で変化し、イベントキュー U がグローバルキューに追加されるべきことを記録                                                                             |
| `RET x`                                          | 変数 x がコンポーネントから返されたことを記録                                                                                                                          |
| `EXT (ℓ₁⟨v̄₁₁⟩, v₂₁),…`                           | スケジューラ ℰ からの外部イベント発火バッチの受信を記録し、続くイベントごとの処理レコードのブロックを区切る                                                            |
| `FIRE (ℓ⟨v̄₁⟩, v₂)`                               | イベント発火を記録                                                                                                                                                     |
| `FIRE-CXL (ℓ⟨v̄₁⟩, v₂)`                           | キャンセルされた発火を記録                                                                                                                                             |
| `FIRE-SUC (ℓ⟨v̄₁⟩, v₂) → { (U₁,F₁),…,(U_k,F_k) }` | 成功した発火と、各リスナーが生成したキュー U_i とそのエフェクト F_i の対応を記録（事後の完全エフェクト解析が登録済みエフェクトを操作トレースを通して追跡するのに使う） |

### well-typed configuration

```
⟨Σ; Δ; Γ_s ∣∣ 𝒮 ∣ A ∣ x̄=v̄ ∣ status ∣ T₁ ∣ T₂⟩
```

- `Γ_s` — main コンポーネントが型検査から返した型環境全体
- `𝒮 = (X₁, X₂, V_s, ℒ, 𝒞)` — `X₁`/`X₂` はそれぞれ「前レンダー以前」「直近レンダー」の housekeeping フェーズ中に変更された変数集合
- `A` — main コンポーネント名、`status` は `waiting` または `rendered`
- `T₁` — 直近レンダーが生成したトレースの**処理済み**部分、`T₂` は**未処理**部分

### Theorem 6.1（Preservation for Configurations）

well-typed なプログラムが main コンポーネント A を持つとき、housekeeping フェーズの 1 ステップ後に、

1. エフェクト環境と「前 housekeeping フェーズで変更された状態／引数の集合」が、直近レンダーが生成したトレースを**説明する**
2. トレースの既処理部分が、次レンダーに向けて「変化した」と印付けられた各変数を**説明する**

補助判断:

| 判断                             | 意味                                                                                                                                                                              |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `(Δ, X) ≻ T₁, T₂`                | **トレース正当化**。トレースの各エントリについて、それを正当化する X 内の変数と Δ 内のエフェクトが存在する。すなわち T₁,T₂ は型・エフェクトシステムが許すエフェクトのみを反映する |
| `(Δ, X) ≻ T₁ ≻ X′`               | **トレース駆動の変数変化集合**。Δ,X が T₁ を正当化するだけでなく、三者が合わせて「次レンダーに向けて変化と印付けられた各変数」を正当化できる                                      |
| `Σ; Γ ⊨_t V`                     | **値の well-typedness**。V の全変数-値対応が Γ の変数-型対応の下で well-typed                                                                                                     |
| リスナーマップの整合性           | マップ内のクロージャが矢印型 `Σ_E(ℓ⟨v̄⟩) → unit ∣ F` の下で well-typed。引数型は束縛先イベントが運ぶ型でなければならない                                                           |
| in-flight 発火のペイロード型付け | 実行中イベントに紐づく値が正しい型 `Σ_E(ℓ⟨v̄⟩)` を持つ                                                                                                                             |

スケジューラには制約を課さず、スケジュールされる内容についての保証も与えない。

Appendix F は Theorem F.1（Configurations）、**F.2（Declarations）**、**F.3（Expressions）** に加え、副条件（更新キューの型付け、トレース正当化、変数変化集合、flush queue）を含む。

### ケーススタディ: サインアップフォームのユーザー名入力

ユーザーが希望ユーザー名を入力するテキスト入力。名前はネットワーク越しにサーバへ送られ、クライアントは「利用可能か使用済みか」の boolean 応答を受け取る。動的に可用性を確認することでフォームの応答性を高め、送信時に全入力を一括検証する必要をなくす。

構成:

- 2–4 行目: 状態変数 — `username`（入力中のユーザー名の文字列）、`availableNames`（サーバが利用可能と印付けた候補の集合）、`status`（ユーザー名チェックのネットワークリクエスト状態）
- 5 行目: `username` の debounce 版を宣言。可用性 API へのリクエスト数を抑える。内部で debounce は slow 更新のための timeout をスケジュールし、以下のエフェクトではこれをラベル `db⟨⟩` で参照する
- 7–8 行目: チェック成功時のハンドラ。チェックされた名前と可用性 boolean の対を受け取り、利用可能なら `availableNames` に追加、そうでなければ何もしない
- 9 行目: ネットワーク失敗時に `status` を `"error"` に設定（ユーザー名チェックの失敗状態は 2 つある: ネットワークリクエスト自体の失敗と、名前が使用済みであること。後者は既に処理済み）
- 10 行目: ユーザーが入力を止めると debounce が解決し `slowUsername` が更新され、この on ブロックが実行される
- 11–12 行目: 既にチェック済みで利用可能ならネットワーク状態を idle に
- 14–15 行目: それ以外は `status` を `"checking"` にし、新しい可用性チェック API 呼び出しを開始（`fetchUsernameCheck` は §5 の `asyncCompute` と類似の型を持ち、イベントは `req⟨check,suc⟩` と `req⟨check,err⟩`）
- 戻り値: (1) 現在入力中のユーザー名が利用可能かの bool、(2) 可用性・リクエスト状態・入力欄を表示する HTML

Willow が明かす **3 つのバグ**:

**(1) ローディング状態のスタック**

テキスト入力の変化に対する完全エフェクトを手で検査すると、**ネットワークリクエストの全地点で `status` を更新しているが、リクエストが成功したときだけ更新していない**ことが分かる。`slowUsername` が変化した直後は on ブロックの両分岐が `status` を更新する。その後、ネットワークリクエストの error ケースは `status` を更新するが success ケースは更新しない。つまり成功時、「ユーザー名が利用可能で待つものは何もない」と表示しながらローディングスピナーが回り続ける、という混乱を招く状態になる。修正は `handleUsernameSuc` クロージャ内で `status` を更新すること。

**(2) リクエスト競合状態**

型を眺めると、**複数のネットワークリクエストが同一の `status` 変数を共有している**ことに気づく。これは複数リクエストの状態に関する競合状態を作り出している。React のような従来の設定では解決にポインタを使うところだが、Willow の簡素化された設定では「速度を落とす」方針を採る。すなわち、ユーザー名チェックの status を、既に進行中のリクエストがあるかを確認して、あれば何もしないように束縛する:

```
do { if availableNames.has(slowUsername) || status == "checking" then () else ... }
```

これにより同時に 2 つ以上のネットワークリクエストが始まらなくなり、競合状態が除去される。

**(3) 時間的ループ（ただし意図通り）**

完全エフェクト解析が自動的にコード中のループをフラグする（`loop[status]`）ので、これが許容できるかを手で解析する必要がある。

- `availableNames` が `slowUsername` を含まず `status == "idle"` のとき → ユーザー名をチェックしたい。else 分岐に至りチェックする
- `availableNames` が `slowUsername` を含み `status == "idle"` のとき → ユーザーがユーザー名を決めチェック済み。then 分岐で何もしない
- `availableNames` が `slowUsername` を含まず `status == "error"` のとき → else 分岐に至り再チェックを起動。**これはネットワークエラー失敗ケースの組み込みリトライ機構として望ましい**

つまり Willow は「時間的ループがある」と告げ、実際にあるが、それはエラー処理として機能しているのでコードはそのままでよい。**ループ検出は「バグの断定」ではなく「注意の誘導」として働く**という点が示されている。

## 11. 関連研究（§8）

### FRP・React・GUI プログラミング

FRP は **Fran**（Elliott and Hudak 1997）に始まり、時変 behavior と離散 event を第一級の値としてモデル化した。この値中心の変化観は **Flapjax**（Meyerovich et al. 2009）と **FrTime**（Cooper and Krishnamurthi 2006）によって Web に持ち込まれ、これらは更新を自動伝播させるデータフローグラフを構築する。系譜は高階 FRP の超距離的・モーダルな説明（Krishnaswami and Benton 2011）へ続く。**Elm**（Czaplicki 2012）は FRP を GUI に特化させ、後に Redux と React エコシステムを形作った model–view–update ループを普及させた。Demetrescu et al.（2011）はデータフロー制約を命令型 C/C++ に持ち込んだ。

最も近いのは React 自体の形式意味論。**λ_react**（Madsen et al. 2020）は旧来のクラスベース React の意味論を与え、**React-tRace**（Lee et al. 2025）は現代の hooks API を、エフェクトと状態更新の微妙な順序を含めてモデル化する。Willow の意味論は**タイミング解析に焦点を合わせる**点で Lee et al. と異なる。Willow は React を「問題空間の様子を知る」ために参照しつつ、時間的依存グラフを reactive プログラミング一般に広く適用可能にすることを目指す。React-tRace はマウント／アンマウントのコンポーネントライフサイクルと、setter・effect・サブコンポーネント評価の高度に非同期な順序を完全にエンコードする。tRace の意味論を直接使うと、型システムの可読性を損なう動的命名の層をまるごと導入する必要が生じる。著者らは将来的に React-tRace 上に Willow の型・エフェクトシステムを実装したいとしている。

**Adjoint Reactive GUI programming**（Graulund et al. 2021）は GUI 側で最も近い型理論的隣人で、イベントから値を受け取るモダリティを導入し、ある型の値を得るのに必要な時間を推論する。ただしそちらは**値に対する coeffect 規律**を用いるのに対し、Willow は**計算に対する effect 規律**を用いる。

別の流れとしてセッション型と GUI／reactive プログラミングの統合がある: **Event-Driven Multiparty Session Actors**（Fowler and Hu 2017）は複数セッションに同時参加するアクターにフロー依存のエフェクト型付けを用い、**Model-View-Update-Communicate**（Fowler 2019）はセッション型を Elm 風アーキテクチャに畳み込む。

### タイミング解析

Willow の graded next モダリティ `○` は**時相セッション型**から直接着想を得ている。Das et al.（2018）はセッション型にタイミングモダリティを加えてメッセージパッシングプログラムの並列計算量を上界づける。next 演算子自体は時相論理の next 演算子（Pnueli 1977）である。

**ESTEREL**（Berry and Gonthier 1992）と **LUSTRE**（Halbwachs et al. 1991）は離散論理時刻と明示的クロックの上で計算し、Kahn プロセスネットワーク（Kahn 1974）のデータフロー意味論に基づく。Willow の render は同等の離散 tick だが、Willow は**非同期で外部からスケジュールされる** UI イベントの世界を対象とし、単一固定同期クロックを仮定する代わりに**分岐を may エフェクトとして過大近似**する。

**Simply RaTT**（Bahr et al. 2019）のようなモーダル FRP 計算体系は Fitch 風の `○` モダリティで reactive 計算を時間ステップ間にステージングし、空間リークを排除する。Ahman（2023）は非宣言的な関数 reactive プログラムの停止性とリソースロックを研究する。**actor-reactor モデル**（Van den Vonder et al. 2017）は reactive 言語が日常的に陥る落とし穴（glitch、stale read、意図しないフィードバック）を目録化しており、Willow は同じ危険を静的に、循環カスケードと stale リスナーのバグを型レベルのエフェクトとして表面化させることで攻める。

時刻添字付きハードウェアシステムは、Willow の render モデルがソフトウェアを超えて一般化しうることを示唆する: **ephemeral history register**（Rosenband 2004）は React のスケジュールされた状態に似た回路設計構成子である。**Timeline types**（Nigam et al. 2023）は信号の到着時刻で型システムを添字づけるが、対象は動的スケジュールの UI イベントではなく静的スケジュールのハードウェアである。

### エフェクトシステム

Willow の next モダリティ `○` は **graded monad**（Katsumata 2014）の意味での graded モダリティであり、**bounded linear logic**（Girard et al. 1992）とその**リソース半環**への一般化（Brunel et al. 2014; Ghica and Smith 2014）— 代数構造から引いた量で型を注釈する系譜 — に連なる。

graded な時相モダリティとエフェクトの結び付きは Sekiyama et al. が近年発展させており、高階再帰プログラムの時相エフェクトの代数的公理化（Sekiyama and Unno 2025）と、限定継続のための answer-effect modification を持つ依存型時相型・エフェクトシステム（Sekiyama and Unno 2023）がある。

Willow のエフェクトはより広いエフェクトシステムの伝統にも基づく: 代数的エフェクトとハンドラ（Kammar et al. 2013）、エフェクト多相言語 **Frank**（Lindley et al. 2017）がエフェクト多相の扱いに影響を与えた。

並列・並行構造を型付けする 2 つの体系が方法論的に近い: Muller の並列計算グラフの静的予測（Muller 2022）と、Rinaldi et al.（2024）の future 付き ADT のためのグラフ型（その **vertex structure** が future 間の依存を記述する）。著者らは Willow の設計でこの体系から強く着想を得ており、**サブコンポーネントの動的マウント／アンマウントを許すには将来 vertex structure を取り込む必要がある**と見ている。

より広く、Willow の時間的依存グラフは依存解析の長い系譜 — program dependence graph（Ferrante et al. 1987）、依存性の意味論ベースの説明（Cousot 2019）、その安全な情報流（Denning and Denning 1977）における起源 — に接続する。**Willow が異なるのは、「どの計算がどれに依存するか」だけでなく「依存がレンダーを越えていつ発火するか」を追跡する点**である。

## 12. 制約と将来課題

### 意図的な単純化

- 意味論は React ランタイムに忠実ではなく単純化されている。レンダー出力は形式化せず、周囲のホストランタイムを仮定する
- キャッシュ・メモ化は無視（React Compiler を根拠に正当化）
- JavaScript の microtask/task 交錯と React の priority lane を、より具体的な実行順序で置き換えている

### 表現力の制限

- イベントラベルのタプルには**静的に既知**な基本値のみ。生成されたタイマー ID などの動的識別子はエフェクト層に入れられず、`timeout⟨⟩` のようなラベルを強いられる
- 型は unit, bool, 直積, エフェクト付き矢印に限定
- 条件分岐は任意の式ではなく**変数**で分岐する
- **listener safety**: イベントハンドラは自身のキューに新たなラベル付きイベント発火を出せない（`⊢ U lsafe`）
- setter はエフェクトを持てない（updater クロージャ実行前に環境から setter が除去される）
- 副作用のあるコードを実行できる宣言は **on ブロックのみ**
- 時間単位は意図的に相互変換不可。同種の単位のみ結合する

### 未解決／パラメータ化された点

- データフロー関数 `df` はパラメータで、最も単純な具体化（自由変数）はおそらく不精密
- **最小**のカスケードエフェクトを持つ Δ を見つけることが検査の難所として明示されている
- 新しい時間単位は組み込みから導入する必要があり、プログラマがライブラリ API 用に自前の単位を型エイリアスで作るという案は実装済み機能ではなく現実世界での可能性として述べられている
- **最大の将来課題**: Willow は Lee et al.（2025）が形式化するコンポーネントのマウント／アンマウントをまだモデル化していない。この制限を外すには Rinaldi et al.（2024）の vertex structure の上に構築された依存型システムが必要になる。これができれば Willow の解析を既存のレンダーベースフレームワークに直接適用できる

## 13. 結論（著者らの総括）

レンダーを時間の基本単位として扱い、状態変更・イベント登録・スケジュールされたイベントを graded effect として追跡することで、Willow は通常フレームワークランタイムに埋もれているタイミング特性を**静的で検査可能な人工物**に変える。時間的 next モダリティ `○` は観測可能な更新が**いつ**（レンダー単位または任意の宣言された時間単位で）起こりうるかを記録し、`□`、`◇`、`⊘`、`✗` モダリティはイベントリスナーの登録と破棄のライフサイクルを追跡する。

2 フェーズの time-aware 操作的意味論を与え、その instrumented 版に対してエフェクトシステムの preservation を証明し、推論されたエフェクトが標準的なグラフアルゴリズムで解析できる時間的依存グラフを成すことを示した。プロトタイプ推論アルゴリズムは論文中の全例を検査し、サインアップフォームのケーススタディは Willow がローディング状態のスタック、リクエスト競合状態、更新ループを静的に表面化させることを示す。

reactive 計算の「**いつ**」を第一級の静的解析可能な性質にすることで、Willow は UI プログラマがアプリの応答性をコンパイル時に原理的に理解し、手作業の時間的推論に費やす労力を減らす道を与える。
