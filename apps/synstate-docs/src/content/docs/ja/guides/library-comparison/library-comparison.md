:::note[プッシュ型 vs プル型のグリッチフリー]
SynState と Solid は**プッシュ型**でグリッチフリー伝搬を実現します。派生値は依存関係の順序で即座に更新されるため、subscriber はプルすることなく常に整合的な値を受け取ります。SynState は更新が届くノードを深さ順に訪れ、Solid は書き込みの下流をすべて印付けしてからメモを再実行し、上流がまだ stale のメモは先にそれを実行します。

MobX、Jotai、Preact Signals、Recoil は**プル型（遅延）評価**によってグリッチを回避します。派生値は即座にプッシュされず、subscriber やコンポーネントによる読み取り時にオンデマンドで再計算されるため、不整合な中間状態を自然に回避します。詳細な説明は [SynState がグリッチを解決した方法](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/) を参照してください。
:::

## 評価モデル

「グリッチフリー」は subscriber が何を見るかを表すだけで、処理がいつ行われるかは表しません。派生グラフでベンチマークした6つのライブラリは、それぞれ異なる方法で処理をスケジュールしており、[ベンチマーク](/mono/synstate/ja/guides/library-comparison/benchmark/)の結果に表れているのは純粋な速さよりもこの違いです。

| ライブラリ     | 伝搬                                                   | 派生値が計算されるタイミング                                                                                             | グリッチフリー | ベンチマークで最悪となるケース                                                             |
| -------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ | -------------- | ------------------------------------------------------------------------------------------ |
| **SynState**   | プッシュ型、ルートから深さ順                           | ソースが更新されるたび。読まれているかどうかにかかわらない                                                               | あり           | `combine` が持つブランチ数に比例（条件付きファンアウト）                                   |
| RxJS           | プッシュ型、購読ごとに深さ優先                         | 受け取った発行のたび。購読ごとに別々に（コールド）                                                                       | なし           | 経路ごとに1回発行：ディープチェーンで $O(M^2)$、カスケードダイアモンドで $O(2^N)$          |
| MobX           | 無効化はプッシュ、再計算はプル                         | `computed`：読まれたとき（キャッシュは観測中のみ）、`reaction`：依存が変わったとき                                       | あり           | `reaction` が必要で遅延評価が効かない状態付きチェーン（ディープチェーン）                  |
| Jotai          | 無効化はプッシュ、再計算はプル                         | 読まれたとき（`store.get`、フック）またはマウントされたとき（`store.sub`、コンポーネント）。どちらでもない間は計算しない | あり           | `store.set` ごとの一定の管理コスト（全シナリオ）                                           |
| Solid          | プッシュ型、書き込みの下流をすべて印付けしてから再実行 | メモ：直前の実行で読んだソースが変わるたび。読まれているかどうかにかかわらない、effect：メモの後                         | あり           | 書き込みごと・再実行ごとの固定コスト：2つのキュー、依存の解除と再登録（小さな派生グラフ）  |
| Preact Signals | 無効化はプッシュ、再計算はプル                         | `computed`：ソースのどれかが新しいバージョンになった後に読まれたとき、`effect`：最も外側のバッチの終わり                 | あり           | 小さなグラフ。RxJS の素の `subscribe` の連鎖のほうが更新ごとの処理が少ない（派生チェーン） |

これらのうち最も簡潔に説明できるのは SynState のモデルです。ソースへの `next` は、そこから派生したすべてを深さ順に1回だけ同期的に走査して返り、その時点でグラフ内のすべての `getSnapshot()` は最新で、すべての subscriber はちょうど1回呼ばれています（[Observable の仕組み](/mono/synstate/ja/internals/how-observables-work/)）。RxJS も同じプッシュ型ですが順序付けの手順がなく、グリッチと経路数に比例するコストはそこから生じます。MobX と Jotai は逆に、読み取り時に再計算することでグリッチを避けます。MobX の `ComputedValue` は「アクセスされたときにだけ」再計算し、観測されなくなるとリセットされ（[ソース](https://unpkg.com/mobx@7.0.6/src/core/computedvalue.ts)）、Jotai のストアはマウントされているか読まれた atom だけを再計算します（[ソース](https://unpkg.com/jotai@3.0.1/dist/vanilla/internals.js)）。これにより誰も読まない処理を省略できますが、これは SynState にはできないことです。その代わり、処理は何かが要求したときに、要求したときだけ行われます。Preact Signals も読み取り時に再計算し、すべてのシグナルと `computed` が持つバージョン番号で、読み取りに再計算が必要かどうかを決めます。Solid は SynState と同じくプッシュ型で先行評価ですが、そのメモは MobX や Jotai の派生と同じく、直前の実行で読んだものだけを購読します。

### React の外での動作

ベンチマークしたライブラリはすべてバニラ API を持つので、どれも React の外で動き、Solid と Preact Signals はそれぞれのフレームワークの外でも動きます。違いは、読み手が現れる前に何かが動くかどうかと、2つの signal ライブラリについては、単独で使うのに何が必要かです。

- **SynState** は派生 Observable を作成時にルートへ登録するので、モジュールスコープに書いたパイプラインは、購読の有無にかかわらずソースが変わった時点で動きます。検索ボックスのクエリを debounce して `switchMap` で `fromAbortablePromise(fetch(...))` につなぐ処理を普通のモジュールに置け、それを読むコンポーネント・テスト・スクリプトは同じ値を得ます（[例](/mono/synstate/ja/guides/declarative-state-management/#非同期処理の正確な制御)）。グローバルステートとして持つ router も同じで、route を debounce して `switchMap` で fetch につなげば、そのページのビューがマウントされたかどうかに関係なくデータの読み込みが始まります。その代償が条件付きファンアウトのベンチマークが計測している先行評価で、選択中のブランチへの `switchMap` で避けられます。
- **RxJS** もモジュールスコープに書けますが、パイプラインはコールドです。購読されるまで何も動かず、購読のたびにパイプラインが改めて実行されるため、共有（`share`、`shareReplay`）しない限り中の `fetch` は subscriber ごとに送信されます。
- **MobX** は `computed` を読まれるまで評価せず、観測されていない間はキャッシュもしません。fetch のような副作用を伴う処理は、アプリケーション自身が開始する `reaction` / `autorun` やアクション（`flow`）に書きます。`reaction` は先行して動き、`delay` オプションで間引けます。新しい route によって古くなった fetch の取り消しは、副作用の側に任されます。
- **Jotai** は atom の read 関数（非同期 atom の fetch を含む）を、その atom が初めて読まれたかマウントされたときに実行します。React ではそれはコンポーネントのレンダリングであり（非同期 atom はそのコンポーネントをサスペンドさせます）、React の外ではコードが `store.get` か `store.sub` を呼ぶまで何も動きません。そのため atom として書いたデータ読み込みは、それを読むものによってスケジュールされ、アプリケーションでは通常 React のレンダリングがそれにあたります。jotai 3.0.1 のバニラストアで確かめたところ、route atom から派生した非同期 atom は `store.sub` されるまで何も fetch せず、購読中は route が変わるたびに fetch して前の fetch を `signal` で中断し（`switchMap` に相当）、最後の購読者が離れると route が変わっても何も fetch しませんでした。debounce は派生の中には書けず、書き込む側で組み立てる必要があります。
- **Solid** のリアクティブプリミティブ（`createSignal`、`createMemo`、`createEffect`、`createRoot`）は `solid-js` 本体にあり、DOM レンダラー（`solid-js/web`）も JSX も要らないので、UI を一切持たないモジュールにシグナルとメモのグラフを置けます。メモは SynState の派生値と同じく先行評価されます。そのように使うとき、ほかのライブラリと違う点が3つあります。1つ目に、計算は owner に属します。`createRoot`（またはコンポーネント）の中で作るとそれが dispose を担い、その外で作った計算は解放されません。2つ目に、Node では `import 'solid-js'` がサーバービルドに解決され、そこではメモは1回だけ計算されて effect は一度も実行されません。サーバーレンダリングには正しい振る舞いですが、リアクティブに動いてほしいスクリプト・テストランナー・サーバーでは何も言わずに動きません。`browser` の export 条件か、クライアントビルドのパス（ベンチマークと同じ `solid-js/dist/solid.js`）が必要です。3つ目に、React やほかのフレームワーク向けの公式な連携はなく、橋渡しは `observable()` / `from()` か自前の effect になります。Solid 2.0 はリアクティブコアを `@solidjs/signals` として単独で公開しています（執筆時点ではリリース候補で、ここでは計測していません）。そこでは書き込みがマイクロタスクか明示的な `flush()` までまとめられるので、書き込み直後にメモを読むと前の値が返ります。
- **Preact Signals** のコア `@preact/signals-core` は Preact に依存しません。`signal`、`computed`、`effect`、`batch` はブラウザでも Node でも Worker でも同じように動き、`@preact/signals`（Preact）と `@preact/signals-react`（React）はその上の連携パッケージです。ここで比べたライブラリのうち、フレームワーク非依存の signal ライブラリに最も近いのがこれです。作るべき root や owner はなく、`effect` は自身の disposer を返し、`signal.subscribe(fn)` はコールバックに値を渡します。`computed` は MobX と同じく遅延評価で、読まれたときに実行され、誰も読まなければ何もしません。effect は先行評価で、最も外側のバッチの終わりに実行されます。バッチの外での書き込みはそれ自体が1つのバッチなので、書き込みが返った時点で、それが引き起こした effect は実行済みです。MobX と同じく非同期演算子はなく、fetch は effect に書き、古くなった fetch の取り消しはその effect のクリーンアップで行います。

## ベンチマーク対象ライブラリ

以下のライブラリは SynState の[パフォーマンスベンチマーク](/mono/synstate/ja/guides/library-comparison/benchmark/)に含まれています。各セクションではライブラリの特性と理想的なユースケースを強調しています。

### SynState

SynState はカスタムのグリッチフリー Observable 実装の上に構築されています。シンプルな共有ステート（`createState`）から、`debounce`、`throttle`、`switchMap` などの演算子を使用した複雑な非同期ワークフローまで対応できる統一 API を提供します。

**強み:**

- グリッチフリーの派生値伝搬 — 不整合な中間状態なし。
- 豊富な演算子セットが組み込み（別のストリームライブラリ不要）。
- フレームワーク非依存のコアと専用の React/Preact hooks パッケージ。
- 全体を通じて型安全。
- 単純な実行モデル：`next` のたびに深さ順の同期的な走査を1回行い、その後はグラフ全体が整合している。
- パイプラインはどのコンポーネントにも依存せずモジュールスコープで動き、React の外でも同じように動作する。
- 連なったダイアモンドを含め、グラフの形によらず更新ごとのコストがグラフの大きさに比例する（[ベンチマークのまとめ](/mono/synstate/ja/guides/library-comparison/benchmark/#このページの読み方)を参照）。

**トレードオフ:**

- 読まれていない派生値も、ソースが更新されるたびにすべて再計算される。MobX と Jotai はこの処理を省略できる。省略されるのはグラフが持つ必要のないノードで、`switchMap`、スコープの dispose、`audit` で外せる（[ベンチマークのまとめ](/mono/synstate/ja/guides/library-comparison/benchmark/#このページの読み方)を参照）。
- 小さなグラフでは、更新ごとのオーバーヘッドが RxJS より大きい。
- 演算子の数は RxJS より少ない。ただし動作モデル上必要なものはそろっている。すべての Observable は最初から共有されているので `share` / `shareReplay` の類は不要で、エラーは `catchError` ではなく `Result` 値（`mapResultOk`、`unwrapResultOk` など）として流れる。独自の演算子や生成関数は [組み込みのものと同じファクトリ](/mono/synstate/ja/guides/custom-operators-and-creators/) で書ける。

**最適:** シンプルな共有ステートと高度な非同期パイプラインの両方を単一の一貫した API で必要とするプロジェクト。

### RxJS

RxJS は ReactiveX Observable 仕様のリファレンス実装です。非同期およびイベントベースのプログラムを構成するための豊富な演算子ライブラリを提供します。

**強み:**

- 大規模な演算子ライブラリ（200以上の演算子）。
- 確立されたエコシステムとコミュニティ。
- 複雑なイベント処理に優れる（WebSocket ストリーム、リトライロジックなど）。

**トレードオフ:**

- 同期派生値を組み合わせる際に[グリッチ問題](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)が発生する。
- リアクティブストリームという独自のパラダイムへの転換が必要 — 非同期データフローの時間的振る舞いの理解、Cold/Hot Observable の区別、類似する演算子の使い分け（`switchMap` vs `mergeMap` vs `concatMap` など）が求められ、習熟に時間がかかる。
- 状態管理のために特別に設計されていない。

**最適:** グリッチの問題が許容可能な、非同期イベント処理を中心としたアプリケーション。

### MobX

MobX は JavaScript プロキシを介した透過的リアクティブプログラミングを使用します。Observable オブジェクトへの変更は `computed` 値の再計算と observer コンポーネントの再レンダリングを自動的に引き起こします。

**強み:**

- 直感的なミュータブルスタイル API — ステートを直接変更すればすべてが更新される。
- 自動依存関係追跡による細粒度リアクティビティ。
- プル型遅延評価によりグリッチを回避（`computed` 値は `reaction` による読み取り時にオンデマンドで再計算）。

**トレードオフ:**

- 暗黙的な依存関係追跡により、大規模コードベースではデータフローの追跡が困難になる場合がある。
- 組み込みの非同期演算子がない（`flow` または外部ソリューションを使用）。
- よりシンプルなストアライブラリと比較して更新ごとのオーバーヘッドが高い。
- `observer()` HOC がレンダリング中に observable アクセスを追跡するため、React Compiler と非互換（`"use no memo"` ディレクティブによる opt-out が必要）。

**最適:** ミュータブルプログラミングスタイルと自動リアクティビティを好み、複雑な非同期演算子を必要としないチーム。

### Jotai

Jotai はステートの構成要素としてプリミティブな atom を提供します。派生 atom は自然に構成でき、`createStore` API によりフレームワーク非依存の使用が可能です。

**強み:**

- アトミックモデルにより不要な再レンダリングを回避。
- 自動依存関係追跡による構成可能な派生 atom。
- 小さなバンドルサイズ。

**トレードオフ:**

- 組み込みの非同期演算子チェーンがない（非同期 atom は存在するが限定的）。
- ストアレベルのブックキーピングにより更新ごとのオーバーヘッドが高い。
- `store.sub()` コールバックが現在の値を渡さない（シグネチャが `() => void`）ため、値の取得に別途 `store.get(atom)` の呼び出しが必要 — React 外（vanilla JS）での利用時にエルゴノミクスが劣る。対照的に、SynState の `observable$.subscribe((value) => { ... })` はコールバックに値を直接渡す。

**最適:** シンプルな派生を伴う細粒度アトミックステートの恩恵を受ける React アプリケーション。

### Redux（Redux Toolkit）

Redux は Flux アーキテクチャに基づく予測可能なステートコンテナです。Redux Toolkit は `createSlice` と `configureStore` でボイラープレートを簡素化します。

**強み:**

- 予測可能な単方向データフロー。
- タイムトラベルデバッグのための優れた DevTools。
- 大規模なエコシステム（ミドルウェア、saga、thunk）。

**トレードオフ:**

- Redux Toolkit を使用してもボイラープレートが冗長。
- セレクター（Reselect 経由）はプル型で手動メモ化が必要。
- 組み込みのリアクティブ伝搬がない — 非同期ロジックはミドルウェアに委譲。

**最適:** 厳格な単方向データフロー、タイムトラベルデバッグ、成熟したミドルウェアエコシステムを重視する大規模チーム。

### Solid

Solid は細粒度のシグナルの上に作られた UI フレームワークです。`createSignal`、`createMemo`、`createEffect` と、DOM を直接更新するコンパイル済みの JSX からなります。リアクティブプリミティブは `solid-js` の一部でレンダラーなしでも動き、ベンチマークはそれを単独で計測しています（何が必要かは [React の外での動作](#react-の外での動作) を参照）。

**強み:**

- プッシュ型でグリッチフリーの伝搬。書き込みの下流をすべて印付けしてからメモを再実行するので、各メモは更新ごとに1回だけ実行される。
- 動的な依存追跡。メモは直前の実行で読んだものだけを購読するので、誰も observe していない書き込みのコストはほぼない。
- `createMemo(fn, initialValue)` は前回の値を受け取るので、状態を持つ派生（`scan`）もほかと同じメモで書ける。
- 成熟したフレームワークと広いエコシステム。

**トレードオフ:**

- フレームワークから独立して使うことはできるが、パッケージはそのための形をしていない。計算には owner（`createRoot`）が必要で、Node では `solid-js` が非リアクティブなサーバービルドに解決され、ほかのフレームワーク向けの連携もない。
- 更新ごとのオーバーヘッドが SynState より大きい。書き込みのたびに更新キューをアロケートし、再実行のたびにすべてのソースから計算を外して登録し直す。
- 非同期演算子のチェーンはない。fetch は Suspense と組み合わせる `createResource` が担う。

**最適:** Solid のアプリケーション。Solid の外では、root と Node が解決するビルドを管理する用意のあるコード。

### Preact Signals

Preact Signals は Preact チームによる signal ライブラリ（`signal`、`computed`、`effect`）で、フレームワーク非依存のコア（`@preact/signals-core`）と、Preact・React 向けの連携パッケージとして公開されています。ベンチマークが計測しているのはコアです。

**強み:**

- 公開された形のままフレームワーク非依存。コアパッケージは Preact に依存せず、root などの準備も要らない。
- 更新ごとのオーバーヘッドが小さい。何を再実行するかはバージョン番号で決まり、前回と同じものを読む実行は依存リンクを使い回して何もアロケートしない。
- 遅延評価の `computed` によりグリッチフリー。誰も読まない派生値は計算されない。
- API が小さい。`subscribe(fn)` はコールバックに値を渡す。

**トレードオフ:**

- 非同期演算子がない。
- `computed` は前回の値を受け取らないので、状態を持つチェーン（`scan`）は effect が更新するシグナルの列として書くことになる。
- React 連携は Babel 変換か `useSignals` フックで動く。React Compiler との互換性はここでは検証していない。

**最適:** 小さく速いフレームワーク非依存の signal を求め、非同期演算子を必要としないプロジェクト。

### Zustand

Zustand は小さく高速な Flux 系ストアです。優れた TypeScript サポートと React 連携を備えた最小限の API を提供します。

**強み:**

- シンプルなステートに対して非常に軽量で高速。
- 最小限の API サーフェス — 学習が容易。
- React でプロバイダー不要。

**トレードオフ:**

- 組み込みの派生値プリミティブがない — 派生はインラインセレクター。
- 独立した派生値を組み合わせられない（ダイヤモンド依存関係ベンチマークから除外）。
- 非同期演算子がない。

**最適:** 複雑な派生を必要とせず、最小限のオーバーヘッドでシンプルな共有ステートが必要なプロジェクト。

### Valtio

Valtio は JavaScript プロキシを使用してミュータブルスタイルの API を提供し、プロキシオブジェクトに書き込むと subscriber が自動的に通知されます。

**強み:**

- 非常に直感的な API — オブジェクトを変更するだけ。
- 小さなバンドルサイズ。
- `useSnapshot` による React での自動レンダリング最適化。

**トレードオフ:**

- バニラ API に組み込みの派生値プリミティブがない（`derive` は別ユーティリティ）。
- 独立した派生値を組み合わせられない（ダイヤモンド依存関係ベンチマークから除外）。
- プロキシベースの変更検出は特定のデータ構造でエッジケースがある。

**最適:** 複雑な派生なしで共有ステートのための最もシンプルなミュータブル API を求めるプロジェクト。

## ベンチマーク非対象ライブラリ

以下のライブラリは異なる主要目的を持ち、パフォーマンスベンチマークには含まれていませんが、要件に応じて検討する価値があります。

### Recoil

Recoil は Meta による実験的なアトミックステート管理ライブラリで、React 専用に設計されています。

**ベンチマーク対象外の理由:** Recoil はもはやアクティブにメンテナンスされておらず（最後の npm リリースは2023年）、React に密結合されています。フレームワーク非依存のバニラ API がないため、公平な比較が難しい状況です。

**強み:**

- React 向けアトミックステートモデルの先駆け。
- 組み込みの非同期セレクター。
- Concurrent Mode サポート。

**考慮事項:** 新しいプロジェクトを開始する場合、Jotai は Recoil のアトミックモデルに触発されたメンテナンスされている代替ライブラリです。

### XState

XState はステートマシンおよびステートチャートライブラリです。アプリケーションロジックを明示的な状態、遷移、副作用を持つ有限状態マシンとしてモデル化します。

**ベンチマーク対象外の理由:** XState は根本的に異なる問題を解決します — 汎用的なリアクティブステートコンテナを提供するのではなく、アプリケーションロジックをステートマシンとしてモデル化します。伝搬速度のベンチマークは XState の価値を意味のある形で表現しません。

**強み:**

- ステートマシンとステートチャートによる形式的に検証可能なロジック。
- ステートマシン設計のためのビジュアルエディター（Stately）。
- 複雑な UI フロー（ウィザード、認証、メディアプレーヤー）に優れる。

**最適:** 明確に定義された状態と遷移を持ち、生の伝搬速度よりも形式的な正確性が重要なアプリケーション。

### TanStack Query

TanStack Query（旧 React Query）は、サーバーデータの取得、キャッシュ、同期に特化したサーバーステート管理ライブラリです。

**ベンチマーク対象外の理由:** TanStack Query はクライアント側のリアクティブステートではなく、サーバーステート（HTTP キャッシュ、再取得、ページネーション）を管理します。SynState のようなライブラリの直接的な代替ではなく、補完的なものです。

**強み:**

- 自動キャッシュ、重複排除、バックグラウンド再取得。
- すぐに使える stale-while-revalidate 戦略。
- フレームワーク非依存（React、Vue、Solid、Svelte アダプター）。

**最適:** サーバーからデータを取得するすべてのアプリケーション。クライアントステートライブラリと組み合わせて使用されることが多い。

## 適切なライブラリの選択

| 要件                                                       | 推奨                                             |
| ---------------------------------------------------------- | ------------------------------------------------ |
| シンプルな共有ステート（ダークモード、ユーザーセッション） | **SynState**, Zustand, Valtio, Jotai             |
| 複雑な非同期パイプライン（debounce、switchMap、retry）     | **SynState**, RxJS                               |
| グリッチフリーの派生値                                     | **SynState**, MobX, Jotai, Solid, Preact Signals |
| ミュータブルスタイル API                                   | MobX, Valtio                                     |
| アトミック / 細粒度リアクティビティ                        | **SynState**, Jotai, Solid, Preact Signals       |
| 厳格な単方向データフロー                                   | **SynState**, Redux                              |
| 形式的なステートマシン                                     | XState                                           |
| サーバーステートキャッシュ                                 | TanStack Query                                   |
| 最小バンドル + シンプルな API                              | **SynState**, Zustand, Valtio                    |
| シンプルから複雑までの統一 API                             | **SynState**                                     |

## パフォーマンス比較

[パフォーマンスベンチマーク](/mono/synstate/ja/guides/library-comparison/benchmark/)は6種類のグラフ形状で伝搬時間を計測しています。すべてで最速のライブラリはありません。小さなグラフでは RxJS が速く、単一ステートでは SynState・Preact Signals・Zustand がそれに続きます。処理を省略できる場面では MobX・Solid・Preact Signals が、深いグラフ全体が読まれる場面では SynState と Preact Signals が（ディープチェーンでは Redux も）速くなります。SynState について結果から言えるのは、どこでも最速であることではなく、最悪ケースが抑えられていることで、ページでは各ライブラリの最悪ケースを並べています。シナリオごとのまとめは[このページの読み方](/mono/synstate/ja/guides/library-comparison/benchmark/#このページの読み方)にあります。

同じくグリッチフリーで、コストがグラフの大きさに比例する Preact Signals に対しては、結果に一貫した勝者はなく、シナリオによってどちらかが速くなります。Preact Signals より SynState を選ぶ理由はベンチマークではなく API にあります。`debounce`・`throttle`・`switchMap` などのオペレーターを同じグリッチフリーなグラフの上で使えることで、Preact Signals ではタイミングやキャンセルを effect の中に書くコードに任せることになります（[React の外での動作](#react-の外での動作)と、同じ検索ボックスを両方で書いた[非同期処理の比較](/mono/synstate/ja/guides/library-comparison/async-comparison/)を参照）。
