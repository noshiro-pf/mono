## このページの読み方

このページのすべてのシナリオで最速のライブラリはありません。SynState も例外ではありません。各シナリオは1つのグラフ形状についての問いなので、ライブラリの比較はシナリオの中で行い、シナリオをまたいで比べないでください。

SynState はどのシナリオでも最速のライブラリの {/* bench:summary/synstate-worst-over-fastest */}2.6{/* /bench */} 倍以内に収まっている一方、各シナリオの最遅のライブラリは最速の {/* bench:summary/slowest-over-fastest-least */}48{/* /bench */} 倍以上かかっています。各シナリオが何に負荷をかけているかは、それぞれのセクションで説明しています。

※1 RxJS は glitch-free ではありません。ダイヤモンドでは、subscriber が古い値と新しい値の混ざった組み合わせも受け取ります（[RxJS グリッチ](#シナリオ-ダイヤモンド依存関係)）。glitch の起きないライブラリの中では {/* bench:summary/diamond-fastest-glitch-free */}SynState{/* /bench */} が最速です。

※2 SynState を、MobX や Jotai と同じく選択中の分岐だけを購読する `switchMap` で書いた場合の値です。全分岐を `combine` で書くと {/* bench:summary/fan-out-synstate-combine-over-fastest */}2,388{/* /bench */}× で、[シナリオ](#シナリオ-条件付きファンアウト)では両方を載せています。この書き方は最遅の列からも除いています。

`>` の付いた比率は、タイムアウト（{/* bench:cascaded-diamond/timeout */}5,000 ms{/* /bench */}）までに完了しなかったライブラリを、ちょうどその時間がかかったものとして割った値です。

計測結果から言えること：

- **SynState の更新ごとのオーバーヘッドは中程度で、最小ではありません。** 何も派生しない場合（単一ステート）、どのライブラリも値を保持して subscriber を1つ呼ぶだけなので、7つすべてを同じ条件で比べられるのはこのシナリオだけです。SynState に対して、Zustand は {/* bench:single-state/zustand-over-synstate */}1.0{/* /bench */}倍、Valtio は {/* bench:single-state/valtio-over-synstate */}7.4{/* /bench */}倍、MobX は {/* bench:single-state/mobx-over-synstate */}8.8{/* /bench */}倍、Redux は {/* bench:single-state/redux-over-synstate */}24{/* /bench */}倍、Jotai は {/* bench:single-state/jotai-over-synstate */}33{/* /bench */}倍の時間がかかります。小さな派生グラフでは、順序付けの手順を持たずに `subscribe` 呼び出しを連ねるだけの RxJS が SynState より高速で、MobX・Jotai・Redux は SynState より低速です。
- **SynState の更新ごとのコストはグラフの形によって爆発しません。** これが、もう1つのプッシュベースのライブラリである RxJS との違いです。ソースが1回更新されるたびに子孫を深さ順に1回だけ走査し、そこに至る経路がいくつあっても各 subscriber を1回だけ呼ぶので、ダイヤモンドがあっても発行回数は増えません。RxJS は経路ごとに発行します。ディープチェーンを4倍深くすると（$K = 1000$ で $M = 50 \to 200$）、SynState の時間は {/* bench:summary/deep-chain-synstate-growth */}3.3{/* /bench */} 倍、Jotai は {/* bench:summary/deep-chain-jotai-growth */}4.1{/* /bench */} 倍、MobX は {/* bench:summary/deep-chain-mobx-growth */}4.0{/* /bench */} 倍ですが、RxJS は {/* bench:summary/deep-chain-rxjs-growth */}32{/* /bench */} 倍になり、カスケードダイアモンドでは {/* bench:cascaded-diamond/rxjs-timeout-n-math */}$N=16${/* /bench */} で計測を完了できなくなります。RxJS の中間発行は[グリッチ](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)でもあり、subscriber は古い値と新しい値が混ざった組み合わせを受け取ります。
- **MobX と Jotai が省略しているのは、グラフが持つ必要のなかった処理です。** どちらも派生値を何かに読まれたときにだけ再計算するので、誰も読まないノードのコストはゼロです。SynState は、ソースが更新されるたびに持っている派生値をすべて評価します。これは `next` が返った時点ですべての `getSnapshot()` が整合している、ということの代償で、何を計算するかは誰が読むかではなくグラフの書き方で決まります。このページでそれがプルベースのライブラリを速くするのは条件付きファンアウトだけで、このシナリオはそのために作られています。`combine` が、セレクターが一度も選ばない千個のブランチを抱えているのです。選択中のブランチだけを購読する `switchMap` で書けば、SynState はどのブランチ数でも約 {/* bench:fan-out/synstate-switch-map-typical */}4.2 ms{/* /bench */} のままです。アプリケーションで出会う「誰も読まないノード」も同じ種類のもので、それぞれグラフから外す素直な方法があります。選ばれていないブランチは `switchMap`、画面にないビューはその observable をスコープ内で作ってビューと一緒に dispose、表示されるより頻繁に書かれる値はその手前に `audit` や `throttle` を置く、という具合です。各ライブラリがこの処理をいつ行うかは[評価モデル](/mono/synstate/ja/guides/library-comparison/library-comparison/#評価モデル)を参照してください。
- **SynState のグラフ構築は低コストです。** カスケードダイアモンドは毎回の計測の中でグラフを構築しますが、SynState の行は $N$ が増えても横ばいです。新しいノードは親と、親から受け継いだルートに登録されるだけで、ルートまでの $2^N$ 本の経路をたどることはありません。ディープチェーンのように一度作ったグラフを何度も更新する場合、構築は更新ごとのコストにまったく含まれません。

したがって、このページから言えるのは「SynState は速い」よりも狭いことです。ここで比較したライブラリのうち、グラフの形によらず更新ごとのコストがグラフの大きさに比例したままのプッシュベースのライブラリは SynState だけで、更新ごとのオーバーヘッドは MobX・Jotai・Redux よりかなり小さく、RxJS よりは大きい、ということです。プルベースのライブラリが勝つ唯一のシナリオは、誰も読まない処理を抱えるように作られたグラフで、`switchMap` で書けば SynState もその処理を抱えません。

## シナリオ： 単一ステート

ステート1つ、subscriber 1つ、派生値なし。他のすべてのシナリオの土台となる下限で、Zustand と Valtio が参加するのはこのシナリオだけです。両者のバニラ API には派生値のノードがないため、派生値のあるグラフでは subscriber の中でインライン計算するしかなく、それは他のライブラリが構築するグラフとは別の、より小さなグラフになります。

- ループ： counter を $1$ から $N$ まで同期的に更新（$N = 10^5$）.
- 検証： 最終値 $= N$.
- 各ライブラリの subscriber は渡された値を記録します。コールバックに値が渡されない場合（Jotai、Redux、Valtio）はストアから読み直します。

### 実装の詳細

すべての実装は vitest テストとして実行可能です。

#### SynState

```tsx
export const runBenchmark = (n: number): number => {
    const [counter, setCounter] = createState(0);

    let mut_lastValue = 0;

    const subscription = counter.subscribe((v) => {
        mut_lastValue = v;
    });

    for (let mut_i = 1; mut_i <= n; mut_i++) {
        setCounter(mut_i);
    }

    subscription.unsubscribe();

    return mut_lastValue;
};
```

export const runBenchmark = (n: number): number => {
    const state = observable({ counter: 0 });

    let mut_lastValue = 0;

    const dispose = reaction(
        () => state.counter,
        (value) => {
            mut_lastValue = value;
        },
        { fireImmediately: true },

    for (let mut_i = 1; mut_i <= n; mut_i++) {

    return mut_lastValue;
};

#### Redux

```tsx
export const runBenchmark = (n: number): number => {
    const counterSlice = createSlice({
        name: 'counter',
        initialState: { value: 0 },
        reducers: {
            set: (state, action: Readonly<{ payload: number }>) => {
                state.value = action.payload;
            },
        },
    });

    const store = configureStore({
        reducer: counterSlice.reducer,
        middleware: () => new Tuple(),
    });

    let mut_lastValue = store.getState().value;

    store.subscribe(() => {
        mut_lastValue = store.getState().value;
    });

    for (let mut_i = 1; mut_i <= n; mut_i++) {
        store.dispatch(counterSlice.actions.set(mut_i));
    }

    return mut_lastValue;
};
```

:::caution[数値の読み方について]
この単純なチェーンのシナリオでは、RxJS が SynState より高速です。このグラフから分からないこと：

- **RxJS** はここで高速で、[ダイアモンドシナリオ](#シナリオ-ダイヤモンド依存関係)でもまだ高速です。ダイアモンド1つでは発行回数が2倍になるだけだからです。ダイアモンドが広がったり連なったりすると `combineLatest` は冗長な中間値を発行し、ワイドダイアモンドで $O(N^2)$、**カスケードダイアモンドでは指数関数的**（一般に $O(D^N)$、$D$ = 1段あたりのファンアウト）に劣化します（[ダイアモンドシナリオ](#シナリオ-ダイヤモンド依存関係)および[インタラクティブデモ](/mono/synstate/ja/guides/library-comparison/interactive-demo/)を参照）。さらに RxJS は[グリッチ](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)（不整合な中間状態）の問題を抱えており、SynState はこれを排除しています。

SynState の伝播は、すべてのシナリオで更新1回あたり $O(n)$（$n$ は更新されたソースの子孫の数）です。伝播順序によって各子孫をちょうど1回ずつ訪問するためで、グリッチフリーであり、ダイアモンドがあっても変わりません。これは更新についての主張で、[カスケードダイアモンド](#シナリオ-カスケードダイアモンド)の表にはグラフの構築も含まれていますが、そこでの構築コストは小さなものです。各シナリオから言えることは、SynState の方が遅いケースも含めて[このページの読み方](#このページの読み方)にまとめています。
:::

### 実装の詳細

各ライブラリは同じ派生チェーンパターンを実装しています。すべての実装は vitest テストとして実行可能です。

#### SynState

```tsx
export const runBenchmark = (n: number): number => {
    const [counter, setCounter] = createState(0);

    const doubled = counter.pipe(map((x) => x * 2));

    const quadrupled = doubled.pipe(map((x) => x * 2));

    let mut_lastValue = 0;

    const subscription = quadrupled.subscribe((v) => {
        mut_lastValue = v;
    });

    for (let mut_i = 1; mut_i <= n; mut_i++) {
        setCounter(mut_i);
    }

    subscription.unsubscribe();

    return mut_lastValue;
};
```

## シナリオ： ディープチェーンスループット

最初の2つのシナリオは固定サイズのグラフを使用しています。このシナリオは[スループットのインタラクティブデモ](/mono/synstate/ja/guides/library-comparison/interactive-demo/#throughput-per-update-overhead-under-load)と同じトポロジーを使用します： depth-$M$ の `scan` チェーンで、各ステージが前のステージに向かって lerp し、`combine` が**すべての $M+1$ 個の出力**を読み取ります。$K$ 回のソース更新を同期的に実行します（アニメーションフレームあたり $K$ 回の更新をシミュレート）。

以下の図は $M = 3$ の場合のグラフ構造です。実際のベンチマークでは $M$ は $50$〜$200$ です：

<DeepChainDepGraph />

- $K$（計測あたりの更新回数）： $100$, $500$, $1000$.
- $M$（チェーンの深さ）： $50$, $100$, $200$.
- Zustand、Valtio、Redux は除外（独立した派生値による `scan` チェーンを表現する仕組みがないため）。
- {/* bench:deep-chain/timeout */}5,000 ms{/* /bench */} を超える計測は打ち切り。

:::caution[RxJS がソース更新1回あたり $O(M^2)$ になる理由]
`combineLatest` は $M+1$ 個の入力（source + $M$ 個の scan ステージ）すべてを subscribe しています。source が新しい値を発行すると、RxJS の深さ優先伝播により以下のカスケードが発生します：

1. **source** が発行 → `combineLatest` が実行（**1回目**の subscriber 呼び出し。scan₁〜scanₘ はまだ古い値）
2. source の変更が **scan₁** に伝播 → scan₁ が発行 → `combineLatest` が実行（**2回目**。scan₂〜scanₘ はまだ古い値）
3. scan₁ の変更が **scan₂** に伝播 → scan₂ が発行 → `combineLatest` が実行（**3回目**）
4. …チェーン全体を通じてこれが繰り返される…
5. **scanₘ** が発行 → `combineLatest` が実行（**$M+1$ 回目** — ここで初めてすべての値が最新）

$M+1$ 回の `combineLatest` 発行のそれぞれが subscriber を呼び出し、subscriber は $M+1$ 個の値を処理します → **呼び出し1回あたり $O(M)$**。したがってソース1回の更新コストは $O(M) \times (M+1)$ = **$O(M^2)$** です。

SynState の `combine` は伝播順序が完全に解決されてから発行するため、**ソース更新1回あたり subscriber 呼び出し1回、合計 $O(M)$** です。
:::

## シナリオ： 条件付きファンアウト

これまでのシナリオは伝搬スループットをテストしていました — すべてのソース更新が subscriber に到達します。このシナリオは異なるパターンをテストします： **購読セットに含まれない observable への更新コスト** — 動的依存追跡が最も有利に働くケースであり、MobX や Jotai の動作モデルを確かめるためのシナリオです。

グラフには B 個の分岐とセレクターがあります。セレクターは、結果がどの分岐を読むかを選ぶ source で、結果は `branch[selector]` です。セレクターはベンチマーク中ずっと $0$ に固定されており、`branch[0]` のみが「アクティブ」です。ベンチマークでは **`branch[1]`**（非アクティブな分岐）を $K = 10^5$ 回更新します。

<ConditionalFanOutDepGraph />

このシナリオの核心は、ライブラリによって **`branch[1]` の observer リスト（購読者の有無）が異なる** 点です：

- **静的購読（SynState, RxJS）**： `combine` が構築時に全分岐を購読するため、`branch[1]` にも observer が登録されています。`branch[1]` が更新されるたびに `combine` が発火し、`map` が前回と同じ値を生成し、等値比較で下流への伝搬を防止します。結合配列のサイズが増えるため、コストは B に比例します。
- **同じ2つを `switchMap` で（「(switchMap)」の行）**： `selector.pipe(switchMap((sel) => branches[sel]))` は選択中の分岐だけを購読し、セレクターが変われば別の分岐に購読を移すので、ここでも `branch[1]` に observer はいません。SynState と RxJS では、動的な依存関係はこう書きます。
- **動的購読（Jotai, MobX）**： `computed` や派生 atom の関数が**実行時に** `.get()` で実際にアクセスした observable だけを購読します。`selector = 0` のとき `branch[0].get()` のみが呼ばれるため、`branch[1]` の observer リストは**空**です。`branch[1]` を更新しても、通知先が存在しないため何も起きません。

### 主な観察結果

- **MobX** はこのシナリオで最も高速です。`computed(() => branches[selector.get()].get())` は実行時に `selector` と `branches[0]` のみを購読するため、`branches[1]` の observer リストは空です。`branches[1]` を更新しても通知先が存在せず、B に関係なく約 {/* bench:fan-out/mobx-typical */}1.5 ms{/* /bench */} で一定です。
- **SynState** のコストは B に対して線形に増加します。`combine` が構築時に全分岐を購読するため、どの分岐が更新されても combine が発火します。グラフで線形な傾向が明確に見えます：B=2 で {/* bench:fan-out/synstate@min-b */}31.8 ms{/* /bench */}、B={/* bench:fan-out/synstate-last-measured-b */}1000{/* /bench */} で {/* bench:fan-out/synstate@last-measured-b */}3,821 ms{/* /bench */}（{/* bench:fan-out/updates-math */}$K = 100{,}000${/* /bench */} 回の更新にわたり、1分岐・1更新あたり約 {/* bench:fan-out/synstate-ns-per-branch-per-update */}38{/* /bench */} ns）。
- **`switchMap` の SynState** は B に関係なく約 {/* bench:fan-out/synstate-switch-map-typical */}4.2 ms{/* /bench */}、**`switchMap` の RxJS** は約 {/* bench:fan-out/rxjs-switch-map-typical */}3.7 ms{/* /bench */} のままです。`branch[1]` の更新はどちらでもどのノードにも届きません。上の SynState の行が計測しているのは、それを書いた `combine` であって、モデルの限界ではありません。
- **RxJS** は SynState と同じ静的な `combineLatest` アプローチです。コストは B に応じて増加しますが、SynState より緩やかです。`combineLatest` は等値比較による下流伝搬スキップを行わず常に発行するため、subscriber は毎回呼ばれますが処理は最小限（値の代入のみ）です。
- **Jotai** は MobX と同じ動的購読を行います — `resultAtom` は非アクティブな分岐を購読していないため再計算はトリガーされません。しかし `store.set()` 自体が atom store 内で invalidation チェック等の管理処理を実行するため、B に関係なく約 {/* bench:fan-out/jotai-typical */}119 ms{/* /bench */} の一定オーバーヘッドが発生します。このため B≤{/* bench:fan-out/jotai-slower-through-b */}20{/* /bench */} では SynState より遅い結果です。

    :::note[このベンチマークは動的購読に有利な恣意的シナリオです]
    このベンチマークは静的購読と動的購読の理論的な特性の違いを示すために設計されたものであり、**動的購読側に最も有利な条件**を意図的に構成しています。それでも、静的購読側も `switchMap` を使った自然な実装ではほとんど差が出ません。どのブランチ数でも、SynState は約 {/* bench:fan-out/synstate-switch-map-typical */}4.2 ms{/* /bench */}、RxJS は約 {/* bench:fan-out/rxjs-switch-map-typical */}3.7 ms{/* /bench */} で、MobX の約 {/* bench:fan-out/mobx-typical */}1.5 ms{/* /bench */} と大差ありません。

    現実のアプリケーションにおいて、selector が固定されたまま非アクティブな分岐だけが大量に更新され続けることは考えにくいです。もし使われていないデータが頻繁に更新される状況が発生しているなら、それはライブラリの購読モデルの問題ではなく、アプリケーション側の設計の問題です。例えば、表示されていないチャンネルの WebSocket データを購読し続けている場合、ライブラリの選択に関係なく、不要な購読自体を停止すべきです。

    また、このベンチマークでは selector の切り替えを行っていません。現実のアプリケーションでは selector が変わるたびに MobX/Jotai は購読セットの再構築（古い購読の解除 + 新しい購読の登録）が必要ですが、そのコストはここには含まれていません。
    :::

export const runBenchmark = (k: number, branchCount: number): number => {
    const [selector] = createState(0);

    const branches: DeepReadonly<
        {
            source: Observable<number>;
            set: (v: number) => void;
        }[]
    > = Arr.zeros(asUint32(branchCount)).map(() => {
        const [source, setSource] = createState(0);

        return { source, set: setSource };
    });

    // `as const` needs a literal, and `combine` needs the tuple type only the
    // literal produces.
    // eslint-disable-next-line ts-data-forge/prefer-canonical-array-slicing
    const allSources = [
        selector,
        ...branches.map((b) => b.source),
    ] as const satisfies NonEmptyTuple<Observable<number>>;

    const result = combine(allSources).pipe(
        map(
            ([selectorValue, ...branchesValue]) =>
                branchesValue[selectorValue] ?? 0,
        ),
    );

    let mut_lastValue = 0;

    const subscription = result.subscribe((v) => {
        mut_lastValue = v;
    });

    // Update an INACTIVE branch (branch 1, while selector = 0)
    const inactiveBranch = branches[1];

    if (inactiveBranch === undefined) {
        throw new Error('need at least 2 branches');
    }

    for (let mut_i = 1; mut_i <= k; mut_i++) {
        inactiveBranch.set(mut_i);
    }

    subscription.unsubscribe();

    return mut_lastValue;

        void

## 測定方法

- **ウォームアップ**： 5ラウンド（破棄）。
- **測定**： 20ラウンド。
- $N$： 1ラウンドあたり $10^5$ 回の更新。
- **タイミング**： `performance.now()`（サブミリ秒精度）。
- **統計**： 中央値、最小、最大、p95、ops/sec（中央値に基づく）。最初の3シナリオには、各中央値を SynState の中央値で割った「vs SynState」（SynState の何倍かかったか）も載せています。

### 公平性に関する注記

- **Redux**： デフォルトのミドルウェア（thunk、シリアライザブルチェック、イミュータビリティチェック）は `middleware: () => new Tuple()` で無効化されています。これらは本番ビルドでは tree-shaking で除去される開発時チェックです。
- **Zustand** と **Valtio**（単一ステートのみ）： どちらのバニラ API にも派生値のノードがないため（Valtio の `derive` は別パッケージ）、他のシナリオでは派生値を subscriber 内でインライン計算するしかありません。それは他のライブラリが構築するグラフよりノードが少なく、同じ計測になりません。そのため、どのライブラリも何も派生しないシナリオにだけ参加します。Valtio の `subscribe` の第3引数 `true` は通知を同期にし、すべてのミューテーションで subscriber が呼ばれるようにします（Valtio はデフォルトで非同期にバッチ処理します）。
- **SynState** と **RxJS**（ダイヤモンド、カスケードダイアモンド、条件付きファンアウト）： `combine` / `combineLatest` はタプルを作り、続く `map` がそれを値に変えるので、合流1つが2ノードになります。MobX の `computed` や Jotai の派生 atom では1ノードです。合流ごとにノード1つと配列1つ分のコストがかかりますが、どちらのライブラリでも合流はこう書きます。
- **MobX**（ディープチェーン）： `computed` は自身の前回の出力を読めないため、`scan` チェーンは `observable.box` の列として書き、1つの `reaction` が1つのアクション内でループして更新します。これは派生ノードのチェーンではなく命令的なコードで、MobX の行はそれを計測しています。
- **RxJS**（ダイヤモンド依存関係）： `combineLatest` は[グリッチ問題](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)により、ソース更新ごとに subscriber を2回発火させます。ベンチマークはこの追加作業を含むウォールクロック時間を測定しており、RxJS におけるダイヤモンド依存関係の実際のコストを反映しています。
- **MobX**： 他のライブラリの subscribe-and-record パターンに合わせるため、`autorun` ではなく `reaction` を使用しています。MobX の strict mode で要求されるとおり、`runInAction` で各ミューテーションをラップしています。
- **Jotai**： `store.sub()` はコールバックに現在の値を渡さないため、リスナー内で追加の `store.get()` 呼び出しが必要です。初期値もsubscribe前に `store.get()` で読み取られます。
- ディープチェーン以外では、すべてのライブラリがベンチマーク関数内でステート、派生値、およびsubscriptionを作成するため、セットアップコストは測定に含まれています。ディープチェーンはタイマーを開始する前にグラフを構築します。
- **条件付きファンアウト**： SynState と RxJS は、全ブランチに対する静的な `combine` / `combineLatest` と、MobX や Jotai と同じく選択中のブランチだけを購読する `switchMap` の2通りで計測しています。

## 分析： Jotai が遅い理由

Jotai はグリッチフリーのセマンティクスを持ちながら、両方のシナリオで最も遅いライブラリです。根本原因は**更新ごとのフレームワークオーバーヘッド**、つまりグラフのサイズに関係なく Jotai のストアが `store.set()` の呼び出しごとに実行する処理量です。

### 更新ごとのコスト内訳

`store.set(counterAtom, i)` が呼び出されると、Jotai のストアは以下のステップを実行します：

1. **値の更新** — 新しい値を書き込み、`Object.is` で比較。$O(1)$。
2. **無効化パス**（`invalidateDependents`）— マウントされたすべての依存先の DFS トラバーサル。`Map<Atom, EpochNumber>` でのエポック番号追跡により各ノードを「再計算が必要」とマーク。$O(N)$（$N$ = 影響を受ける atom の数）。
3. **トポロジカルソート**（`recomputeInvalidatedAtoms`）— 訪問追跡に `WeakSet` を使用した2回目の DFS 後順トラバーサル。正しい順序の再計算リストを生成。$O(N)$。
4. **再計算** — トポロジカル順序の各 atom に対して `read` 関数を実行。read 関数内で、各 `get(dep)` 呼び出しは： (a) 依存先の `AtomState` を検索、(b) エポック番号を比較して古さをチェック、(c) 将来の無効化のために `Map` に依存関係を記録。コストは $O(\sum D_i)$ — 再計算されるすべての atom の直接依存の合計であり、積ではない。各1つの依存を持つ N 個の atom のチェーンでは $O(N)$。
5. **subscriber 通知** — リスナーコールバックを発火。Jotai の `store.sub()` は新しい値を渡さないため、コールバックは `store.get()` を再度呼び出す必要があり、追加のキャッシュ検索が発生する。リスナーあたり $O(1)$ だが、追加のトラバーサルが1回発生。

### SynState との比較

| ステップ                    | SynState                                                   | Jotai                                                           |
| --------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------- |
| **グラフの解決**            | 構築時に1回                                                | `store.set()` のたびに（ステップ2-3）                           |
| **伝搬**                    | 事前構築されたsubscriptionチェーンを通じた直接関数呼び出し | getter spy + `Map`/`WeakSet` 操作を伴う `read` 関数実行         |
| **依存関係の追跡**          | 静的（構築時に設定）                                       | 動的（getter spy を通じて評価のたびに再検出）                   |
| **鮮度チェック**            | 不要（プッシュ型）                                         | `get()` 呼び出しごとのエポック番号比較                          |
| **subscriber への値の配送** | 値がコールバックに直接渡される                             | コールバックが値を読むために `store.get()` を呼び出す必要がある |

### 定数倍の差が見えるケース

ベンチマークのループは更新ごとの差を測定可能にするために{/* bench:derived-chain/updates */}100,000{/* /bench */}回の更新を実行しています。しかし、この定数倍のコストは高頻度イベントを扱う実際のアプリケーションでも問題になります。

例えば、`mousemove` や `pointermove` イベントは1秒間に数十回発火します。各イベントがリアクティブパイプラインを駆動する場合（ドラッグ&ドロップ、ツールチップの位置計算、キャンバスアニメーションなど）、更新ごとのオーバーヘッドがイベント発生頻度に比例して増大します。チェーンの深さが増すと差は劇的になります： [スループットデモ](/mono/synstate/ja/guides/library-comparison/interactive-demo/#throughput-per-update-overhead-under-load)（depth-100 チェーン、フレームあたり500回更新）では、Jotai では ms/frame が 16ms を超えて目に見えるカクつきが生じる一方、SynState は16ms以内で安定して描画できます。

更新ごとの差が生じる根本原因：

- **SynState**： `setCounter(i)` → `doubled` の map 関数を呼び出し → `quadrupled` の map 関数を呼び出し → subscriber を呼び出し。フレームワークによる管理処理を伴わない、3回の直接関数呼び出しのみ。
- **Jotai**： `store.set(counterAtom, i)` → DFS 無効化（WeakSet アロケーション + Map 書き込み）→ DFS トポロジカルソート（WeakSet アロケーション + 配列 push + reverse）→ `doubledAtom` の再計算（Map 検索 + エポックチェック + Map 書き込み）→ `quadrupledAtom` の再計算（同上）→ コールバックをフラッシュ → `store.get(quadrupledAtom)`（キャッシュ検索）。

{/* bench:derived-chain/updates */}100,000{/* /bench */}回のイテレーションにわたって、SynState は3回の関数呼び出しが処理の大半を占める一方、Jotai では更新ごとの管理処理（Map/WeakSet アロケーション、エポック比較、2回の DFS トラバーサル）が蓄積され、観測される約{/* bench:derived-chain/jotai-over-synstate */}46{/* /bench */}倍の差になります。
