SynState はどのシナリオでも最速のライブラリの {/* bench:summary/synstate-worst-over-fastest */}2.4{/* /bench */} 倍以内に収まっている一方、各シナリオの最遅のライブラリは最速の {/* bench:summary/slowest-over-fastest-least */}43{/* /bench */} 倍以上かかっています。各シナリオが何に負荷をかけているかは、それぞれのセクションで説明しています。

※1 RxJS は glitch-free ではありません。ダイヤモンドでは、subscriber が古い値と新しい値の混ざった組み合わせも受け取ります（[RxJS グリッチ](#シナリオ-ダイヤモンド依存関係)）。glitch の起きないライブラリの中では {/* bench:summary/diamond-fastest-glitch-free */}Preact Signals{/* /bench */} が最速です。

1 更新あたり：その行の時間を更新回数で割ったものです。タイムアウトしたライブラリは > を付けた下限です。ディープチェーン以外のシナリオは計測の中でグラフも構築するため、その分も含みます。カスケードダイアモンドは 1 つのグラフで 100 回しか更新せず、時間のほとんどが構築なので、表示していません（—）。比が大きくても時間の差は小さいことがあり、この列がそのどちらかを示します。

※3 ほかのライブラリと同じ条件で実装できるシナリオでのみ計測しているため、最悪のケースはそれらのシナリオの中でのものです。Zustand と Valtio は派生値のノードを持たないため、単一ステートにのみ参加しています（[公平性に関する注記](#公平性に関する注記)を参照）。

強調した倍率は、すべてのシナリオで計測したライブラリのうち、最悪のケースでも1桁倍に収まっているものです。

条件付きファンアウトでは、※2 と同じく SynState と RxJS を `switchMap` で書いた形で数えています。

計測結果から言えること：

- **SynState の更新ごとのオーバーヘッドは中程度で、最小ではありません。** 何も派生しない場合（単一ステート）、どのライブラリも値を保持して subscriber を1つ呼ぶだけなので、9つすべてを同じ条件で比べられるのはこのシナリオだけです。SynState に対して、Zustand は {/* bench:single-state/zustand-over-synstate */}1.2{/* /bench */}倍、Preact Signals は {/* bench:single-state/preact-signals-over-synstate */}1.2{/* /bench */}倍、Solid は {/* bench:single-state/solid-over-synstate */}6.5{/* /bench */}倍、Valtio は {/* bench:single-state/valtio-over-synstate */}11{/* /bench */}倍、MobX は {/* bench:single-state/mobx-over-synstate */}13{/* /bench */}倍、Redux は {/* bench:single-state/redux-over-synstate */}27{/* /bench */}倍、Jotai は {/* bench:single-state/jotai-over-synstate */}41{/* /bench */}倍の時間がかかります。小さな派生グラフでは、順序付けの手順を持たずに `subscribe` 呼び出しを連ねるだけの RxJS は、派生チェーンで SynState {/* bench:compare/derived-chain/rxjs-speed */}より高速{/* /bench */}（{/* bench:derived-chain/rxjs-over-synstate */}0.5{/* /bench */}倍）、ダイヤモンドで SynState {/* bench:compare/diamond/rxjs-speed */}とほぼ同じ速さ{/* /bench */}（{/* bench:diamond/rxjs-over-synstate */}0.8{/* /bench */}倍）です。各ノードの依存リストを実行から実行へ使い回す Preact Signals は、派生チェーン（{/* bench:derived-chain/preact-signals-over-synstate */}0.9{/* /bench */}倍）とダイヤモンド（{/* bench:diamond/preact-signals-over-synstate */}1.0{/* /bench */}倍）のどちらでも SynState {/* bench:compare/derived-graphs/preact-signals-speed */}とほぼ同じ速さ{/* /bench */}です。Solid・MobX・Jotai・Redux は SynState {/* bench:compare/derived-graphs/heavy-speed */}より低速{/* /bench */}です。
- **SynState の更新ごとのコストはグラフの形によって爆発しません。** これが、順序付けの手順を持たないプッシュベースのライブラリである RxJS との違いです。ソースが1回更新されるたびに、更新が届くノードを深さ順に1回ずつ訪れ、そこに至る経路がいくつあっても各 subscriber を1回だけ呼ぶので、ダイヤモンドがあっても発行回数は増えません。同じくプッシュベースの Solid は、更新が届くノードをすべて印付けしてから再実行するので、やはり各ノードを1回ずつ実行します。RxJS は経路ごとに発行します。ディープチェーンを4倍深くすると（$K = 1000$ で $M = 50 \to 200$）、SynState の時間は {/* bench:summary/deep-chain-synstate-growth */}3.8{/* /bench */} 倍、Solid は {/* bench:summary/deep-chain-solid-growth */}4.2{/* /bench */} 倍、Preact Signals は {/* bench:summary/deep-chain-preact-signals-growth */}6.1{/* /bench */} 倍、Jotai は {/* bench:summary/deep-chain-jotai-growth */}4.1{/* /bench */} 倍、MobX は {/* bench:summary/deep-chain-mobx-growth */}4.0{/* /bench */} 倍、Redux は {/* bench:summary/deep-chain-redux-growth */}2.2{/* /bench */} 倍ですが、RxJS は {/* bench:summary/deep-chain-rxjs-growth */}19{/* /bench */} 倍になり、カスケードダイアモンドでは {/* bench:cascaded-diamond/rxjs-timeout-n-math */}$N=14${/* /bench */} で計測を完了できなくなります。RxJS の中間発行は[グリッチ](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)でもあり、subscriber は古い値と新しい値が混ざった組み合わせを受け取ります。
- **MobX・Jotai・Preact Signals・Solid が省略しているのは、グラフが持つ必要のなかった処理です。** 前の3つは派生値を何かに読まれたときにだけ再計算するので、誰も読まないノードのコストはゼロです。Solid のメモは SynState の派生値と同じく先行評価されますが、メモは直前の実行で読んだものだけを購読するので、読まなかったソースには通知先がありません。SynState は、ソースが更新されるたびに持っている派生値をすべて評価します。これは `next` が返った時点ですべての `getSnapshot()` が整合している、ということの代償で、何を計算するかは誰が読むかではなくグラフの書き方で決まります。条件付きファンアウトはそのために作られたシナリオです。`derive` が、セレクターが一度も選ばない千個のブランチを抱えているのです。選択中のブランチだけを購読する `switchMap` で書けば、SynState はどのブランチ数でも約 {/* bench:fan-out/synstate-switch-map-typical */}1.8 ms{/* /bench */} のままです。アプリケーションで出会う「誰も読まないノード」も同じ種類のもので、それぞれグラフから外す素直な方法があります。選ばれていないブランチは `switchMap`、画面にないビューはその observable をスコープ内で作ってビューと一緒に dispose、表示されるより頻繁に書かれる値はその手前に `audit` や `throttle` を置く、という具合です。各ライブラリがこの処理をいつ行うかは[評価モデル](/mono/synstate/ja/guides/library-comparison/library-comparison/#評価モデル)を参照してください。
- **Preact Signals の最悪ケースは最速のライブラリの {/* bench:summary/preact-signals-worst-over-fastest */}2.0{/* /bench */}倍で、SynState は {/* bench:summary/synstate-worst-over-fastest */}2.4{/* /bench */}倍です。** MobX や Jotai と同じプルベースですが、前回と同じものを読む実行は何もアロケートしないので（[分析](#preact-signals-バージョン番号と使い回される依存リンク)を参照）、更新ごとのオーバーヘッドは単一ステート・派生チェーン・ダイヤモンドのいずれでも SynState {/* bench:compare/small-graphs/preact-signals-overhead */}と同程度{/* /bench */}です。
- **SynState のグラフ構築は低コストです。** カスケードダイアモンドは毎回の計測の中でグラフを構築しますが、SynState の行は $N$ に対して{/* bench:compare/cascaded-diamond/synstate-growth */}ほぼ横ばいです{/* /bench */}。新しいノードは親と、親から受け継いだルートに登録されるだけで、ルートまでの $2^N$ 本の経路をたどることはありません。ディープチェーンのように一度作ったグラフを何度も更新する場合、構築は更新ごとのコストにまったく含まれません。

したがって、このページから言えるのは「SynState は速い」よりも狭いことです。SynState はグリッチフリーで、グラフの形によらず更新ごとのコストがグラフの大きさに比例したままです。これは Solid と Preact Signals も同じで、RxJS は違います。小さなグラフでの更新ごとのオーバーヘッドは、Solid・MobX・Jotai・Redux {/* bench:compare/small-graphs/synstate-vs-heavy-overhead */}よりかなり小さい{/* /bench */}です。Preact Signals {/* bench:compare/small-graphs/synstate-vs-preact-signals-overhead */}と同程度{/* /bench */}です。単一ステートでは Zustand {/* bench:compare/single-state/synstate-vs-zustand-overhead */}と同程度{/* /bench */}です。RxJS {/* bench:compare/small-graphs/synstate-vs-rxjs-overhead */}と同程度かそれより大きい{/* /bench */}です。SynState が最も遅れるのは{/* bench:summary/worst/synstate-scenario */}[条件付きファンアウト](#シナリオ-条件付きファンアウト)（B=1000）{/* /bench */}で、そこで最速のライブラリの {/* bench:summary/synstate-worst-over-fastest */}2.4{/* /bench */}倍ですが、{/* bench:summary/synstate-worst-explained */}これはすでに誰も読まない分岐を持たない `switchMap` の形での数字です。残っているのは、どのノードにも届かない書き込みの SynState でのコストです{/* /bench */}。最初の2つの性質を共有する Preact Signals に対しては、{/* bench:compare/preact-signals-winner */}これらの結果に一貫した勝者はありません{/* /bench */}。Preact Signals の時間は SynState に対して単一ステートで {/* bench:single-state/preact-signals-over-synstate */}1.2{/* /bench */}倍、ディープチェーン（$K=1000$、$M=200$）で {/* bench:deep-chain/preact-signals-over-synstate@k1000-m200 */}1.2{/* /bench */}倍、ダイヤモンドでは {/* bench:diamond/preact-signals-over-synstate */}1.0{/* /bench */}倍です。Preact Signals との違いは、`debounce`・`throttle`・`switchMap` などのオペレーターを同じグリッチフリーなグラフの上で使えることです（[SynState の強み](/mono/synstate/ja/guides/why-synstate/#グリッチフリーでコストは線形)）。

## シナリオ： 単一ステート

ステート1つ、subscriber 1つ、派生値なし。他のすべてのシナリオの土台となる下限で、Zustand と Valtio が参加するのはこのシナリオだけです。両者のバニラ API には派生値のノードがないため、派生値のあるグラフでは subscriber の中でインライン計算するしかなく、それは他のライブラリが構築するグラフとは別の、より小さなグラフになります。

- ループ： counter を $1$ から $N$ まで同期的に更新（$N = 10^5$）.
- 検証： 最終値 $= N$.
- 各ライブラリの subscriber は渡された値を記録します。コールバックに値が渡されない場合（Jotai、Redux、Valtio）はストアから読み直します。Solid と Preact Signals は、シグナルを読む effect で購読します。

```tsx
        return { setCounter: setCounterValue, dispose: disposeRoot };
    });

    for (let mut_i = 1; mut_i <= n; mut_i++) {
        setCounter(mut_i);
```
```tsx
    }

    dispose();

    return mut_lastValue;
};
```

## シナリオ： ディープチェーンスループット

最初の2つのシナリオは固定サイズのグラフを使用しています。このシナリオは[スループットのインタラクティブデモ](/mono/synstate/ja/guides/library-comparison/interactive-demo/#スループット-負荷時の更新ごとのオーバーヘッド)と同じトポロジーを使用します： depth-$M$ の `scan` チェーンで、各ステージが前のステージに向かって lerp し、`combine` が**すべての $M+1$ 個の出力**を読み取ります。$K$ 回のソース更新を同期的に実行します（アニメーションフレームあたり $K$ 回の更新をシミュレート）。

以下の図は $M = 3$ の場合のグラフ構造です。実際のベンチマークでは $M$ は $50$〜$200$ です：

<DeepChainDepGraph />

- $K$（計測あたりの更新回数）： $100$, $500$, $1000$.
- $M$（チェーンの深さ）： $50$, $100$, $200$.
- Zustand と Valtio は、派生値のあるほかのシナリオと同じく除外（[公平性に関する注記](#公平性に関する注記)を参照）。

:::caution[RxJS がソース更新1回あたり $O(M^2)$ になる理由]
`combineLatest` は $M+1$ 個の入力（source + $M$ 個の scan ステージ）すべてを subscribe しています。source が新しい値を発行すると、RxJS の深さ優先伝播により以下のカスケードが発生します：

1. **source** が発行 → `combineLatest` が実行（**1回目**の subscriber 呼び出し。scan₁〜scanₘ はまだ古い値）
2. source の変更が **scan₁** に伝播 → scan₁ が発行 → `combineLatest` が実行（**2回目**。scan₂〜scanₘ はまだ古い値）
3. scan₁ の変更が **scan₂** に伝播 → scan₂ が発行 → `combineLatest` が実行（**3回目**）
4. …チェーン全体を通じてこれが繰り返される…
5. **scanₘ** が発行 → `combineLatest` が実行（**$M+1$ 回目** — ここで初めてすべての値が最新）

$M+1$ 回の `combineLatest` 発行のそれぞれが subscriber を呼び出し、subscriber は $M+1$ 個の値を処理します → **呼び出し1回あたり $O(M)$**。したがってソース1回の更新コストは $O(M) \times (M+1)$ = **$O(M^2)$** です。

SynState の `combine` は、すべての親がその更新で確定してから訪れられるため、**ソース更新1回あたり subscriber 呼び出し1回、合計 $O(M)$** です。
:::

## シナリオ： 条件付きファンアウト

これまでのシナリオは伝搬スループットをテストしていました — すべてのソース更新が subscriber に到達します。このシナリオは異なるパターンをテストします： **購読セットに含まれない observable への更新コスト** — 動的依存追跡が最も有利に働くケースであり、MobX や Jotai の動作モデルを確かめるためのシナリオです。

グラフには B 個の分岐とセレクターがあります。セレクターは、結果がどの分岐を読むかを選ぶ source で、結果は `branch[selector]` です。セレクターはベンチマーク中ずっと $0$ に固定されており、`branch[0]` のみが「アクティブ」です。ベンチマークでは **`branch[1]`**（非アクティブな分岐）を $K = 10^5$ 回更新します。

<ConditionalFanOutDepGraph />

このシナリオの核心は、ライブラリによって **`branch[1]` の observer リスト（購読者の有無）が異なる** 点です：

- **SynState と RxJS を `switchMap` で（「(switchMap)」の行）**： `selector.pipe(switchMap((sel) => branches[sel]))` は選択中の分岐だけを購読し、セレクターが変われば別の分岐に購読を移すので、下の動的購読と同じく `branch[1]` に observer はいません。SynState と RxJS では、動的な依存関係はこう書きます。
- **同じ2つを愚直に静的購読で（「(naive …)」の行、グラフでは点線）**： セレクターと全分岐に対する `derive`（SynState）や `combineLatest`（RxJS）が構築時に全分岐を購読するため、`branch[1]` にも observer が登録されています。`branch[1]` が更新されるたびにそのノードが発火し、射影関数が前回と同じ値を生成し、等値比較で下流への伝搬を防止します。更新のたびに B 個の分岐をすべて読むため、コストは B に比例します。これらの行は誰も読まない分岐を抱えるコストを示すためのもので、どちらのライブラリでも想定された書き方ではありません。
- **動的購読（Jotai, MobX, Solid, Preact Signals）**： `computed`、メモ、派生 atom の関数が**直前の実行で**実際に読んだ observable だけを購読します。`selector = 0` のとき `branch[0].get()` のみが呼ばれるため、`branch[1]` の observer リストは**空**です。`branch[1]` を更新しても、通知先が存在しないため何も起きません。
- **単一ストア（Redux）**： 分岐ごとの購読というものがそもそもありません。dispatch のたびに、どの分岐を変えたかによらず reducer が走ってすべての subscriber が呼ばれ、subscriber のセレクターは選択中の分岐だけを読みます。書き込み自体が `branches` 配列をコピーするので、コストの一部は B に比例します。

### 結果

### 主な観察結果

- **MobX**・**Solid**・**Preact Signals** はこのシナリオで最も高速です。`computed(() => branches[selector.get()].get())` は実行時に `selector` と `branches[0]` のみを購読するため、`branches[1]` の observer リストは空です。`branches[1]` を更新しても通知先が存在せず、B に関係なく一定です。MobX は約 {/* bench:fan-out/mobx-typical */}1.4 ms{/* /bench */}、Solid は約 {/* bench:fan-out/solid-typical */}0.7 ms{/* /bench */}、Preact Signals は約 {/* bench:fan-out/preact-signals-typical */}1.1 ms{/* /bench */} です。残るのは、observer のいない書き込みそのもののコスト、つまり値の比較と、Preact Signals ではバージョンの更新です。
- **`switchMap` の SynState** は B に関係なく約 {/* bench:fan-out/synstate-switch-map-typical */}1.8 ms{/* /bench */}、**`switchMap` の RxJS** は約 {/* bench:fan-out/rxjs-switch-map-typical */}2.9 ms{/* /bench */} のままです。`branch[1]` の更新はどちらでもどのノードにも届きません。SynState ではそもそも更新を開きません。`branch[1]` には子も購読者もないので、書き込みは値を保存して戻ります。Solid で誰も observe していないシグナルへの書き込みと同じです。
- **愚直に書いた SynState** のコストは B に対して線形に増加します。`derive` が構築時に全分岐を購読するため、どの分岐が更新されても発火します。点線で線形な傾向が見えます：B=2 で {/* bench:fan-out/synstate-naive@min-b */}10.6 ms{/* /bench */}、B={/* bench:fan-out/last-measured-b */}1000{/* /bench */} で {/* bench:fan-out/synstate-naive@last-measured-b */}630 ms{/* /bench */}（{/* bench:fan-out/updates-math */}$K = 100{,}000${/* /bench */} 回の更新にわたり、1分岐・1更新あたり約 {/* bench:fan-out/synstate-naive-ns-per-branch-per-update */}6{/* /bench */} ns）。この行が計測しているのは、それを書いた全分岐の `derive` であって、モデルの限界ではありません。
- **愚直に書いた RxJS** は同じ静的なアプローチを `combineLatest` で取ります。コストは B に応じて増加しますが、愚直な SynState より緩やかです。`combineLatest` は等値比較による下流伝搬スキップを行わず常に発行するため、subscriber は毎回呼ばれますが処理は最小限（値の代入のみ）です。
- **Jotai** は MobX と同じ動的購読を行います — `resultAtom` は非アクティブな分岐を購読していないため再計算はトリガーされません。しかし `store.set()` 自体が atom store 内で invalidation チェック等の管理処理を実行するため、B に関係なく約 {/* bench:fan-out/jotai-typical */}138 ms{/* /bench */} の一定オーバーヘッドが発生します。このため B≤{/* bench:fan-out/jotai-slower-through-b */}200{/* /bench */} では愚直な SynState よりも遅い結果です。
- **Redux** は B=2 で {/* bench:fan-out/redux@min-b */}146 ms{/* /bench */}、B={/* bench:fan-out/last-measured-b */}1000{/* /bench */} で {/* bench:fan-out/redux@last-measured-b */}197 ms{/* /bench */} です。大部分は B によらず更新ごとにかかる dispatch と subscriber の呼び出しで、B とともに増えるのは `branches` 配列のコピーです。

    :::note[このベンチマークは動的購読に有利な恣意的シナリオです]
    このベンチマークは静的購読と動的購読の理論的な特性の違いを示すために設計されたものであり、**動的購読側に最も有利な条件**を意図的に構成しています。それでも、静的購読側も `switchMap` を使った自然な実装なら数ミリ秒に収まります。どのブランチ数でも、{/* bench:fan-out/updates-math */}$K = 100{,}000${/* /bench */} 回の更新で SynState は約 {/* bench:fan-out/synstate-switch-map-typical */}1.8 ms{/* /bench */}、RxJS は約 {/* bench:fan-out/rxjs-switch-map-typical */}2.9 ms{/* /bench */} で、MobX は約 {/* bench:fan-out/mobx-typical */}1.4 ms{/* /bench */}、Solid は約 {/* bench:fan-out/solid-typical */}0.7 ms{/* /bench */} です。

    現実のアプリケーションにおいて、selector が固定されたまま非アクティブな分岐だけが大量に更新され続けることは考えにくいです。もし使われていないデータが頻繁に更新される状況が発生しているなら、それはライブラリの購読モデルの問題ではなく、アプリケーション側の設計の問題です。例えば、表示されていないチャンネルの WebSocket データを購読し続けている場合、ライブラリの選択に関係なく、不要な購読自体を停止すべきです。

    また、このベンチマークでは selector の切り替えを行っていません。現実のアプリケーションでは selector が変わるたびに MobX・Jotai・Solid・Preact Signals は購読セットの再構築（古い購読の解除 + 新しい購読の登録）が必要ですが、そのコストはここには含まれていません。
    :::

#### SynState (`switchMap`)

```tsx
export const runBenchmark = (k: number, branchCount: number): number => {
    const [selector] = createState(0);

    const branches: DeepReadonly<
        {
            source: Observable<number>;
            set: (v: number) => void;
        }[]
    > = Arr.zeros(asUint32(branchCount)).map(() => {
        const [source, setSource] = createState(0);

        return { source, set: setSource };
    });

    // Dynamic dependency: only follows the branch selected by selector
    const result = selector.pipe(
        switchMap((sel) => branches[sel]?.source ?? just(0)),
    );

    let mut_lastValue = 0;

    const subscription = result.subscribe((v) => {
        mut_lastValue = v;
    });

    // Update an INACTIVE branch (branch 1, while selector = 0)
    const inactiveBranch = branches[1];

    if (inactiveBranch === undefined) {
        throw new Error('need at least 2 branches');
    }

    for (let mut_i = 1; mut_i <= k; mut_i++) {
        inactiveBranch.set(mut_i);
    }

    subscription.unsubscribe();

    return mut_lastValue;
};
```

```tsx
export const runBenchmark = (k: number, branchCount: number): number => {
    type State = Readonly<{
        selector: number;
        branches: readonly number[];
    }>;

    const setBranch =
        createAction<Readonly<{ index: number; value: number }>>(
            'fanOut/setBranch',
        );

    const isSetBranch = isAnyOf(setBranch);

    const initialState: State = {
        selector: 0,
        branches: Arr.zeros(asUint32(branchCount)),
    } as const;

    // A plain reducer rather than `createSlice`: an Immer draft of the
    // `branches` array would be finalized element by element on every update,
    // and that would be measured as Redux's cost.
    const store = configureStore({
        reducer: (
            state: State | undefined,
            action: Readonly<UnknownAction>,
        ): State => {
            const current = state ?? initialState;

            return isSetBranch(action)
                ? {
                      ...current,
                      branches: current.branches.with(
                          action.payload.index,
                          action.payload.value,
                      ),
                  }
                : current;
        },
        middleware: () => new Tuple(),
    });

    // Reads only the branch the selector picks. Every update replaces the
    // `branches` array, so this recomputes on each one — an index lookup.
    const selectResult = createSelector(
        (state: State) => state.selector,
        (state: State) => state.branches,
        (sel, branches) => branches[sel] ?? 0,
        { memoize: lruMemoize },
    );

    let mut_lastValue = selectResult(store.getState());

    store.subscribe(() => {
        mut_lastValue = selectResult(store.getState());
    });

    // Update an INACTIVE branch (branch 1, while selector = 0)
    for (let mut_i = 1; mut_i <= k; mut_i++) {
        store.dispatch(setBranch({ index: 1, value: mut_i }));
    }

    return mut_lastValue;
};
```

## 測定方法

- **ウォームアップ**： 5ラウンド（破棄）。
- **測定**： 20ラウンド。
- $N$： 1ラウンドあたり $10^5$ 回の更新。
- **タイミング**： `performance.now()`（サブミリ秒精度）。
- **分離**： 各行はそれぞれ別の Node プロセスで計測しています。V8 は関数をそれまでに見た形に合わせて最適化するので、1つのプロセスを共有すると、ある行は前の行が教えたことを引き継ぎ、その数値はどの行が先に走ったかで変わります。
- **ビルド**： SynState を含むすべてのライブラリを本番ビルド（`NODE_ENV=production`）で実行しています。アプリケーションが配布するのはこちらなので、開発時のみのチェックは測定に含まれません。例外は Valtio で、その ES モジュールビルドは `import.meta.env.MODE` を読みますが、これはバンドラが定義するもので Node は定義しません。残る開発時チェックは購読の作成時とネストしたプロキシの接続時にだけ実行され、更新ごとには実行されません。
- **統計**： 中央値、最小、最大、p95、ops/sec（中央値に基づく）。最初の3シナリオには、各中央値を SynState の中央値で割った「vs SynState」（SynState の何倍かかったか）も載せています。

### 公平性に関する注記

- **Redux**： デフォルトのミドルウェア（thunk、シリアライザブルチェック、イミュータビリティチェック）は `middleware: () => new Tuple()` で無効化されています。これらは本番ビルドでは tree-shaking で除去される開発時チェックです。
- **Redux**（ディープチェーン、条件付きファンアウト）： reducer は `createSlice` の reducer ではなく、`createAction` と照合するプレーンな関数です。$M$ 個の点や $B$ 個の分岐の Immer ドラフトが更新のたびに作られ要素ごとに確定されると、ストアではなく Immer を計測することになるためです。最初の3つのシナリオはステートが数値1つなので `createSlice` のままです。
- **Redux**（ディープチェーン）： セレクターは自身の前回の出力を読めないため、`scan` チェーンは各ステージの保存された位置を回す reducer のループです。MobX と同じく命令的なコードで、Redux の行はそれを計測しています。
- **Zustand** と **Valtio**（単一ステートのみ）： どちらのバニラ API にも派生値のノードがないため（Valtio の `derive` は別パッケージ）、他のシナリオでは派生値を subscriber 内でインライン計算するしかありません。それは他のライブラリが構築するグラフよりノードが少なく、同じ計測になりません。そのため、どのライブラリも何も派生しないシナリオにだけ参加します。Valtio の `subscribe` の第3引数 `true` は通知を同期にし、すべてのミューテーションで subscriber が呼ばれるようにします（Valtio はデフォルトで非同期にバッチ処理します）。
- **RxJS**（ダイヤモンド、カスケードダイアモンド、条件付きファンアウトの愚直な行）： `combineLatest` はタプルを作り、続く `map` がそれを値に変えるので、合流1つが2ノードになります。SynState の `derive`、MobX の `computed`、Jotai の派生 atom では1ノードです。合流ごとにノード1つと配列1つ分のコストがかかりますが、RxJS では合流はこう書きます。
- **MobX**（ディープチェーン）： `computed` は自身の前回の出力を読めないため、`scan` チェーンは `observable.box` の列として書き、1つの `reaction` が1つのアクション内でループして更新します。これは派生ノードのチェーンではなく命令的なコードで、MobX の行はそれを計測しています。
- **RxJS**（ダイヤモンド依存関係）： `combineLatest` は[グリッチ問題](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)により、ソース更新ごとに subscriber を2回発火させます。ベンチマークはこの追加作業を含むウォールクロック時間を測定しており、RxJS におけるダイヤモンド依存関係の実際のコストを反映しています。
- **Solid**： シナリオは `solid-js/dist/solid.js`、つまりバンドラーがブラウザ向けに選ぶビルドを import しています。`solid-js` のルートの export は Node の `node` 条件ではサーバービルドに解決され、そこではメモは1回だけ計算されて effect は一度も実行されないため、この Node でのベンチマークでは何も計測できません。関数はアプリケーションが `solid-js` から import するものと同じです。グラフはすべて `createRoot` の中で作り（これで dispose できます）、subscriber は `createEffect` です。計測しているのは Solid 1.9 です。コアを `@solidjs/signals` として単独で公開する Solid 2.0 は、執筆時点ではリリース候補でした。
- **Solid**（ディープチェーン）： `scan` の各ステージは前回の値を受け取るメモ（`createMemo(fn, initialValue)`）で、Solid 自身のアキュムレータの書き方です。
- **Preact Signals**： Preact に依存しないパッケージ `@preact/signals-core` を使っています。subscriber は `effect` です。値を渡す `signal.subscribe(fn)` も内部では effect です。
- **Preact Signals**（ディープチェーン）： `computed` には前回の値が渡されないため、`scan` チェーンは1つの effect が `batch` の中で進めるシグナルの列で、各ステージは `peek` で読みます。MobX の `reaction` と同じ形です。前回の値をクロージャに保持する `computed` もここでは動きます（毎回の更新ですべてのステージが読まれるため）が、それはライブラリが何回評価するかに依存する書き方で、MobX の行もそうは書いていません。
- **MobX**： 他のライブラリの subscribe-and-record パターンに合わせるため、`autorun` ではなく `reaction` を使用しています。MobX の strict mode で要求されるとおり、`runInAction` で各ミューテーションをラップしています。
- **Jotai**： `store.sub()` はコールバックに現在の値を渡さないため、リスナー内で追加の `store.get()` 呼び出しが必要です。初期値もsubscribe前に `store.get()` で読み取られます。
- ディープチェーン以外では、すべてのライブラリがベンチマーク関数内でステート、派生値、およびsubscriptionを作成するため、セットアップコストは測定に含まれています。ディープチェーンはタイマーを開始する前にグラフを構築します。
- **条件付きファンアウト**： SynState と RxJS は、全ブランチに対する静的な `derive` / `combineLatest` で愚直に書いた形（「(naive …)」の行）と、MobX・Jotai・Solid・Preact Signals と同じく選択中のブランチだけを購読する `switchMap` の2通りで計測しています。

## 分析： 各ライブラリの時間はどこに使われているか

[ライブラリごとの表](#このページの読み方)の各行は、そのライブラリが更新のたびに行う処理から来ています。この節では、その処理を各ライブラリのソースから読んだとおりに説明し、どのシナリオに現れるかを示します。SynState が更新で行うことは[更新を 1 ステップずつ追う](/mono/synstate/ja/internals/tracing-an-update/)で順に追っています。

### RxJS： 経路ごとに1回の発行

RxJS の更新ごとの処理はわずかです。`next` は各 subscriber を深さ優先で直接呼び、順序付けの手順も管理処理もありません。単一ステート・派生チェーン・ダイヤモンドで最速の一角にいるのはそのためです。RxJS がしないのは、待つことです。`combineLatest` は入力のどれか1つが発行した時点で発行するので、$P$ 本の経路が届くノードはソース更新1回につき $P$ 回発行し、その下流はそのたびに動きます。これが[ディープチェーン](#シナリオ-ディープチェーンスループット)の $O(M^2)$ と、{/* bench:summary/rxjs-worst-label */}RxJS の最悪の行である{/* /bench */}[カスケードダイアモンド](#シナリオ-カスケードダイアモンド)の $O(2^N)$ です。最後の1回を除くすべての発行は[グリッチ](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)です。

### MobX： 実行のたびの依存追跡

書き込みは `runInAction` の中での observable への代入で、`box.set` か、`observable` オブジェクトのプロパティへの代入（その裏の box に set されます）です。アクションがバッチを開き、set が値を比較してすべての observer を stale にし（`propagateChanged`）、バッチが閉じると stale になった reaction がそれぞれ再実行されます。実行はすべて追跡されます。MobX は新しい依存配列を確保し、実行中の `.get()` をすべて記録し、その結果を前回の実行のリストと比較して（`bindDependencies`）、差分のある observer を追加・削除します。この固定コストが、単一ステートでの MobX の{/* bench:single-state/mobx-over-synstate */}13{/* /bench */}倍です。

{/* bench:summary/mobx-worst-label */}MobX の最悪の行である{/* /bench */}[ディープチェーン](#シナリオ-ディープチェーンスループット)では、`scan` のステージは1つのアクションの中で1つずつ set される `observable.box` で、その $M+1$ 個すべてを読む `autorun` が更新のたびに再実行され、$M+1$ 個の依存を追跡し直します。何も実行する必要がないところ、つまり誰も読まない `computed` や誰も観測しない分岐では MobX は何もしません。条件付きファンアウトで最速の一角にあり、最後の `computed` だけを `reaction` が読むカスケードダイアモンドで、$N$ が増えても SynState に近く、典型的には SynState の {/* bench:cascaded-diamond/mobx-over-synstate-typical */}2.6{/* /bench */}倍（$N$ ごとの比の中央値）にとどまるのはそのためです。

### Jotai： `set` のたびのグラフ解決

Jotai はグリッチフリーで、そのコストは**更新ごとのフレームワークオーバーヘッド**、つまり Jotai のストアが `store.set()` の呼び出しごとに、さらにその呼び出しが再計算する atom ごとに実行する処理量です。ほかのライブラリのする処理が最も少ないところで最もよく現れ、最悪の行は{/* bench:summary/worst/jotai-scenario */}[条件付きファンアウト](#シナリオ-条件付きファンアウト)（B=1000）{/* /bench */}です。{/* bench:summary/jotai-worst-explained */}誰も読まない分岐への書き込みは MobX・Solid・Preact Signals にはほとんど何のコストもかかりませんが、Jotai には `store.set()` 1回分がまるごとかかります{/* /bench */}。

#### 更新ごとのコスト内訳

`store.set(counterAtom, i)` が呼び出されると、Jotai のストアは以下のステップを実行します：

1. **値の更新** — 新しい値を書き込み、`Object.is` で比較。$O(1)$。
2. **無効化パス**（`invalidateDependents`）— マウントされたすべての依存先の DFS トラバーサル。`Map<Atom, EpochNumber>` でのエポック番号追跡により各ノードを「再計算が必要」とマーク。$O(N)$（$N$ = 影響を受ける atom の数）。
3. **トポロジカルソート**（`recomputeInvalidatedAtoms`）— 訪問追跡に `WeakSet` を使用した2回目の DFS 後順トラバーサル。正しい順序の再計算リストを生成。$O(N)$。
4. **再計算** — トポロジカル順序の各 atom に対して `read` 関数を実行。read 関数内で、各 `get(dep)` 呼び出しは： (a) 依存先の `AtomState` を検索、(b) エポック番号を比較して古さをチェック、(c) 将来の無効化のために `Map` に依存関係を記録。コストは $O(\sum D_i)$ — 再計算されるすべての atom の直接依存の合計であり、積ではない。各1つの依存を持つ N 個の atom のチェーンでは $O(N)$。
5. **subscriber 通知** — リスナーコールバックを発火。Jotai の `store.sub()` は新しい値を渡さないため、コールバックは `store.get()` を再度呼び出す必要があり、追加のキャッシュ検索が発生する。リスナーあたり $O(1)$ だが、追加のトラバーサルが1回発生。

#### SynState との比較

| ステップ                    | SynState                                             | Jotai                                                           |
| --------------------------- | ---------------------------------------------------- | --------------------------------------------------------------- |
| **グラフの解決**            | 深さは構築時に確定し、更新は深さ順のキューで進む     | `store.set()` のたびに（ステップ2-3）                           |
| **伝搬**                    | 直接関数呼び出し。子は発行したノードがキューに入れる | getter spy + `Map`/`WeakSet` 操作を伴う `read` 関数実行         |
| **依存関係の追跡**          | 静的（構築時に設定）                                 | 動的（getter spy を通じて評価のたびに再検出）                   |
| **鮮度チェック**            | 不要（プッシュ型）                                   | `get()` 呼び出しごとのエポック番号比較                          |
| **subscriber への値の配送** | 値がコールバックに直接渡される                       | コールバックが値を読むために `store.get()` を呼び出す必要がある |

#### 定数倍の差が見えるケース

ベンチマークのループは更新ごとの差を測定可能にするために{/* bench:derived-chain/updates */}100,000{/* /bench */}回の更新を実行しています。しかし、この定数倍のコストは高頻度イベントを扱う実際のアプリケーションでも問題になります。

例えば、`mousemove` や `pointermove` イベントは1秒間に数十回発火します。各イベントがリアクティブパイプラインを駆動する場合（ドラッグ&ドロップ、ツールチップの位置計算、キャンバスアニメーションなど）、更新ごとのオーバーヘッドがイベント発生頻度に比例して増大します。チェーンの深さが増すと差は劇的になります： [スループットデモ](/mono/synstate/ja/guides/library-comparison/interactive-demo/#スループット-負荷時の更新ごとのオーバーヘッド)（depth-100 チェーン、フレームあたり500回更新）では、Jotai では ms/frame が 16ms を超えて目に見えるカクつきが生じる一方、SynState は16ms以内で安定して描画できます。

更新ごとの差が生じる根本原因：

- **SynState**： `setCounter(i)` → `doubled` の map 関数を呼び出し → `quadrupled` の map 関数を呼び出し → subscriber を呼び出し。3回の関数呼び出しで、管理処理はノードごとのバケットへの追加と更新ごとのキューオブジェクト1つだけ。
- **Jotai**： `store.set(counterAtom, i)` → DFS 無効化（WeakSet アロケーション + Map 書き込み）→ DFS トポロジカルソート（WeakSet アロケーション + 配列 push + reverse）→ `doubledAtom` の再計算（Map 検索 + エポックチェック + Map 書き込み）→ `quadrupledAtom` の再計算（同上）→ コールバックをフラッシュ → `store.get(quadrupledAtom)`（キャッシュ検索）。

{/* bench:derived-chain/updates */}100,000{/* /bench */}回のイテレーションにわたって、SynState は3回の関数呼び出しが処理の大半を占める一方、Jotai では更新ごとの管理処理（Map/WeakSet アロケーション、エポック比較、2回の DFS トラバーサル）が蓄積され、観測される約{/* bench:derived-chain/jotai-over-synstate */}47{/* /bench */}倍の差になります。

### Redux： 1つのストア、すべての subscriber、すべての dispatch

dispatch は、Redux と Redux Toolkit が実行する順に次のステップを踏みます：

1. **アクション** — アクションクリエイターが `{ type, payload }` を確保し、`dispatch` はそれが文字列の `type` を持つプレーンオブジェクトであることを確かめます。
2. **reducer** — ルートの reducer はすべてのアクションで実行されます。`createSlice` の reducer は Immer の `produce` の中で実行され、Immer がドラフトのプロキシを作り、そこへの書き込みを記録し、ドラフトを新しいステートオブジェクトに確定します。最初の3つのシナリオの、数値1つのステートでは、これが reducer のコストの大半です。
3. **通知** — アクションが何を変えたかによらず、すべての subscriber が呼ばれます。どの subscriber が何を読むかを、ストアは記録していません。
4. **セレクター** — 各 subscriber はセレクターを通してステートを読み直します。`createSelector` のセレクターは、まず引数を自前のキャッシュで引き（デフォルトは `weakMapMemoize` で、新しいステートオブジェクトのたびにエントリを追加します）、入力セレクターを実行して結果を新しい配列に入れ、それを前回の結果と比較してから結果関数を呼びます。

{/* bench:summary/redux-worst-label */}Redux の最悪の行である{/* /bench */}[条件付きファンアウト](#シナリオ-条件付きファンアウト)は、この4ステップだけでできています。誰も選んでいない分岐への書き込みでも reducer が走り、subscriber が呼ばれてそのセレクターが実行され、最小のブランチ数でもすでに約{/* bench:fan-out/redux@min-b */}146 ms{/* /bench */}かかります。読んでいるものに購読が従う MobX・Solid・Preact Signals は、ここでは何もしません。ほかのライブラリがノードとして組むものは、Redux ではただのコード（ディープチェーンでは reducer のループ、カスケードダイアモンドではセレクターの連鎖）なので、ディープチェーンでは Redux は SynState との差が速い側にも遅い側にも{/* bench:compare/deep-chain/redux-factor-either-way */}小さな定数倍{/* /bench */}に収まり、カスケードダイアモンドでは $N$ とともに広がる差で遅れます。

### Solid： 先行評価のメモと、実行のたびに登録し直す依存

setter は新しい値を比較し（既定は `===`）、シグナルに observer がいれば更新（`runUpdates`）を開き、メモ用と effect 用の2つのキューをアロケートします。各 observer はキューに入れられて stale と印付けされ、その下流はすべて pending と印付けされます（`markDownstream`）。続いてメモのキューが実行されます。上流がまだ stale のメモは先にそれを実行し（`runTop`、`lookUpstream`）、これによってダイヤモンドの合流点は両側が更新された後の値を見ます。effect は最後に実行されます。再実行はまず、前回の実行で読んだすべてのソースからその計算を外すことから始まり（`cleanNode`）、関数が読み直すたびに各ソースへ登録し直されます。つまり MobX と同じく、依存関係は実行のたびに再発見されます。メモは先行評価です。何かに読まれているかどうかにかかわらず、ソースが変わればメモは再実行されます。

書き込みごとの2つのキューと、再実行ごとの解除と再登録が固定コストで、それが単一ステートでの {/* bench:single-state/solid-over-synstate */}6.5{/* /bench */}倍、派生チェーンでの {/* bench:derived-chain/solid-over-synstate */}5.7{/* /bench */}倍です。最悪の行は{/* bench:summary/worst/solid-scenario */}[派生チェーン](#シナリオ-派生チェーン){/* /bench */}です。誰も observe していないシグナルへの書き込みは更新そのものを省くので、Solid は条件付きファンアウトで最速の一角にいます。子も購読者もない observable への書き込みでは SynState も同じように更新を省くので、そこで両者の差になっているのはその書き込み自体のコストです。

### Preact Signals： バージョン番号と、使い回される依存リンク

`.value` への書き込みは `!==` で比較し、シグナルのバージョンとグローバルなバージョンを増やして、バッチの中でターゲットに通知します。`computed` は outdated と印付けされて通知を先へ渡し、effect はキューに入ります。最も外側のバッチが終わると、キューの各 effect は、ソースのどれかが前回見たより新しいバージョンを持っているかを確かめ（`needsToRecompute`）、再実行します。`computed` を読むときも同じように refresh し、ソースのバージョンが動いたときだけ再計算するので、ダイヤモンドの合流点は両側の後に1回だけ計算されます。MobX や Jotai と同じく、プルによってグリッチフリーです。

ここでも依存関係は実行のたびに追跡されますが、ノードからソースへのリンクは連結リストで、再実行はそれに印を付けて使い回します（`prepareSources`、`cleanupSources`）。前回と同じものを読む実行は何もアロケートせず、どの購読者リストにも触れません。そのため、単一ステート（{/* bench:single-state/preact-signals-over-synstate */}1.2{/* /bench */}倍）・派生チェーン（{/* bench:derived-chain/preact-signals-over-synstate */}0.9{/* /bench */}倍）・ダイヤモンド（{/* bench:diamond/preact-signals-over-synstate */}1.0{/* /bench */}倍）のいずれでも、行は SynState {/* bench:compare/small-graphs/preact-signals-overhead */}と同程度{/* /bench */}です。最悪の行は{/* bench:summary/worst/preact-signals-scenario */}[派生チェーン](#シナリオ-派生チェーン){/* /bench */}です。

### Zustand と Valtio

どちらも単一ステートでのみ計測しています。Zustand の `setState` は変更を新しいオブジェクトにマージし（`Object.assign`）、各リスナーにそれを渡して呼ぶだけで、SynState とほとんど変わりません（{/* bench:single-state/zustand-over-synstate */}1.2{/* /bench */}倍）。Valtio の書き込みはプロキシの `set` トラップを通り、そこで古い値と比較し、オブジェクトの値ならそれ自身のプロキシで包み、バージョン番号を進め、操作を記録します。`subscribe` が登録したリスナーは、その操作を配列で受け取ります（{/* bench:single-state/valtio-over-synstate */}11{/* /bench */}倍）。
