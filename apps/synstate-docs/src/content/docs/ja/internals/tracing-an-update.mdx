[SynState がグリッチを解決した方法](/mono/synstate/ja/internals/how-synstate-solved-the-glitch/)では、キューを深さごとのバケットとして説明しました。このページでは、それを実装しているコードを、「スキップされた更新の処理」のグラフの 2 回の更新と、subscriber が別の更新の中で始める更新で、フィールド単位に追います。各ステップには、そのステップを実行した後の値が表示されます。`propagation-state.mts` のモジュール状態、更新の `UpdateQueue` の private フィールド、実行中の関数のローカル変数、そして各ノードの 4 つのフィールドです。

## グラフ

`combine` とその後の `map` は別々のノードなので、前のページの `C` は、ここでは `BD`（`combine`）と `C`（`map`）の 2 つになります。

```tsx
import { combine, createState, filter, map } from 'synstate';

const [A, setA] = createState(0);

const B = A.pipe(map((n) => n * 10)); // depth 1

const D = A.pipe(filter((n) => n % 2 === 0)); // depth 1

const BD = combine([B, D]); // depth 2

const C = BD.pipe(map(([b, d]) => b + d)); // depth 3

const E = D.pipe(map((n) => n * 10)); // depth 2

setA(1); // B = 10, BD = [10, 0], C = 10; D rejects 1, so E is not reached

setA(2); // B = 20, D = 2, BD = [20, 2], E = 20, C = 22
```

## キューの置き場所

| 場所                        | フィールド                                        | 持っているもの                                                                                                                                                                     |
| :-------------------------- | :------------------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `propagation-state.mts`     | `propagation.depth`、`propagation.outermostToken` | 実行中の `startUpdate` の数と、最も外側の更新のトークンです。`depth > 0` の間にルートへ書き込むと、更新の中からの書き込みとして一度だけ警告が出ます。                              |
|                             | `queueState.level`                                | この SynState のコピーで開いている更新の数です。これを 1 に上げた更新がリストを所有します。                                                                                        |
|                             | `heads[i]`、`tails[i]`                            | リストを所有する更新の、深さ `base + i` のリストの先頭と末尾のノードです。配列は更新をまたいで使い回すので、更新ごとのメモリ確保はありません。                                     |
| `UpdateQueue`（＝トークン） | `#base`                                           | バケット 0 の深さです。更新を始めたノードの深さ + 1 で、ノードはバケット `node.depth - base` に入ります。                                                                          |
|                             | `#ownsLists`                                      | この更新がコピー内で最も外側の更新かどうかです。true なら `heads`・`tails` とノード自身のフィールドを使えます。                                                                    |
|                             | `#size`                                           | 使っているバケットの数です。drain のループはここまで回り、ループ中にも増えます。                                                                                                   |
|                             | `#spill`、`#spilled`                              | リストに入れられないノードのための、深さごとの配列と Set です（[後述](#spill-が使われるとき)）。初めて使うときに作るので、ここでの 2 回の更新ではどちらも `undefined` のままです。 |
| 各ノード                    | `updateToken`                                     | そのノードが最後に発行した更新のトークンです。子は、渡されたトークンとこれを比べます。                                                                                             |
|                             | `snapshot`                                        | ノードの現在の値です。                                                                                                                                                             |
|                             | `queuedFor`                                       | ノードが待っているリストの更新、または `undefined` です。これを確かめることで、1 回の更新でノードがキューに入るのは 1 回だけになります。                                           |
|                             | `nextInQueue`                                     | 同じリストの次のノードです。                                                                                                                                                       |

### `heads` と `tails` が要る理由

バケットは、ノード自身を通してつないだ単方向の連結リストです。キューに入ったノードは、同じバケットの次のノードを `nextInQueue` で指します。そのためノードをキューに入れても何も確保せず、更新がノードについて持つ情報は、すべてそのとき読んでいるノード自身の上にあります。このリストは先頭のノードからしかたどれないので、更新は先頭を `heads[i]` に持ちます。また、末尾に一定時間で足すには最後のノードが要るので、それを `tails[i]` に持ちます。`tails` がなければ、`enqueueChildren` のたびにリストを末尾までたどるか、先頭に足して、同じ深さのノードを入れた順の逆に訪れることになります。下の更新 2 では、`B` が `BD` を `heads[1]` かつ `tails[1]` にし、`D` は `BD` がすでに入っているのを見て、`tails[1]` を通してその後ろに `E` をつなぎます。`drain` は `heads[1]` から `BD`、`E` の順にたどります。

この 2 つの配列は `UpdateQueue` のフィールドではなくモジュール状態なので、一度だけ確保して、すべての更新で使い回します。同時に使える更新が 1 つだけなのもそのためで、使うのはコピー内で最も外側の更新、つまり `#ownsLists` を持つ更新です。

図では、ノードに付いた水色のタグはそのノードを指している `heads[i]` か `tails[i]`、ピンクのタグはそのノードを持っているローカル変数です。`enqueueChildren` の `child`、`drain` の `curr`・`next`・`node` があります。黄色の点線の輪はノードの `queuedFor` が設定されていること、黄色の点線の矢印は `nextInQueue` のつながりを表します。ピンクで強調されたフィールドは、そのステップで変わったものです。ステップは下に表示したコードのモデルから生成しています。このページのサンプルのテストで、ライブラリが同じ順序で発行することを確かめています。

## 更新 1：`setA(1)`（奇数）

<PropagationTrace scenario="filterDiamond" update={1} lang="ja" />

- `B` と `D` は同じリストで待ちます。2 つをつなぐのは `B.nextInQueue = D` だけで、`B` 自身に書き込まれます。
- ループが `index = 1` にいる間に、`BD` が `C` をキューに入れて `#size` が 2 から 3 に増えます。ループは毎回 `index` と `#size` を比べるので、新しいバケットにも届きます。
- `D` は訪問されますが 1 を通さず、`setNext` せずに戻ります。`t0` のままで、`BD` も `E` もキューに入れません。`BD` は `B` がキューに入れたので訪問され、`B.updateToken === t1` と `D.updateToken === t0` を見ます。`E` には一切触れません。

## 更新 2：`setA(2)`（偶数）

<PropagationTrace scenario="filterDiamond" update={2} lang="ja" />

- `D` は 2 を通して子をキューに入れます。`BD` は `B` によってすでに `queuedFor === t2` になっているので飛ばします。ノードが 2 回キューに入らないのは、この比較 1 つのおかげです。`E` はその後ろに、`BD.nextInQueue = E` と `tails[1] = E` でつながります。
- ノードは取り出したとき、`tryUpdate` の前に切り離されます（`nextInQueue` と `queuedFor` が `undefined` に戻ります）。更新が終わると、キューのフィールドはすべて `undefined` に戻り、`heads` と `tails` は次の更新のために長さを保ちます。

## subscriber からの書き込み

ルートに書き込む subscriber は、呼び出し元の更新がまだ drain している間に新しい更新を始めます。SynState はこの書き込みを通し、ルートごとに一度だけ警告します。グラフの subscriber が途中の状態を見ることになるからです。このグラフでは、1 回の `setA` で `BDR` が 2 回発行します。

```tsx
import { combine, createState, map } from 'synstate';

const [A, setA] = createState(0);

const [R, setR] = createState(0);

const B = A.pipe(map((n) => n * 10)); // depth 1

const D = A.pipe(map((n) => n * 100)); // depth 1

const BDR = combine([B, D, R]); // depth 2

// A write from a subscriber: an update nested in the one that reached D.
D.subscribe((d) => {
    if (d > 0) {
        setR(d);
    }
});

const mut_received: (readonly number[])[] = [];

BDR.subscribe((values) => {
    mut_received.push(values);
});

setA(1); // warns once: a root written to from a subscriber

// [0, 0, 0], then [10, 100, 100] twice: in setR(100), then in setA(1)
```

<PropagationTrace scenario="nestedWrite" update={1} lang="ja" />

- `B` は、`D` の subscriber が動く前に `BDR` を `t1` に入れます。`setR(100)` が `t2` を始めたとき、`BDR` はすでに `t1` のリストで待っています。`BDR.queuedFor` は `t1` で、1 本しかない `nextInQueue` はそのリストのものです。
- `t2` はこのコピーで 2 つ目に開いた更新（`queueState.level` が 2）なので、`#ownsLists` は false です。`heads`・`tails` にも、どのノードの `queuedFor`・`nextInQueue` にも触れません。`BDR` を `#spill[1]` に入れて `#spilled` に記録し、`drain` はそこから `BDR` を訪問します。
- `t2` は `D` の subscriber の中で最後まで動きます。`t1` が次のノードを訪問する前に drain され、閉じられます。`t1` のリストはそのままなので、`t1` は `heads[1]` からもう一度 `BDR` を訪問し、`BDR` はトークンごとに 1 回ずつ `[10, 100, 100]` を発行します。`t1` には、`t2` がすでに `BDR` を最新にしたことが分かりません。
- `propagation.depth` は両方の更新を数えるので、`outermostToken` は `t1` のままで、`runAfterPropagation` で後回しにした処理は `t1` の `endPropagation` まで待ちます。

値を導出にすれば（`const R = D.pipe(…)`）、警告も 2 回目の発行も起きません。1 回の更新が、親がすべて確定した状態で `BDR` に 1 回だけ届きます。

:::caution[終わらない書き込み]
入れ子の更新は、subscriber の中でコールスタックに積まれたまま最後まで動きます。そのため、自分を呼んだ更新に書き戻す subscriber は再帰します。直接書き戻す `A.subscribe((a) => setA(a + 1))` も、別のルートを経由する `A.subscribe((a) => setB(a + 1))` と `B.subscribe((b) => setA(b + 1))` の組み合わせも同じです。書き込むたびに、直前の更新の中にもう 1 つ更新が開きます。`queueState.level` が 1 段上がり、その更新は届いたノードを自分の `#spill` に入れます。これは SynState が止めるまで続きます。入れ子の 101 段目（`maxUpdateNesting`）を開こうとする書き込みが、ループであることを示すエラーを投げます。スタックがあふれる前に止まり、いちばん外側の `setA` がそのエラーを呼び出し元に伝えます。抜ける途中で各 `startUpdate` が `finally` で自分の更新を閉じるので、その後の更新はきれいな状態から始まります。ただし、それまでに書き込まれた値は残ります。

収束する書き込みは自然に止まります。`createState` は現在の値と等しい値を捨てる（`equals`、既定は `Object.is`）ので、`A.subscribe((a) => setA(a))` は 1 周で終わります。いずれ偽になる条件の下での書き込みも同様です。収束する書き込みでも、入れ子が 100 段を超えれば同じく止まります。上限は SynState のコピーごとに数えます。
:::

## spill が使われるとき

filter のダイヤモンドの 2 回の更新では `#spill` を使いません。一度に動く更新は 1 つで、SynState のコピーも 1 つだからです。次の 2 つの場合には、ノードはリストではなく spill に入ります。

- **ネストした更新**（上で追ったもの）。`queueState.level` が 2 以上なので、内側の `UpdateQueue` は `#ownsLists === false` です。届いたノードはすべて spill に入れ、外側の更新のリストはそのままにします。
- **別の更新のリストで待っているノード。** ノードの `queuedFor` が別の更新のトークン（上の `BDR` のように外側の更新のもの、または同じプログラムに読み込まれた別の SynState のコピーの更新のもの）のときは、ノードの `nextInQueue` は 1 本しかなく使用中なので、つなぐ代わりに spill に入れます。コピーが 2 つあると、どちらの更新も `#ownsLists` を持てるので、この確認が一方のリストを他方が壊さないようにしています。

`drain` は、ある深さのリストの直後に、その深さで spill に入れたノードを訪問します。そのため訪問は深さの順のままです。`tryUpdate` が例外を投げた場合は、`close` がリストに残ったものを切り離すので、次の更新は空のリストから始まります。
