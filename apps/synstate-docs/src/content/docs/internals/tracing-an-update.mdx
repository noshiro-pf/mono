[How SynState Solved the Glitch](/mono/synstate/internals/how-synstate-solved-the-glitch/) described the queue as buckets, one per depth. This page follows the code that implements them, field by field, through two updates of the graph from "Handling skipped updates", and then through an update that a subscriber starts inside another. Each step shows what the code holds after it: the module state of `propagation-state.mts`, the private fields of the update's `UpdateQueue`, the local variables of the function running, and four fields of every node.

## The graph

`combine` and the `map` after it are two nodes, so the `C` of the previous page appears here as `BD` (the `combine`) and `C` (the `map`):

```tsx
import { combine, createState, filter, map } from 'synstate';

const [A, setA] = createState(0);

const B = A.pipe(map((n) => n * 10)); // depth 1

const D = A.pipe(filter((n) => n % 2 === 0)); // depth 1

const BD = combine([B, D]); // depth 2

const C = BD.pipe(map(([b, d]) => b + d)); // depth 3

const E = D.pipe(map((n) => n * 10)); // depth 2

setA(1); // B = 10, BD = [10, 0], C = 10; D rejects 1, so E is not reached

setA(2); // B = 20, D = 2, BD = [20, 2], E = 20, C = 22
```

## Where the queue lives

| Where                     | Field                                             | What it holds                                                                                                                                                                              |
| :------------------------ | :------------------------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `propagation-state.mts`   | `propagation.depth`, `propagation.outermostToken` | How many `startUpdate` calls are running, and the token of the outermost one. A root written to while `depth > 0` is written to from inside an update, and warns once.                     |
|                           | `queueState.level`                                | How many updates of this copy of SynState are open. The update that raises it to 1 owns the lists.                                                                                         |
|                           | `heads[i]`, `tails[i]`                            | The first and the last node of the list of depth `base + i`, for the update that owns the lists. The arrays are kept from one update to the next, so an update allocates nothing for them. |
| `UpdateQueue` (the token) | `#base`                                           | The depth of bucket 0: the depth of the node that started the update, plus one. A node goes in bucket `node.depth - base`.                                                                 |
|                           | `#ownsLists`                                      | Whether this update is the outermost one of its copy, and so may use `heads`, `tails` and the nodes' own fields.                                                                           |
|                           | `#size`                                           | How many buckets are in use. The drain loop runs up to it, and it grows while the loop runs.                                                                                               |
|                           | `#spill`, `#spilled`                              | An array per depth, and a set, for the nodes that cannot go in the lists (see [below](#when-spill-is-used)). Made on first use, so both stay `undefined` in the two updates here.          |
| every node                | `updateToken`                                     | The token of the last update the node emitted in. Its children compare it with the token they are given.                                                                                   |
|                           | `snapshot`                                        | The node's current value.                                                                                                                                                                  |
|                           | `queuedFor`                                       | The update whose list the node waits in, or `undefined`. Checking it is what queues a node only once per update.                                                                           |
|                           | `nextInQueue`                                     | The next node in the same list.                                                                                                                                                            |

### Why `heads` and `tails`

A bucket is a singly linked list threaded through the nodes themselves: a queued node points to the next one in its bucket with `nextInQueue`, so queuing a node allocates nothing, and everything the update keeps about a node is on the node it is already reading. Such a list is reachable only from its first node, so the update keeps it in `heads[i]`; and adding a node at the end in constant time needs the last one, so it keeps that in `tails[i]`. Without `tails`, each `enqueueChildren` would walk the list to its end, or put the node at the front and so visit the nodes of a depth in the reverse of the order they were queued in. In update 2 below, `B` makes `BD` both `heads[1]` and `tails[1]`; `D` then finds `BD` already queued and links `E` after it through `tails[1]`; and `drain` walks `BD`, then `E`, from `heads[1]`.

The arrays are module state rather than fields of the `UpdateQueue`, so they are allocated once and reused by every update. That is also why only one update at a time may use them: the outermost one of the copy, the one with `#ownsLists`.

In the drawing, a cyan tag on a node is `heads[i]` or `tails[i]` pointing at it, and a pink tag is a local variable holding it: `child` in `enqueueChildren`, and `curr`, `next` and `node` in `drain`. A dashed yellow ring means the node's `queuedFor` is set, and a dashed yellow arrow is a `nextInQueue` link. A field highlighted in pink changed in this step. The steps come from a model of the code below them; the tests of the samples on this page check that the library emits in the same order.

## Update 1: `setA(1)`, an odd value

<PropagationTrace scenario="filterDiamond" update={1} lang="en" />

- `B` and `D` wait in the same list. The only link between them is `B.nextInQueue = D`, written into `B` itself.
- `#size` grows from 2 to 3 while the loop is at `index = 1`, when `BD` queues `C`. The loop compares `index` with `#size` on every turn, so it reaches the new bucket.
- `D` is visited, rejects 1, and returns without `setNext`: it keeps `t0`, and queues neither `BD` nor `E`. `BD` is visited anyway, because `B` queued it, and sees `B.updateToken === t1` and `D.updateToken === t0`. `E` is never touched.

## Update 2: `setA(2)`, an even value

<PropagationTrace scenario="filterDiamond" update={2} lang="en" />

- `D` passes 2 and queues its children. `BD` already has `queuedFor === t2`, put there by `B`, so it is skipped: that one comparison keeps a node from being queued twice. `E` is linked after it, with `BD.nextInQueue = E` and `tails[1] = E`.
- A node is unlinked (`nextInQueue` and `queuedFor` back to `undefined`) when it is taken out, before its `tryUpdate`. When the update ends, every queue field is `undefined` again, and `heads` and `tails` keep their length for the next update.

## A write from a subscriber

A subscriber that writes to a root starts an update while the update that called it is still draining. SynState lets the write through, and warns once per root, because the subscribers of the graph can then see intermediate states: in this graph, `BDR` emits twice for one `setA`.

```tsx
import { combine, createState, map } from 'synstate';

const [A, setA] = createState(0);

const [R, setR] = createState(0);

const B = A.pipe(map((n) => n * 10)); // depth 1

const D = A.pipe(map((n) => n * 100)); // depth 1

const BDR = combine([B, D, R]); // depth 2

// A write from a subscriber: an update nested in the one that reached D.
D.subscribe((d) => {
    if (d > 0) {
        setR(d);
    }
});

const mut_received: (readonly number[])[] = [];

BDR.subscribe((values) => {
    mut_received.push(values);
});

setA(1); // warns once: a root written to from a subscriber

// [0, 0, 0], then [10, 100, 100] twice: in setR(100), then in setA(1)
```

<PropagationTrace scenario="nestedWrite" update={1} lang="en" />

- `B` queues `BDR` in `t1` before `D`'s subscriber runs. When `setR(100)` starts `t2`, `BDR` already waits in `t1`'s list: `BDR.queuedFor` is `t1`, and its one `nextInQueue` belongs to that list.
- `t2` is the second update open in this copy (`queueState.level` is 2), so its `#ownsLists` is false: it touches neither `heads` and `tails` nor any node's `queuedFor` and `nextInQueue`. It puts `BDR` in `#spill[1]` and records it in `#spilled`, and its `drain` visits `BDR` from there.
- `t2` runs to the end inside `D`'s subscriber: drained and closed before `t1` visits another node. `t1`'s lists are as it left them, so `t1` visits `BDR` again from `heads[1]`, and `BDR` emits `[10, 100, 100]` once per token. `t1` cannot tell that `t2` has already brought `BDR` up to date.
- `propagation.depth` counts both updates, so `outermostToken` stays `t1`, and the work deferred with `runAfterPropagation` waits for `t1`'s `endPropagation`.

Deriving the value instead (`const R = D.pipe(…)`) avoids the warning and the second emission: the one update reaches `BDR` once, with every parent settled.

:::caution[A write that never stops]
The nested update runs to its end inside the subscriber, on the call stack. So a subscriber that writes back into the update that called it recurses, either directly, `A.subscribe((a) => setA(a + 1))`, or through another root, `A.subscribe((a) => setB(a + 1))` with `B.subscribe((b) => setA(b + 1))`. Each write opens one more update inside the last one (one more level of `queueState.level`, which spills what it reaches into its own `#spill`) until SynState stops it: the write that would open the 101st nested update (`maxUpdateNesting`) throws an error that names the loop, rather than letting the stack overflow, and the outermost `setA` passes it on. On the way out, each `startUpdate` closes its update in a `finally`, so the updates after it start from a clean state, but the values written so far stay.

A write that converges stops by itself. `createState` drops a value equal to the current one (`equals`, `Object.is` by default), so `A.subscribe((a) => setA(a))` ends after one round, as does a write behind a condition that becomes false. A chain that would converge but nests more than 100 deep is stopped too. The limit counts the updates of one copy of SynState.
:::

## When `spill` is used

The two updates of the filter diamond never touch `#spill`: one update runs at a time, and there is one copy of SynState. Two cases send a node there instead of the lists:

- **A nested update**, as traced above. `queueState.level` is 2 or more, so the inner `UpdateQueue` has `#ownsLists === false`, and it spills every node it reaches, leaving the outer update's lists as they are.
- **A node waiting in another update's list.** When a node's `queuedFor` is another update's token — the outer update's, as `BDR`'s is above, or one of another copy of SynState in the same program — its one `nextInQueue` is taken, so the update spills the node instead of linking it. With two copies, both updates can have `#ownsLists`, and this is the check that keeps one from breaking the other's list.

`drain` visits the nodes spilled at a depth right after that depth's list, so they are still visited in order of depth. If a `tryUpdate` throws, `close` unlinks what is left in the lists, so the next update starts from empty lists.
